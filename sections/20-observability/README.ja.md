# 20 · Observability & evaluation

[English](README.md) · [繁體中文](README.zh-TW.md) · [简体中文](README.zh-CN.md) · **日本語** · [한국어](README.ko.md)

> 見えないものを修正することはできませんし、誰も記録していないランを採点することもできません。

エージェントは無人で実行され、副作用が発生し、お金がかかります。モデル呼び出しはブラックボックスです。トークンを書き込み、実際のアクションをトリガーします。

計測機器がなければ、基本的な質問に答えることはできません。それは何をしたのでしょう。ツールが失敗した頻度。このセッションの費用はいくらでしたか。

このセクションはレコードを所有します。各ステップで何を行ったか、それにどれくらいのコストがかかったのかが記録され、その記録は保管できる程度にきれいに保たれます。

変更によって品質が良くなったのか悪くなったのかは別の仕事です。セクション 23 はその役割を果たし、このセクションの記録に基づいて実行されます。

記録を放置しておくと、あらゆるコストの高騰に驚かされます。すべてのバグレポートは再現不可能です。 eval セットには実際に引き出せるものは何もありません。

## メカニズム

![機構図](assets/20-observability.png)

ループの制御フローには決して触れない 2 つの分離可能なパイプライン。

テレメトリはインラインで実行されます。各ステップでファイア アンド フォーゲット ロガーが呼び出されます。

イベントはシンク、端末などの宛先、ファイル、または Datadog などのバックエンドに送信されます。
ロガーはシンクが接続されるまでイベントをキューに入れ、その後サンプリング、機密フィールドのスクラブを行って、ファンアウトします。

Evaluation は、独自のタスク セットに対してオフラインで実行されます (セクション 23)。このセクションで記録するのは、そのタスク セットが何から構築されているかです。

- `emit` はブロックも発生もしないため、ロギング障害によってループが停止したりクラッシュしたりすることはありません (セクション 1)。
- イベントはシンクが接続されるまでキューにバッファリングされ、その後排出されるため、テレメトリの準備が整う前にループがログを記録できます。
- サンプリングはレートに基づいてイベントをドロップします。スクラビングでは許可リストに登録されたフィールドのみが保持されるため、コードとパスが漏洩することはありません。
- コストはモデルごとに 1 米ドルに累積され、ライブおよび終了時に表示されます。

### 新機能: ファイアアンドフォーゲットイベントロギング

`telemetry.py` は、シンクが接続されるまでキューに入れられたイベントを発行し、その後サンプリング、スクラブ、ファンアウトします。 `emit` は決して発生しません:

```python
def emit(self, name, **meta):                          # src/telemetry.py
    if not self.sinks:
        self._queue.append((name, meta))               # buffer until a sink is ready
        return
    self._deliver(name, meta)

def _deliver(self, name, meta):
    if not self.sample(name):                          # dropped by sampling rate
        return
    clean = scrub(meta)                                # allowlist before any backend sees it
    for sink in self.sinks:
        try:
            sink(name, clean)
        except Exception:                              # one bad sink never breaks the loop
            pass
```

- シンクが接続される前に、イベントは `_queue` にバッファーされます。 `attach` は同じ `_deliver` パスを介してそれらを排出するため、キューに入れられたイベントもサンプリングされ、スクラブされます。
- `scrub` は `SAFE_FIELDS` のみを保持するため、安全であることが不明な値 (コード、ファイル パス、プロンプト) はバックエンドに到達しません。
- スローするシンクは飲み込まれるため、1 つの壊れたバックエンドがループをストールしたりクラッシュしたりすることはありません。

### 新機能: モデルごとのコストとオフライン eval

コストはモデルごとに累積され、1 つの実行中の USD 合計になります。

```python
def add(self, model, input_tokens, output_tokens):    # src/telemetry.py
    i, o = self.by_model.get(model, (0, 0))
    self.by_model[model] = (i + input_tokens, o + output_tokens)
    pi, po = PRICES.get(model, (0.0, 0.0))             # modelCost.ts pricing tiers
    self.cost_usd += input_tokens * pi + output_tokens * po
    return self.cost_usd
```

- `add` はトークンごとの価格を検索し、支出を `cost_usd` にロールし、その数値はライブおよび終了時に表示されます。
- その合計はセッションをカバーします。どのタスクにお金が費やされたかは決して明らかにされません。

ここの `run_eval` は、存在する最小の eval です。候補ビルドに対して固定タスク セットを再生し、パスをカウントし、レートを返します。
セクション 23 では、環境、シミュレートされたユーザー、および繰り返し実行を同じエントリ ポイントに配置します。また、このレートのわずかな低下が通常ノイズである理由も説明されます。

### 統合方法

デモでは、モデル ラッパーのテレメトリを利用します。ループは変わりません。

```python
def model(messages, registry, system):
    r = client.messages.create(...)
    cost.add(MODEL, r.usage.input_tokens, r.usage.output_tokens)   # cost rollup
    tel.emit("model_call", model=MODEL, tokens=..., cost_usd=...)  # scrubbed event
    return r
run_turn([...goal...], lambda m, r, s: model(m, r, SYSTEM), reg, Session(mode=DEFAULT))   # the one agent call
```

- テレメトリは外部から観察します。ラッパーはイベントを発行し、コストを追跡するため、`run_turn` とディスパッチはセクション 13 とバイト同一のままです。
- シンクは各イベントを出力します。セッションコストは最後に出力されます。次に、オフラインの `run_eval` が固定タスク セットを採点します。
- 上流のすべては変更されません。 Observability はサイドオブザーバーであり、ループの新しいステップではありません。

### さらに読む

これは `src/` にはありません。これは、ai-agent-book と 2 つのトレース標準に基づいており、表内のシステムについては確認されていません。

**フラット イベントではなく、スパンです。** スパンは、モデル呼び出し、ツール呼び出し、取得など、実行内の 1 つの作業です。トレースとは実行全体です。
すべてのスパンは次のことを記録します。

- いつ始まったのか、どれくらい時間がかかりましたか、
- それが成功したかどうか、
- どのスパンがその親であるか、
- 作品を説明する自由形式の属性。

親リンクが重要です。実行のスパンをツリーに変換するので、ツリーを上から読むと、どのステップが失敗したかがわかります。
どのステップが遅かったのか、各ブランチにかかるコストは何か。

フラットイベントではそれができません。イベントは、呼び出しが発生したことを示すものであり、呼び出しがどのステップに属したかを示すものではありません。
1 つのユーザー リクエストが、多くのモデル呼び出し、ツール呼び出し、取得に変わる可能性があり、一部は他のリクエスト内にネストされ、一部は同時に実行されます。
タイムスタンプで並べ替えるのは推測です。

2 つの標準によってスパンの形状が固定されるため、バックエンドを推測する必要はありません。

- OpenTelemetry は、スパン自体 (トレース ID、親 ID、タイミング、ステータス、属性) を定義します。
- OpenInference は、その上の LLM 作業にプロンプト、完了、モデル、トークン数、ツール呼び出しという名前を付けます。

これらの名前に対してインストルメンテーションを一度書き込むと、バックエンドの切り替えは書き換えではなく構成変更になります。

エクスポートは `emit` と同じルールに従い、ホット パスから外されます。スパンはキューに入り、バックグラウンド ワーカーがそれらをバッチで送信します。
したがって、遅いコレクタでは実行コストはかかりません。このセクションの `emit` は、これらすべてのフラット バージョンです。
トレース ID と親 ID を同じイベントに追加すると、ツリーがそこに表示されます。

**非線形コストとタスクごとの上限** コストはモデルが読み取るトークンの数を追跡し、毎ターン会話全体を再送信します。
したがって、2 ターン目に戻ってきた tool result は、3、4、5 ターン目に再び支払われます。
コンテキストに追加されたものはすべて、その後のターンごとに支払われ、合計はターン数よりも速く増加します。
歩数だけでは予測できません。

2 つの harness 機能は料金の一部を削減しますが、それらの節約額は合計されません。

- Prompt caching (セクション 10) は、同じままのプレフィックスを割引きします。
- 圧縮 (セクション 8) は、古いターンをコンテキストから削除します。

これらは重複しています。圧縮により、キャッシュによって割引されるのと同じトークンが削除されます。

1 つのセッションの合計では、どのタスクに費用が費やされたかが決して示されないため、これらすべてが隠蔽されます。
したがって、タスクごとのコストを追跡し、各タスクに上限を設定します。天井は、ステップ制限が終了しないループを停止するのと同じように、実行を停止します (セクション 1)。
この本がここでの唯一の情報源であり、外部の情報は何も引用していないため、このコスト モデルは 1 人の著者のフィールド アカウントとして読んでください。

**トレースは eval セットにフィードします。** 2 つのパイプラインは一方向に結合し、実稼働トレースは eval タスクになります。 3 つのステップで一方が他方に変わります。

- **選択** 学習する価値のある実行を保持します。エラーが発生した実行、ユーザーが再試行または修正した実行、および他の実行よりはるかにコストが高かった実行です。
  うまくいった実行は何も追加しません。
- **スクラブ** コードとパスをバックエンドに入れないようにするホワイトリストにより、タスク ファイルにもコードとパスが入れられなくなります。
- **再構築** トレースは開始状態とすべてのツール呼び出しを保持するため、タスクのセットアップと実行が到達するはずの結果の両方を提供します。

これを継続的に実行すると、eval セットはユーザーの実際の操作に従います。セクション 23 では、そこに着地したものを採点します。

各エージェントがテレメトリを発行し、支出を追跡し、eval セットをフィードする方法。

| | Claude Code | mini-swe-agent | deepseek-harness |
| --- | --- | --- | --- |
| **長所** |生産の可視性が高く、安価で安全です。 |クラッシュした実行でもファイルが残ります。 |特別に計測するものは何もありません。モデルが認識したものがログに記録されます。 |
| **短所** |答えが良かったかどうかではなく、何が起こったかを述べます。 |実稼働テレメトリはほとんどありません。 |編集ルールは配布されません。配達は紛失したり、繰り返したりする可能性があります。 |
| **理由** |プロダクションはループに触れずに視聴する必要があります。 |ベンチマークはオフラインで評価されるため、完全な記録が重要です。 |セッションログはすでに記録されているため、エクスポートします。 |
| **方法: テレメトリー** |イベントはシンクのキューに入れられ、サンプリングとスクラブが行われます。 |実行ごとに 1 つの軌跡ファイルがあり、ステップごとに保存されます。 |セッション イベントは、リダクション パスを通じてミラーリングされます。 |
| **方法: コスト追跡** |モデルごとのトークンはセッション合計に組み込まれます。 |コールごとの価格は実行合計とグローバル合計に反映されます。 |リプレイパスでは、ドルではなくログイントークンの価格が設定されます。 |
| **方法: eval フィード** |ソースにはありません。スクラブされたトレースは回帰ケースになります。 |保存された軌道はベンチマーク ランナーにフィードされます。 |記録されたランは、キーなしでフィクスチャーとして再生されます。 |

## 障害モード

- **ホット パス上のテレメトリ。** ブロックまたはスローするロギング呼び出しにより、ループが停止します (セクション 1)。ネットワーク上で待機するスパン エクスポータも同様の処理を行います。
  軽減策: プリシンク キュー、シンクごとのキルスイッチ、バックグラウンド ワーカーからのバッチ エクスポートによるファイア アンド フォーゲット。
- **機密データがログに漏洩します。** コード、ファイル パス、またはプロンプトが一般アクセスのバックエンド、またはトレースから構築されたタスク ファイルに到達します。
  軽減策: ログ可能なフィールドを許可リストに登録し、ファンアウトまたは保存する前に残りをスクラブします。
- **親リンクのないフラット ストリーム** どのモデル呼び出しがどのステップに属していたのかは何も示されていないため、失敗した実行はタイムスタンプによって結合する必要があります。
  軽減策: バックエンドがすでに理解している命名規則に基づいて、すべてのイベントのトレース ID と親スパン ID。
- **コスト ドリフトは気づかれません。** モデル スワップや暴走ループにより支出が増大し、合計 1 つのセッションにより、それを燃やした単一のタスクが隠蔽されます。
  緩和策: モデルごとおよびタスクごとの合計が、ライブおよび終了時に明らかになり、タスクごとの上限、およびループのステップ上限 (セクション 1)。
- **eval セットは実稼働環境からドリフトします。** オフライン タスクは実際の使用を逃すため、スイートはパスしますが、ユーザーは失敗します (セクション 23)。
  軽減策: 失敗した高価な実行のスクラブされたトレースをタスク セットにフィルタリングし続けます。
