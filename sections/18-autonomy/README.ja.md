# 18 · Autonomy

[English](README.md) · [繁體中文](README.zh-TW.md) · [简体中文](README.zh-CN.md) · **日本語** · [한국어](README.ko.md)

> 人間によるプロンプトなしでループを実行します。アイドル状態で、ボードをスキャンし、準備完了のタスクを要求し、それを実行します。

自律性はセクション 1 (agent loop) であり、各ターンを開始するための人間のプロンプトなしで実行されます。

チームを生成すると、各ワーカーに次のタスクを渡すリードとなる明白な設計が行われます。

それはスケールが合わない。 10 件の未申請タスクは 10 件の手動割り当てを意味し、リードがボトルネックになります。

ワーカーが終了した瞬間にアイドル状態になると、ロードしたばかりのコンテキストも無駄になります。

修正は、中央での割り当てではなく、自己組織化です。

中央割り当ては依然として実際の設計であり、出版されたマルチエージェントに関する研究のほとんどはこれを説明しています。
マネージャーパターンでは、各子エージェントがツールとして登録され、1 人のマネージャーがすべてのサブタスクを担当します。
マネージャーは計画全体を保持しているため、作業を指示したり、重複したタスクを削除したり、実行を早期に停止したりできます。
また、すべてのタスクに 2 回触れます。1 回目はタスクを配布し、もう 1 回目は結果を読み取ります。
2 つのデザインの価格は異なります。マネージャーは 1 つのグローバル順序を与え、すべてのタスクはマネージャーの順番を待ちます。
ボードはスループットを提供しますが、クレームが古くなるためロックが必要になります。このセクションではボードを構築します。

自律性では、アイドル状態のエージェントに次のことを許可する必要があります。

1. 何も関係がないことに注意してください (作業フェーズは `end_turn` に達しました)。
2. 共有ボードを見て、誰も所有していないタスクやブロックされていないタスクを探します。
3. 他のアイドルエージェントを争うことなく、エージェントを獲得します。
4. 要求されたタスクのループに再度入り、ボードが空になるまで繰り返します。

これを無視すると、すべてのエージェントは操り人形になります。人間またはリードが次のプロンプトをプッシュするのを待つため、スループットはディスパッチャがプロンプトを渡す速度によって制限されます。

## メカニズム

![機構図](assets/18-autonomy.png)

外側のループは agent loop をラップします。

内側のループは、セクション 1 の通常の `while` です。 `end_turn` に達しても、エージェントは戻りません。投票に入ります。

ポーリングは 2 つのチャネルを使用します。1 つはこのエージェントに宛てられたメッセージのダイレクト受信ボックス (セクション 16)、もう 1 つはアイドル状態のエージェントが要求できるタスクのアンダイレクト ボード (セクション 12) です。

最初にシャットダウン要求、次に受信箱メッセージ、次にボード上のタスクという優先順位でそれらをチェックします。

見つかったものはすべて次のプロンプトとなり、内側のループが再度実行されます。

- 内側のループはモデルの `stop_reason` で終了します。これはセクション 1 と同じ信号です。
- ポーリングでは最初にシャットダウンがチェックされるため、停止がピア メッセージに埋もれることはありません。
- 要求は、読み取り、チェック、ロックの下での書き込みです。所有されていない、ブロックされていないタスクを選択し、他のエージェントが行う前に所有権を書き込みます。
- タスクは依存関係が `completed` の場合にのみ要求できるため、エージェントはブロックされた作業を要求しません。

シャットダウン要求とその確認はセクション 17 プロトコルであるため、停止はハンドシェイクであり、強制終了ではありません。

### 新機能: アイドル投票

`autonomy.py` は、外側のループと 1 つのポーリング パスを追加します。 `next_action` は、受信トレイを一度空にしてから、最初に見つかったものを優先順位に従って返します。

```python
def next_action(proto, team, store, me):               # src/autonomy.py
    inbox = team.drain(me)
    shutdown = next((m for m in inbox if _is(m, "shutdown_request")), None)
    if shutdown is not None:                            # checked first, so chat cannot starve a stop
        proto.reply(shutdown, "shutdown_approved")
        return ("shutdown", shutdown["content"].get("reason"))
    chat = [m for m in inbox if isinstance(m["content"], str)]
    if chat:
        chat.sort(key=lambda m: m["from"] != "lead")   # lead before peers; sort is stable
        return ("message", _fold(chat))                # section 16's shared fold helper
    task = claim_next(store, me)                        # else claim the next ready task
    return ("task", task) if task is not None else None
```

- シャットダウン (確認して停止)、折りたたまれたチャット、または要求されたタスクのうちの最初のものを返します。
- チャットの前にシャットダウンがチェックされるため、ピア トラフィックが停止することはありません (セクション 16)。
- `claim_next` は、最初の保留中の所有されていないタスクを要求します。 `TaskStore.claim` はブロックされた作業を拒否し、クレームをシリアル化します (セクション 12)。
- `None` はアイドルを意味します。外側のループはスリープ状態になり、再度ポーリングします。

### ロックされた主張

投票ではタスクが提案されます。ロックは誰がそれを取得するかを決定します。 `claim_next` は、最も古いボードを最初にスキャンし、最初の未所有の保留中のタスクを提案します。

```python
def claim_next(store, me):                             # src/autonomy.py
    for t in store.list():                             # oldest first
        if t["status"] == "pending" and t["owner"] is None:
            got = store.claim(t["id"], me)             # read, check, write under a lock
            if got["ok"]:
                return got["task"]
            # not ok: another agent won it, or it just became blocked; try the next
    return None
```

`claim_next` のチェックはヒントにすぎません。2 つのアイドル状態のエージェントが同じタスクを所有されていないものとして同時に読み取ることができます。 `TaskStore.claim` (セクション 12) はロックの下で解決します。

```python
def claim(self, tid, owner):                           # src/tasks.py, section 12
    with self._lock():                                 # fcntl.flock: one claimer at a time
        task = self.get(tid)
        if task["owner"] is not None:                  # someone already won: back off
            return {"ok": False, "reason": "already_claimed"}
        unmet = [b for b in task["blockedBy"]
                 if (self.get(b) or {}).get("status") != "completed"]
        if unmet:                                       # a dependency is not done yet
            return {"ok": False, "reason": "blocked"}
        task["owner"], task["status"] = owner, "in_progress"
        self._write(task)
        return {"ok": True, "task": task}
```

- ロックにより、読み取り、チェック、書き込みが 1 つのアトミック ステップになるため、書き込み前にチェックが失効することはありません。
- 敗者はロック内を再読み取り、`owner` が設定されていることを確認し、`already_claimed` を取得します。 `claim_next` は次のタスクに進みます。
- ブロックされたタスクはここでも拒否されるため、依存関係が `completed` ではない作業をエージェントは要求しません。
- これは、2 つのスレッドが共有状態をめぐって競合する唯一の場所です。残りの投票はローカルです。

### 統合方法

外側のループは `run_turn` を外側からラップするため、ループと subagent パスは変わりません。

```python
def run_teammate(team, store, me, lead, work):         # src/autonomy.py
    proto, prompt, claimed = Protocol(team, me), None, None
    while True:
        if prompt is not None:
            work(prompt, claimed)                      # inner loop (section 1) does the claimed task
            prompt, claimed = None, None
            team.send(me, lead, {"type": "idle", "reason": "available"})
        action = next_action(proto, team, store, me)   # poll: shutdown, message, or task
        if action is None:                             # idle: sleep, then poll again
            time.sleep(POLL_INTERVAL); continue
        kind, payload = action
        if kind == "shutdown":
            return "shutdown"
        if kind == "task":
            prompt, claimed = task_prompt(payload), payload
        else:
            prompt = payload
```

- この `run_teammate` はセクション 17 で、もう 1 つの投票ソースがタスク ボードです。シャットダウン (セクション 17) とチャット (セクション 16) は変更されていません。
- `work(prompt, claimed)` は、要求されたタスクに対して `end_turn` への 1 つの内部ループを実行し、エージェントはそれが使用可能であることを通知します。
- 要求されたタスクは次のプロンプトになります。ポーリングで何も見つからなかった場合、ワーカーは独自の停止を決定します。
- その停止は次のいずれかのモードです: シャットダウン ハンドシェイク (セクション 17) までアイドル状態、または有限ボード上の空のポーリングの範囲の後に終了します。
- ここでは 1 つのワーカーが実行されますが、ループはエージェントごとに行われます。実際のチームは、1 つの共有ボードと受信トレイ セット上でリード ループと多くのワーカー ループを同時に実行します。
- リードは 1 つの積極的なステップを実行します。ツールを呼び出してチームと作業を構築し、完了します。
- `TeamCreate` および `SpawnTeammate` はセクション 16 のツールです。 `TaskCreate` がボードを投稿します (セクション 12)。
- `SpawnTeammate` は `runtime.start(...)` (セクション 13): リードのツール呼び出しにより、スレッド上でワーカーの自律ループが開始されます。
- スポーン後の作業のプルと停止の決定は、リードやスクリプトではなく、各ワーカー自身が行うことです。メインプロセスは、ワーカーの作業が終了するのを待つだけです。
- チームの形成、生成、ボードの投稿はモデルの決定です (セクション 16 および 12)。自律的主張は第 18 条の追加です。

### さらに読む

これは `src/` にはありません。これは、ai-agent-book および出版された研究に基づいたものであり、表内のシステムについては確認されていません。

**忙しい従業員に質問する** アンケートにより、従業員は次に何をすべきかがわかります。走っている作業員の様子をリーダーに伝えることはありません。

**ステータス呼び出しが弱い理由** ツール呼び出し中のワーカーはメッセージをリッスンしていません。したがって、通話はハングするか、空の状態で戻ってきます。
本当に行き詰まっている労働者は、答えようとしない労働者です。

**うまくいく 3 つの方法。** 最初の方法では作業者の助けが必要ですが、最後の方法では何も必要ありません。

1. メッセージで質問してください。ステータスリクエストを受信箱にドロップします (セクション 16)。ワーカーは次の投票で回答します。これは正確であり、ワーカーがまだポーリングしている間のみ機能します。
2. 合意された進行状況ファイルを読み取ります。ワーカーは、双方が知っているパスにステップごとに 1 行を追加します。読者が作業を中断することはありません。
3. 保存された軌跡を追跡します。 runtime はすでに毎ターンディスクに書き込みを行っています (セクション 13)。リードはそれらのターンを読み取り、ワーカーはまったく何もしません。

**ストールを見つける。** 最後の 2 つの方法では、それを無料で提供します。新しい書き込みがないことは新しい進行状況がないことを意味するため、ファイルが最後に書き込まれたのがいつであるかを確認してください。
1 つのしきい値がそれを決定に変えます。遅いツール呼び出しでは実行中に何も書き込まれないため、予想される最も遅い呼び出しよりも高いしきい値を設定します。それを超えて、立ち往生している労働者に電話します。
このしきい値は、スタックビジー障害モードが欠落していたトリガーです。リードは、永遠に待つ代わりに、タスクを取り戻すか、シャットダウン ハンドシェイク (セクション 17) を開始することができます。

**プールの予算** 世論調査には、労働者に請求をやめるように指示するものは何もありません。怠惰な労働者はすべて、もう 1 つのタスクを引き受けます。
したがって、作業が完了したときではなく、予算がなくなったときに実行が終了します。

**配布するもの** ある公開されたマルチエージェント システムでは、実行がうまくいくかどうかの違いの約 80% がトークンの使用だけで説明できることがわかりました。
したがって、割り当てる単位はターンではなくトークンです。 4 つのノブがボードとワーカー プールに取り付けられています。

- タスクごとの予算。各タスクには独自のステップ キャップとトークン キャップがあり、ポストされたときに書き込まれます。 1 つの暴走タスクでは、実行全体を使い切ることができません。
- 同時実行の上限。 `in_progress` に一度に格納できるタスクの数を制限します。理事会はすでにそれらをカウントしているため、上限を超えた請求は単純に失敗します。
- モデルの配置。最も思考が難しい場所に最強のモデルを置きます。計画の品質が結果を決定するため、リーダーはそのモデルを取得し、日常業務の従業員はより安価なモデルを実行します。
- 先制。従業員が予算を超過したり、しきい値を超えて停滞したりすると、そのタスクは取締役会に戻されます。次にそれを主張する人は、クリーンな状態から始めます。

**ワーカーに予算を示します。** 残額を知っているエージェントは、単に上限を増やすだけのエージェントとは異なる方法で予算を使います。
この結果は本書自身の実験から得られたものであるため、ある情報源がそれを裏付けています。コピーする数値ではなく、テストするものとして扱います。

## システムごと

アイドル状態のエージェントが自分の仕事を見つけて要求する方法。

| | Claude Code | deepseek-harness |
| --- | --- | --- |
| **長所** |ディスパッチャのボトルネックはありません。ウォッチャーは、他の場所で作成されたタスクも取得します。 |無人実行は予測可能であり、継続状態は永続的です。 |
| **短所** | 2 人のアイドル状態のエージェントが 1 つのタスクに注目できるため、ロックが競争に決着をもたらします。 | 1 人のエージェント、1 つの目標。目標が達成されたかどうかはモデル自体が判断します。 |
| **理由** |すべてのタスクを指示するリードがボトルネックになります。 |自律性は、モードではなく、予算化された権限レベルです。 |
| **方法: アイドル動作** | 500 ミリ秒のポーリング: シャットダウン、未読メッセージ、クレーム。 |完全にアイドル状態になると、次のラウンドが予約され、1 つのプロンプトがキューに入れられます。 |
| **方法: 仕事の主張** |ブロックされていないタスクの所有権をロックの下に書き込むため、1 つのクレーマーが勝ちます。 |目標の正確なリビジョンに対して次のラウンドを予約するか、失敗します。 |
| **方法: 自己組織化** |労働者はボードから手を引きます (セクション 12)。リードは合成しますが、ルートは作成しません。 |ボードはありません。エージェントは独自の目標を継続し、ファンアウトには制限があります。 |

## 障害モード

- **競合の要求** 2 人のエージェントがタスクを未所有として読み取り、両方ともそれを要求し、一方のエージェントの作業を削除します。チェックと書き込みをアトミックにするファイル ロック内で要求します (セクション 12)。
- **チャットによる飢餓。** ピアのチャットによりシャットダウン要求が埋もれるため、停止すべきエージェントがポーリングを続けます。通常のメッセージの前にシャットダウンを確認します (セクション 16)。
- **ブロックされた作業の時期尚早な要求。** エージェントは依存関係が完了していないタスクを要求し、その後停止します。 `blockedBy` が未解決の ID を保持しているタスクをスキップします (セクション 12)。
- **圧縮後のアイデンティティの喪失** 長時間走行しているチームメイトが実行途中 (セクション 8) で自動的に圧縮され、その役割を忘れてしまいます。役割が存続するように、system prompt を保存します。
- **ビジー状態でスタック、またはアイドル状態でスタック。** `end_turn` に到達しないフェーズでは、解放されることはありません。出口スピンのない投票。停止信号で終了（セクション 1）。各ポーリングを中止するかどうかを確認します。
- **検出されないストール。** ワーカーはタスクを保持しており、忙しそうに見えますが、どこにも到達できないため、ボードはタスクを解放しません。進行状況ファイルが最後に書き込まれたときを監視し、タスクを元に戻します。
- **無制限のプール支出。** アイドル状態のワーカーが要求を続けるため、予算がなくなった場合にのみ実行が終了します。すべてのタスクにステップとトークンの上限を与え、一度に実行する数に上限を設けます。
- **プリエンプション二重書き込み。** 解放されたタスクは古いワーカーの実行中に再利用されるため、2 つのエージェントが同じファイルを書き込みます。停止が確認された後にのみ解放してください (セクション 17)。

## 実行可能

[`src/`](src/) 17 を前方に繰り上げて次を追加します。

- [`autonomy.py`](src/autonomy.py): セクション 12 ボード上の外側ループとアイドル ポーリング (セクション 16 の `SpawnTeammate` が各ワーカーを開始します)。
- [`test.py`](src/test.py): シングルワーカーメカニズム、`TeamCreate` チェック、強制クレームレース (16 スレッド、1 タスク、1 勝者)、スレッドパイプライン、およびスポーンツールチェック。
- [`demo.py`](src/demo.py): リードが 1 歩進みます (`TeamCreate`、`TaskCreate`、`SpawnTeammate`)。労働者はボードからタスクを外し、ボードがなくなると作業を停止します。

メカニズム内のシングルワーカー `run_teammate` はティーチング削減です。

実際のチームは、1 つの共有ボードと受信トレイ セット上で、リード ループと複数のワーカー ループを同時に実行します。

セクション 13 ではスレッドの作業を開始します。セクション 12 およびセクション 16 のファイル ロックは、レース下で共有状態を安全に保ちます。

同時デモとクレームレーステストがそれを結び付けます。

```bash
python sections/18-autonomy/src/test.py         # offline checks, no key
uv run python sections/18-autonomy/src/demo.py  # live demo, needs a key
```
