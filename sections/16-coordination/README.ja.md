# 16 · Coordination

[English](README.md) · [繁體中文](README.zh-TW.md) · [简体中文](README.zh-CN.md) · **日本語** · [한국어](README.ko.md)

> リードはタスクに応じた規模のチームを形成し、独自のスレッドでチームメイトを生成し、共有受信トレイで会話します。

1 つのエージェントには 1 つの context window と 1 つのアクティブな作業ラインがあります。大規模なジョブでは、複数のエージェントが同時に作業する必要があることがよくあります。

subagent は集中したタスクを処理できますが、単発の subagent は開始後の操縦が困難です。

エージェントを追加するたびにトークンがかかり、2 人のエージェントが同じファイルを異なる方向に編集できます。
したがって、最初に決定するのはチームの形状です。エージェントは何人いるか、エージェントが 1 つのコンテキストを共有しているかどうか、誰が誰に何をすべきかを指示するかどうかです。

調整されたエージェントには、互いに生成する方法、安定した名前、会話するための受信箱、および人間に許可リクエストを送信する方法が必要です。

調整は次のことを行う必要があります。

1. エージェントに安定したアドレスを与えます。
2. リードの規模を調整し、タスクのチームを編成します。
3. リードが各チームメイトを独自のスレッドにスポーンさせます。
4. 各チームメイトが受信トレイを取得し、スクリプトを使用せずに行動できるようにします。
5. 人間の承認者に対するバブル ゲート アクション。

このレイヤーがないと、大規模な作業が連続したままになるか、共同作業できないワーカーに分割されてしまいます。

## メカニズム

![機構図](assets/16-coordination.png)

各エージェントは受信トレイを所有します。メッセージを送信するということは、受信者の受信箱に書き込むことを意味します。受信者が受信箱を空にするときに配信が行われます。

チームのサイズと名前は、スクリプトにハードコーディングされるのではなく、実行時にリーダーのモデルによって決定されます。
リーダーは `TeamCreate` を呼び出してタスクのチームを形成し、各メンバーを生成します。

リードはチームメイトを手でスタートさせません。これは `SpawnTeammate` を呼び出し、harness はバックグラウンド スレッドでチームメイトのループを実行します (セクション 13)。
その後、チームメイトが独自の受信箱を取得して行動するため、スクリプトは誰も動かなくなります。

デモには中央ブローカーはありません。名前、受信ボックスのパス、メッセージの形式には共通の規則があります。

- 各エージェントは 1 つの受信箱を所有します。
- メッセージには送信者、受信者、および内容があります。
- リードは `TeamCreate` を呼び出して、名簿のサイズを設定して形成します。次に、`SpawnTeammate` は各メンバーを開始します。
- リードは `SpawnTeammate` のチームメイトを生成します。そのチームメイトは独自のスレッドで実行されます。
- `to="*"` は、送信者を除くすべてのチームメイトにブロードキャストします。
- 送信者は書いて返信します。応答の待機をブロックしません。
- チームメイトは投票ごとに受信箱を取得し、新しいメッセージを次のターンに組み込みます。
- 許可リクエストは同じチャネルを使用します。

### 新機能: チームの結成

`TeamCreate` は、リードが名簿をサイズ設定して形成するために呼び出すツールです。これにより、harness が各メンバーを生成するときに読み戻す 1 スロット ホルダーが埋められます。

```python
def team_tools(root, me, formed):                      # src/mailbox.py
    def create(a):
        members = list(dict.fromkeys([me, *a["members"]]))   # the lead joins its own team
        formed["team"] = Team(root, members)                 # the tool call sizes and forms the team
        return f"team created: {', '.join(members)}"
    ...                                                # SendMessage stays inert until the team exists
```

- スクリプトはサイズも名前も修正しません。リードはタスクから両方を選択します。
- `SendMessage` は、`TeamCreate` が実行されるまで不活性であるため、リードは通信する前にチームを形成します。
- `formed` は 1 スロット ホルダーです (ポニーテール: チーム レジストリのインプロセスの代役。別のプロセスのチームメイトが参加できるように名簿ファイルでバックアップします)。

### 新機能: チームメイトの生成

`SpawnTeammate` は、リードのモデルが呼び出すツールです。 harness は、独自のスレッドでセクション 13 runtime でチームメイトのループを開始します。

```python
def teammate_tools(runtime, spawn_worker):             # src/mailbox.py
    def spawn(a):
        runtime.start(lambda: spawn_worker(a["name"]))  # section-13 thread runs the teammate's loop
        return f"spawned teammate {a['name']}; it runs on its own thread and pulls its own work"
    return [Tool("SpawnTeammate", spawn, is_read_only=True, ...)]
```

チームメイトのループは `serve_mailbox` です。受信トレイをプルし、行動し、繰り返します。これは生成されたスレッド上で実行されるため、チームメイトはスクリプトではなく独自に反応します。

```python
def serve_mailbox(team, me, work, *, poll=0.05, max_idle_polls=None):   # src/mailbox.py
    while True:
        chat = [m for m in team.drain(me) if isinstance(m["content"], str)]
        if chat:                                        # a message to act on
            folded = "\n".join(f"<message from={m['from']!r}>{m['content']}</message>" for m in chat)
            work(folded)                                # one inner loop (section 1) on the message
            continue
        time.sleep(poll)                                # empty: poll again
```

- `spawn_worker(name)` はアプリのサンクです。そのチームメイトに対して `serve_mailbox` ループを 1 つ実行します。
- チームメイトはメッセージを消費するので、メッセージは 1 回配信されます。
- 優雅な停止はまだありません。スレッドはプロセスとともに終了するデーモンです。セクション 17 ではシャットダウン ハンドシェイクが追加されています。
- `max_idle_polls` はアイドル待機を制限するため、デモまたはテストが終了します。実際のチームメイトはプロセスが停止するまでポーリングします。

### 受信トレイと許可チャネル

別々のコンテキストを持つエージェントには 2 つの会話方法があり、プロセスと同じ 2 つの方法があります。
共有メモリでは、全員が 1 つの場所を読み書きし、同じ状態が表示されます。
メッセージ パッシングでは、送信者はコピーを 1 人の受信者にアドレス指定し、2 人は何も共有しません。
3 つのチャンネルがこれら 2 つを伝送します。ツール呼び出しの引数は一方通行であり、応答パスはありません。ファイルは再起動後も存続しますが、ロックが必要です。
メッセージ バスはアドレスと順序を追加し、ディスクに書き込む場合にのみ再起動後も存続します。
ここでの受信トレイはロックされたファイルであるため、共有ファイル システムを介してメッセージが受け渡されます。
チーム メモリ (セクション 9) とタスク ボード (セクション 18) は共有メモリ側です。
ほとんどのチームは、作業を配布するためのメッセージと、メッセージよりも存続するファクトの共有メモリの両方を必要とします。

`mailbox.py` は、名前付き受信トレイの `Team` を実装します。

```python
def send(self, frm, to, content):                      # src/mailbox.py
    targets = [m for m in self.members if m != frm] if to == "*" else [self._check(to)]
    with self._lock():                                 # serialize concurrent senders
        for t in targets:
            inbox = self._read(t)
            inbox.append({"from": frm, "to": t, "content": content})
            self._path(t).write_text(json.dumps(inbox))
```

- `_check` は、パスになる前に不明な名前を拒否します。
- ロックは読み取り、変更、書き込みをシリアル化するため、同時送信者がメッセージをドロップしません。
- `drain` は 1 つの受信トレイを読み取り、クリアします。

権限バブリングは承認者の実装です。同じチャネルを介してゲートされた通話を人間に転送します。

```python
def bubbling_approver(team, me, lead, human=None, timeout=0.0, poll=0.05):
    def approve(name, args):                            # approver for an agent with no human UI
        team.send(me, lead, {"kind": "permission_request", "tool": name, "args": args})
        if human is not None:                           # the lead routes it to its approval UI
            team.send(lead, me, {"kind": "permission_response", "tool": name, "ok": human(name, args)})
        deadline = time.time() + timeout
        while True:
            resp = [m["content"] for m in team.drain(me)
                    if isinstance(m["content"], dict) and m["content"].get("kind") == "permission_response"]
            if resp:
                return bool(resp[-1]["ok"])
            if time.time() >= deadline:
                return False                            # nobody answered in time: default deny
            time.sleep(poll)
    return approve
```

1. チームメイトがゲート ツールの呼び出しを打ったが、そのループにはキーボードを操作する人がいません。
2. 承認者は、`permission_request` をリードの受信箱に送信します。
3. リードはそれを承認 UI (ここでは `human` コールバック) にルーティングします。
4. 判定はチームメイトの受信箱に `permission_response` として返されます。
5. チームメイトはその応答を読み、許可または拒否をゲートに返します。

ゲートは依然として `approver(name, args)` を呼び出し、変更されません。回答は直接呼び出しではなく受信箱メッセージとして届くため、エスカレーションでは同じチャネルが再利用されます。

`human` がなければ、答えは他の場所 (別のスレッドのリード、チャット プラットフォーム上の人) から得られる必要があります。
承認者は受信トレイを `timeout` までポーリングしてから拒否します。応答のない許可は「いいえ」であり、ストールや「はい」になることはありません。
これは、Hermes の Clear Gateway を反映しており、チャット アダプタが応答するかタイムアウトが発生するまで、`wait_for_response` がエージェント スレッドをブロックします。

### 統合方法

デモでは 1 つのメイン エージェントが実行されます。リードが一歩踏み出すと、チームメイトも自ら走り出します。

```python
def spawn_worker(name, formed, model):                 # src/demo.py, module level
    team = formed["team"]                              # whatever the lead formed with TeamCreate
    ...                                                 # build the teammate's tools
    return mailbox.serve_mailbox(team, name, work)      # the teammate pulls its own inbox

run_turn([...goal...], model, lead_reg, session)        # the one agent call in demo(): the lead
```

- 唯一のスクリプト化された入力はリードの目標です。リードは `TeamCreate` でチームのサイズを決定し、`SpawnTeammate` で各チームを生成し、`SendMessage` で委任します。
- `demo()` は、先頭の `run_turn` を 1 つ実行します。チームメイト自身の `run_turn` は `spawn_worker` にあり、スポーン ツールを介してのみアクセスできます。
- 各チームメイトはセクション 13 スレッドで `serve_mailbox` を実行します。受信トレイを取得し、動作し、返信します。返信の数はリードの選択です。メインプロセスは待機するだけです。
- `loop.py` は汎用のままです。フォールディングとプル ループは調整であり、`run_turn` 内ではなく、このラッパー内で行われます。
- 許可ゲートは変更されません。ゲートコールは依然としてリードに泡立ちます。

### さらに読む

これは `src/` にはありません。これは、ai-agent-book および出版されたマルチエージェント研究に基づいており、表内のシステムについては確認されていません。

**チームが 1 人のエージェントに勝ったとき。** 2 人目のエージェントを追加するのは、最初のエージェントが見えなかったものを取り戻した場合のみです。
テスト結果、スクリーンショット、取得したページ、実行中のシステムからの応答。それは新しい情報です。
エージェントが同じテキストをもう一度読んで投票しても、新しい情報は得られません。トークンのみを消費します。

公表された 2 つの結果は、これを誤解する代償を設定しています。トランとキーラは 1 人のエージェントとチームに同じ思考トークンの予算を与えました。
彼らが測定したタスクでは、1 人のエージェントが追いつきました。 Anthropic は、研究チームが 1 回のチャット ターンで約 15 倍のトークンを使用していると報告しています。
それだけの費用がかかったチームは何かを取り戻さなければなりません。

**共有または分離されたコンテキスト。** 2 つのエージェントが 1 つの履歴を共有するか、別々の履歴を保持します。

- **共有。** 次のエージェントはすべてを継承するため、何も詰め込む必要はなく、ファクトが失われることもありません。
  コストは、一度に 1 つのエージェントが実行され、1 つのウィンドウにチーム全体の履歴が保持されることです。
- **孤立。** 各エージェントには独自のウィンドウがあり、必要なことを言う必要があります。エージェントは同時に実行され、一方のエージェントの混乱はそのウィンドウで止まります。
  その代償として、すべての引き継ぎを書き留める必要があります。

サブタスクがほとんどなく、履歴が 1 つのウィンドウに収まり、ステップが順番に実行される場合は、共有を選択します。それ以外の場合は隔離してください。
このリポジトリは分離します。subagent は空で開始され (セクション 6)、チームメイトは受信トレイのみを読み取ります。

** 3 つのトポロジ。** 孤立したエージェントは、誰が誰と話しているのかを知る必要があります。形状は 3 つあります。

- **ピア。** 同等の立場のエージェントが互いにメッセージを送ります。ここで適合性を確認してクロスチェックしてください。
- **マネージャー。** 1 人のリーダーが作業を分割して配り、戻ってきたものを結合します。子供は履歴ではなく概要を返します。
- **分散型。** リードなし。各エージェントは次に誰に仕事を依頼するかを選択します。

このセクションではマネージャーを構築します。リーダーは全員の計画を立てるため、悪い分割は悪いままとなり、作業者はそれを修正できません。
これが、リーダーに最も強力なモデルを与え、労働者にはより安価なモデルを与えるという議論です。

**分散型チームが仕事をルーティングする方法** リードがない場合でも、仕事は次のエージェントを見つける必要があります。 3 つの公開デザイン、3 つのルート:

- **MetaGPT** はすべてのメッセージをプールに投稿します。各ロールは、それが処理するメッセージ タイプをサブスクライブするため、送信者が受信者に名前を付けることはありません。
- **AutoGen** グループ チャットは 1 つのトランスクリプトを保持し、中央セレクターが次に話す人を選択します。セレクターが同じ 2 人のエージェントを選択し続けると、チャットがライブロックされます。
- **OpenAI Swarm** は、各ハンドオフをツール呼び出しにし、作業のハンドオフの回数を制限するため、一連のハンドオフが終了します。

**ファイル ツリーの 4 つの領域。** エージェントは名前でお互いを検索します。彼らはパスによって状態を見つけます。この本ではツリーを 4 つの領域に分割しています。

- **プライベート スクラッチパッド。** 1 人のエージェントの下書き。他の人は読まないので、何も調整する必要はありません。
- **共有ワークスペース。** リポジトリ、タスク ボード、およびチーム メモリ。チームメイト全員がここに書き込みをするため、ここで衝突が発生します。
  ロック、またはエージェントごとに worktree が必要です (セクション 15)。
- **外部マウント。** チェックアウトやデータセットなど、チームが作成したものではないデータ。ここに書くことでチームの外で何かが変わります。
- **読み取り専用の組み込み。** Skills、プロンプト、およびツール定義 (セクション 7 および 2)。これらは実行中に変更されないため、すべてのエージェントに同じコピーが表示されます。

状態を間違った領域に置くと、調整バグとして戻ってきます。 2 人のエージェントが 1 つのファイルを編集しているということは、そのファイルが共有ワークスペースに存在していることを意味します。
事実が 3 回送信されたということは、それがチームの記憶に残るはずだったことを意味します。

**ハンドオフの内容** チームメイトはリードのチャットを見ることができないため、「失敗したテストを修正する」だけでは何も行動できません。ハンドオフ パケットには次の 3 つの内容が含まれます。

1. 受信者が独自にチェックできる受け入れ基準を備えたタスク。
2. すでに確認されている事実とその制約が存在するため、受信者はそれらを再度調べたり、破ったりすることはありません。
3. ファイル、ログ、ブランチへのパス。

送信者の生の履歴は外部に残ります。長くて行き止まりが多く、受け手には送り手の間違いを読ませてしまう。

共有コンテキスト ハンドオフはもう 1 つのオプションであり、パケットをスキップします。あるエージェントが別のエージェントに制御を渡し、履歴全体が追跡されるため、何も残されません。
この本では、役割間で制御を移動するツールを使用してこれを示しています。これは著者自身の実験ですので、一つの情報源として扱ってください。
その代償として、1 つのエージェントのみが制御を保持するため、同時に何も実行されなくなります。パケットは書き込む作業を必要とし、並行して実行される作業を購入します。

> **次へ:** ここでのチームメイトは正常な停止を持たないデーモンであり、メッセージにのみ反応します。
> セクション 17 では、リードがチームメイトをきれいに終わらせることができるように、シャットダウン ハンドシェイクが追加されています。
> セクション 18 では、共有タスク ボードを追加します。これにより、アイドル状態のチームメイトは、メッセージの受信を待つのではなく、自分の作業を要求できます。

## 障害モード

- **メッセージ消失の競合。** 2 人の送信者が 1 つの受信箱に同時に書き込みます。読み取り、変更、書き込みをロックします。
- **ピア デッドロック。** エージェントは相互に待機します。送信をブロックするのではなく、メッセージをキューに入れてターン間に排出します。
- **権限が停止します。** チームメイトには人間の UI がありません。リクエストをリードにバブルします。
- **作成前に生成します。** リードは `TeamCreate` より前に生成またはメッセージを生成するため、名簿はありません。チームが存在するまで、両方を不活性にしておいてください。
- **孤立したチームメイト。** スポーンされたチームメイトは、作業が完了した後もポーリングを続けます。アイドル待機を制限するか、セクション 17 ハンドシェイクで停止します。
- **エージェント間のあいまいなメッセージ。** チームメイトはリードのチャットを見ることができません。パケットを送信します: タスク、受け入れ基準、確認された事実、成果物パス。
- **チャットは記憶として使用されます。** 永続的に共有された事実はチームの記憶に残ります。
- **ビザンチンのチームメイト** 失敗したエージェントはクラッシュしません。間違った答えが返されますが、それは間違いないようです。
  再試行するか、同じ証拠に投票すると、同じ答えが返されます。モデルの外部のものに対するチェックのみがそれをキャッチします。
- **共有ファイルの更新が失われました。** 2 人のエージェントが 1 つのファイルを読み取り、両方ともそれを書き戻します。最初の書き込みが消えてしまいました。
  書き込みをロックするか、バージョン番号を保存して、一致しない場合は再試行します。
- **セマンティック競合** 両方の書き込みが正常に適用されますが、結果はまだ壊れています。 1 人のエージェントが関数の名前を変更し、もう 1 人のエージェントが古い名前への呼び出しを追加しました。
  2 人のエージェントが同じものを所有しないように作業を分割するか、1 つの時点でマージします。
- **エラー カスケード** 1 人のエージェントが事実を誤解します。次のエージェントがそれを繰り返し、その次のエージェントが再びそれを繰り返し、その時点でそれは確認されたものとして読み取られます。
  結論だけを見る査読者は、結論が一貫していると判断します。生の証拠を作成したエージェントではなく、誰かに生の証拠をチェックしてもらいます。
