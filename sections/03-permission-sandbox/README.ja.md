# 3 · Permission & sandbox

[English](README.md) · [繁體中文](README.zh-TW.md) · [简体中文](README.zh-CN.md) · **日本語** · [한국어](README.ko.md)

> システムに届く前に各アクションを確認してください。

モデルは有効なツールの実行を要求することができます。許可レイヤーがその呼び出しが実行可能かどうかを決定します。

許可のない tool runtime はほぼ無人のリモートシェルに近いです。

悪いツールの呼び出しはファイルを削除したり、秘密情報を漏らしたり、間違ったコードをプッシュしたりする可能性があります。モデルを信頼することは安全の境界ではありません。コードは実行前に要求を確認する必要があります。

理由は簡単です。モデルは他の人が書いたテキストを読みます。ウェブページ、問題コメント、リポジトリ内のファイルは、
エージェントを対象とした指示を含む可能性があります。これらの指示が何をできるかを決定するのは三つの能力です。エージェントはプライベートデータを読むことができます。
エージェントは信頼されていないコンテンツを受け取ります。エージェントはデータを外部に送信できます。この三つのうち二つであれば耐えられます。三つすべて同時に存在すると
、注入されたテキストがエージェントに秘密を開いてどこかに投稿させることができます。その組み合わせは致命的な三位一体と呼ばれます。

永続的なメモリは事態を悪化させます。注入された命令がメモリファイル（第9節）に記録されると、次のセッションでそれが再び読み込まれます。
一度の注入が、そのセッションが終了した後も長く機能し続けます。

ゲートはこの三つの能力を取り除くことはできません。何も読まず何にも到達しないエージェントは機能できません。したがってゲートは
他の二つのことを行います。三位一体を完成させる呼び出しの前に決定を置きます。許可された呼び出しの後ろにsandboxを置きます。

許可レイヤーは次のことを行う必要があります:

1. 各ツールの呼び出しは、実行前に必ず検査する。
2. `allow`、`ask`、または`deny`のいずれかを決定する。
3. 危険な呼び出しが事前承認されていない場合は、人間に確認する。
4. 呼び出しが実行された場合の損害を制限する。

この層がないと、1回のツール呼び出しで不可逆的な副作用が発生する可能性がある。

## メカニズム

![メカニズム図](assets/03-permission-and-sandbox.png)

純関数が権限決定を行う。ツール、現在のモード、および任意の許可ルールを読み取り、次の3つの値のいずれかを返す:

- `allow`: ツールを実行する。
- `ask`: 一時停止して人間に確認する。
- `deny`: ツールを実行しない。

モードはデフォルトの動作を変更します。例えば、プランモードでは読み取り専用ツールを許可しますが、プランが承認されるまで編集は拒否されます。

### 新機能: ゲート

`decide()` が全ての権限決定です:

```python
def decide(tool, mode, allow_rules) -> str:      # src/permissions.py (new)
    if mode == BYPASS:                            # operator opted out
        return "allow"
    if mode == PLAN:                              # exploring, not acting yet
        if tool.is_read_only:           return "allow"
        if tool.name == "ExitPlanMode": return "ask"     # approval handshake (section 5)
        return "deny"                             # no side effects until approved
    if tool.is_read_only or tool.name in allow_rules:
        return "allow"
    if mode == ACCEPT_EDITS and tool.is_edit:
        return "allow"                            # a class of work pre-approved
    return "ask"                                  # default: when unsure, ask
```

この関数には入出力がありません。それにより、モードごとのテストが容易になります。

### 統合方法

ゲートは `_dispatch` の内部で、`run_tool` の直前に動作します:

```python
def _dispatch(block, registry, mode, allow_rules, approver):   # src/loop.py
    ...                                                  # resolve tool (section 2)
    decision = decide(tool, mode, allow_rules)           # 3 · the gate, the new line
    if decision == "deny":
        return res(f"{name} not allowed in {mode} mode")
    if decision == "ask" and not approver(name, block.input):
        return res(f"{name} denied by user")
    return res(run_tool(tool, block.input))              # only now does it run
```

- ループ本体はセクション1および2から変更されていません。
- `_dispatch` のみにゲートが適用されます。
- `deny` と未承認の `ask` は `run_tool` に到達しません。
- 拒否は引き続き `tool_result` として返されるため、モデルは何が起こったかを確認して適応できます。
- `approver` は `False` をデフォルトにするので、`ask` は、人間が承認しない限り「いいえ」を意味します。

重要な不変条件は維持されます：実際のアクションが実行されなかった場合でも、すべてのツール呼び出しは結果メッセージを生成します。

実際のシステムでは、ルールの優先順位、記憶された承認、サンドボックス化された実行が追加されます。それらは同じゲートの拡張です。

### さらに詳しく読む

これらは `src/` には含まれていません。ai-agent-book に由来するもので、表にあるシステムで確認されたものではありません。

**コマンドがどう動作するかを確認すること、スペルではない。** エージェントはシェルコマンドを実行するよう要求します。`decide()` では一つのツール名が見えます、
したがって、実際の判断はコマンド文字列に関するものです。文字列の拒否リストが一般的な答えですが、失敗します。`rm -rf /` は簡単に捕まえられます。
これらは通過します：

- `find . -exec rm {} \;` は削除をフラグの中に入れます。
- `$(echo rm) -rf /` は、シェルが実行されている間に言葉 `rm` を構築します。
- `curl -o /etc/crontab` は、書き込みコマンドを指定せずにファイルを書き込みます。

修正は、テキストではなく構造を読み取るパーサーです。それはコマンドをプログラムと引数に分割します。どのフラグが取るかを知っています
値なので、それが引数かフラグかを区別できます。それから、各プログラムが何をするかを尋ねます。`-exec` は独自のコマンドを持っているので、そのコマンド
もチェックされます。`-o` は書き込むファイルの名前を指定するので、そのパスも書き込みとしてチェックされます。

コストは、パーサーがプログラムごとにルールを必要とすることです。知らないプログラムは読み取ることができないため、sandbox はまだその背後にあります。

**それでも通過する破壊的なショートカットをブロックする。** 壊れたテーブルを修正する方法は2つあり、どちらも最終的には動作するテーブルにたどり着きます。
1つは移行する方法。もう1つは削除して最初から再構築する方法です。結果のチェック（第21節）はどちらにも合格します。なぜならそれは最終状態のみを見ているからです。

修正方法は目的地だけでなくルート自体を制御することです。削除して再構築する方法では、再構築されたテーブルが正しくてもブロックされたままになります。
コストは、本当に正しい修正である再構築でも、今は人間の承認が必要になることです。

**sandboxの制限内容。** ゲートが間違っている可能性があります。sandboxは、間違った`allow`が多くのコストを引き起こさないようにするものです。三つの制限がほとんどの作業を行います。

- **出口。** デフォルトでネットワークをブロックします。許可されたトラフィックは、許可されたホストのリストを持つプロキシを通して送信します。
  これは三つ組の中で最も安価に削れる部分です。エージェントは依然としてコードを読み、ファイルを書きます。ただし、それをどこにも送信できません。
- **マウント。** ソースを読み取り専用でマウントします。認証情報ファイルはまったくマウントしないでください。書き込み可能な作業ディレクトリは一つだけ与え、他は与えません。
  エージェントは開けないファイルを漏らすことはできません。
- **クォータ。** CPU、メモリ、ディスク、経過時間に制限を設定します。制限に達した場合、tool resultとしてエラーを返します。
  プロセスを静かに終了させないでください。モデルはタイムアウトを読み取り、より短いコマンドを試すことができます。静かな終了では何も読むことができません。

**ユーザーに二度待たせずに尋ねるために。** ゲートは`ask`を返し、ユーザーは現在待っている状態です。もしチェック自体が遅い場合、
プロンプトが表示される前にすでに一度待っています。投機的なチェックはその最初の待ち時間を取り除きます。順序は次の通りです：

- harness がバックグラウンドで権限チェックを開始します。
- 画面はすぐに進行状況の行を表示します。その行はシステム上の何も変更しません。
- チェックが`allow`を返した場合、行が表示されている間にツールが実行され、プロンプトは表示されません。
- チェックがまだ未決定の場合、その行は確認プロンプトに変わります。

なぜこれがまだ安全なのか：早く実行されるのはチェックだけです。ツール自体はまだ回答を待っています。

## システムごとに

各エージェントが副作用をどのように制御し、モードを変更し、決定を記憶するか。

| | Claude Code | mini-swe-agent | deepseek-harness |
| --- | --- | --- | --- |
| **長所** | モード、順序付けられたルール、およびサンドボックスにより細かい制御が可能。 | 数分で監査可能。拒否はモデルにフィードバックされる。 | 拒否は決して緩めない；サンドボックスは閉鎖的に失敗する。 |
| **短所** | 多くの状態がある。バイパスおよび事前承認のパスは狭く保つ必要がある。 | 全てのコマンドを同じように扱い、何も記憶しない。 | ポリシーはガード、承認、sandbox、プリセットにまたがる。 |
| **なぜ** | 毎回尋ねると疲労が生じるため、承認は持続します。 | プロンプトと正規表現; 環境が被害を制限します。 | 各懸念は独自のフェイルクローズドサービスです。 |
| **方法: ゲートポイント** | 各ツールの前; web, MCP, リモートゲートは別々に。 | ステップが実行される前。 Enterで承認、コメントで拒否。 | 実行前イベント、次に拒否専用ガード。 |
| **方法: 権限モード** | デフォルト、編集承認済み、プラン、拒否、バイパス。 | `human`, `confirm`, `yolo`, runtimeで切り替え。 | Sandboxモードに加え、askまたはneverをバンドルしたプリセット。 |
| **方法: sandbox** | Bash は sandbox 内で実行できます。 | 環境クラスは sandbox です: ホスト、コンテナ、ラッパー。 | プロバイダーは各 argv をラップします; 拒否は分類されて戻ってきます。 |
| **方法: ルールの永続性** | ルールは優先度によってセッションまたは設定にマージされます。 | 設定の正規表現; 一致した場合はプロンプトをスキップします。 | ノブの変更はログイベントです; リプレイはポリシーを折りたたみます。 |

## 失敗モード

- **パターンマッチのバイパス。** 文字列の拒否リストはシェルのバリエーションを見逃します。コマンドを解析し、実際に何をするかを確認してください。パーサーの背後に sandbox を配置してください。
- **モードを開きすぎ。** 広範な許可ルールやバイパスモードは、後で危険な呼び出しを静かに実行させる可能性があります。バイパスの範囲を設定し、アクティブなモードを表示してください。
- **承認疲れ。** 毎回の通話で承認を求めると、ユーザーは内容を読まずに承認するようになります。リスクの低いクラスは事前承認しますが、破壊的な操作は明示的に求めてください。
- **subagentでの沈黙の拒否。** 子エージェントは尋ねるための端末を持たない場合があります。静かに失敗するのではなく、プロンプトを親にバブルさせてください。
- **Sandboxが無効。** 許可されたコマンドがsandbox外で実行される場合、権限プロンプトが最後のチェックです。サンドボックス外の経路はポリシーの背後にゲートを設けてください。
- **承認された通話による情報流出。** 各通話は個別にゲートを通過できますが、セッション全体では秘密を読み取り送信してしまいます。
  デフォルトでネットワークをブロックし、第三の機能が使用できないようにしてください。
- **検証済みだが破壊的。** 削除して再構築すると結果チェックを通過します。なぜなら最終状態が正しいからです。最終状態だけでなく、アクションも確認してください。
- **汚染されたメモリ。** メモリファイルに注入された命令は、以後のすべてのセッションで読み戻されます。保存されたメモリは信頼できる内容としてではなく、常にオペレータルールとして扱わないでください。
