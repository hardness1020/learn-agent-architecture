# 21 · Loop engineering

[English](README.md) · [繁體中文](README.zh-TW.md) · [简体中文](README.zh-CN.md) · **日本語** · [한국어](README.ko.md)

> 次のプロンプトを書くのをやめてください。あなたなしでエージェントを実行するループを設計してください。

前の各セクションは、1回のモデル呼び出しの周りに1つのメカニズムを追加しています。このセクションでは、それらを組み合わせます。

Loop engineering は、エンジニアリングの努力の方向性の変化を示しています。
エージェントをターンごとにプロンプトする代わりに、作業を発見し、エージェントを実行し、出力をチェックし、次に何をするかを決定する外側のシステムを構築します。
人間はオペレーターからデザイナーに移行します。

外側のループは次のことを行わなければなりません:

1. トリガーから実行を開始する。ユーザーからだけでなく（セクション14）。
2. 完了としてカウントする前に出力を確認する。
3. 希望ではなく、予算で停止する。
4. 次の実行で再起動せずに続行できるように状態を保持する（セクション9、12）。
5. 誰も見ていなくても、何が起こったかを報告する（セクション20）。

このレイヤーがなければ、人間が外側のループになる。彼らは手作業でプロンプトを出し、読み、判断し、再試行し、そして人間が作業を止めるとエージェントも機能を停止する。

## メカニズム

![メカニズム図](assets/21-loop-engineering.png)

単純なバージョン: agent loop を、さらに三つのループでラップしている。それぞれが内側のループを包み込み、異なる質問に答える。

1. **Agent loop**（セクション1）。タスクが完了したように見えるまでツールを呼び出す。答え: 一つのステップはどのように完了するか。
2. **検証ループ。** 出力をルーブリックに対して評価する。失敗した場合は再試行にフィードバックし、予算内で繰り返す。答え: 実際に完了したかどうか。
3. **イベントループ。** Cron はスケジュール、ウェブフック、チャネル開始の実行（セクション14、セクション19）を行います。回答：作業はいつ開始されますか。
4. **改善ループ。** トレースおよび evals（セクション20）は harness の設定、skills、またはモデルに変更をフィードします。回答：システムは改善されますか。
   このループが成熟すると、harness 自体を編集します：トレースから弱点を抽出し、限定的な編集を提案し、それを回帰セットで検証します。
   ループ構造は手作りのテンプレートではなく、探索空間になります。

データは外向きに移動します。トリガーが発生してプロンプトをキューに入れます。agent loop が候補を生成します。グレーダーがそれを評価します。
失敗するとフィードバックを追加し、予算が残っている限り再試行します。合格するとタスクのチャネルを通じて結果が届けられます。
実行のトレースはテレメトリに記録され、改善ループがそれを読み取ります。

### 新: 検証ループ

以前のセクションのループは構築されませんでした。インナーループはモデルが完了と判断したときに停止します。検証ループは「完了」を確認済みの主張にします:

```python
def verified_run(task, worker, checker, budget=2):    # src/verify.py
    feedback = ""
    attempts = []
    for n in range(1, budget + 1):                    # the ceiling: harness-enforced
        out = worker(task + feedback)                 # the inner loop (section 1)
        verdict = checker(task, out)                  # a separate checker (section 6)
        attempts.append({"attempt": n, "passed": verdict["passed"], "reason": verdict["reason"]})
        if verdict["passed"]:
            return {"ok": True, "output": out, "attempts": attempts}
        feedback = f"\n\nA prior attempt was rejected... Why it failed: {verdict['reason']}"
    return {"ok": False, "output": None, "attempts": attempts}   # budget spent: escalate
```

- グレーダーは新しいコンテキストを持つ別のエージェントです（セクション6）。自身の出力を評価するワーカーは、それを合格させがちです。
  `agent_checker` は1つ構築します: 各評価は新しい `messages[]` 上でインナーループを実行し、判定の最初の単語として PASS または FAIL を使用します。
- ルーブリックはループの外で固定されています。モデルはそれを満たすことはできますが、書き換えることはできません。
- フィードバックはデータです。失敗した判定はプロンプトの一部として再試行に持ち込まれるため、試行2は試行1がどこで間違えたかを知ることができます。
- `ok: False` はエスカレーション信号です。試行の記録は人間に送られます；ループは永遠に再試行されません。

1回の合格または不合格は、信号として薄いです。判定を3つの質問に分け、それぞれが証拠を示すようにします：

- **結果。** 実行が正しい状態を残したか。証拠：状態自体、コードが確認できる箇所はすべて（セクション23）。
- **プロセス。** 実行がルールに従ったか：許可されたツール、必要な順序、確認を飛ばさない。証拠：トレース内のツール呼び出し。
- **品質。** コードチェックでは表現できない部分で答えは良好か。証拠：ルーブリック、失敗行を明示。

実行可能なものは3番目の質問のみを採点します。成果とプロセスのチェックには、何が起こったかを記録する環境が必要です。これはセクション23が構築するものです。
それらを分けることで修正すべき箇所が分かります。成果が合格でプロセスが失敗の場合、実行が運良く成功したことを意味します。プロセスが合格で成果が失敗の場合、ルールが間違っていることを意味します。

### 予算と停止条件

すべてのループには、モデルが言い訳して回避できない上限が必要です：反復回数、トークン予算、実時間制限、またはドライカウンター（新しいものを見つけられなかったK回のラウンド後に停止）です。

harnessがその上限を強制します。モデルに止まるようお願いするのはヒントであり、停止条件ではありません。
`verified_run`では、上限が`range()`の制約です：`budget + 1`の試みは発生しません。

### 熟練度レベル

ループエンジニアリングのソースは、どれだけ信頼されているかに基づいてループをグレードします：

- **L1 · レポート。** ループは読み取り、報告します。人間が行動します。
- **L2 · 支援。** ループは変更を下書きします。人間が承認します。
- **L3 · 無人。** ループが行動します。人間が事後に監査します。

レベルは許可の判断です（セクション3）。現在のレベルでの出力が退屈なほど正しいことを確認してからのみ、ループを1レベル昇格させます。

### 統合方法

このセクションは新しいプリミティブを追加しません。これは以前のものの組み合わせです：

- トリガーはセクション14のスケジュールとセクション19のチャネルです。
- ワーカーはセクション1のループで、セクション6 subagents がメーカーとチェッカーの分割として機能します。
- 並列ループはセクション15 worktreesで隔離されます。
- 実行間の状態はセクション9のメモリとセクション12のタスク記録に保持されます。
- レポートとトレースはセクション20にあります。改善ループはセクション20の測定をharnessの変更に戻して閉じます。

実行可能なものも同じ方法で接続されます。`run_turn`はセクション20とバイト単位で同一であり、検証は外部からそれをラップします：

```python
def worker(prompt):                                # src/demo.py · the inner loop, unchanged
    return run_turn([{"role": "user", "content": prompt}], model, reg, Session(mode=DEFAULT))

checker = agent_checker(RUBRIC, model)             # a fresh grader agent, no tools
result = verified_run("What is 27 + 15? Use the add tool.", worker, checker, budget=2)
```

新しいのは規律です：完了前に評価、開始前に予算、常にレポート。

### さらなる読書

これらは`src/`には含まれていません。これはai-agent-bookと公開された自己改善の研究から来ており、表にあるシステムでは確認されていません。

**学習した変更のルーティング。** たとえば、実行中にステージングデータベースに異なる接続文字列が必要であることがわかった場合、それはどこに置きますか？
改善のループの難しい部分は、教訓を見つけることではありません。難しいのは、教訓をどこに配置するかを選ぶことです。それを置く場所は4つあります:

- **ナレッジドキュメント。** 実行中に発見した1つの事実。書くのも削除するのも安価です。タスクがそれを必要とするときにエージェントが読み返します（セクション9）。
- **プロンプトまたはskill。** 繰り返すべき行動。読み込むたびにコンテキストを消費します（セクション7）。
- **プログラム。** 毎回同じ方法で実行される手順。推論時には何もコストがかからず、テストすることもできます（セクション2）。
- **重み。** 最終手段。遅く、コストが高く、元に戻すのが最も難しい。このリポジトリのharness論文外のものです。

ルールは、変更を保持できる最小の場所を選ぶということです。最小ということは、確認しやすく、元に戻しやすいということでもあります。
接続文字列は事実なので、ドキュメントに記載します。system promptには含めません。

第二の場所、つまりプロンプトやskillは最も乱用されやすいため、独自のゲートが必要です。
何度も起こった失敗から編集を書きます。一度の失敗からではありません。
適用される場合にのみ使うようにし、無関係の実行では静かにしておきます。それから二重に確認します：編集付近のケースと、編集を書いた元のケースではない保持用データセットで。
まずトラフィックの一部に適用し、ロールバックの準備をしておきます。
Karpathyはこれをsystem prompt学習と呼びます：重みの代わりに単語を編集します。
ACEは、プロンプト全体を書き直すのではなく、番号付きのコンテキスト項目を修正することで、各編集を小さく保ちます。

**ツールユーザーからツール作成者へ。** 第三の場所、プログラムは、前のセクションでは構築されないものです。
skillは、モデルがまだ読み取り従う必要のある指示を渡します（セクション7）。コンパイル済みワークフローは、harnessに、モデルなしで実行されるプログラムを渡します。
例えば、エージェントが同じ種類のチケットを10回予約したとします。5つのステップでそれをプログラムに変えます：

1. **キャプチャ。** うまく動作した1回の実行を記録します：どの呼び出しを行ったか、どの順序で行ったか、各呼び出しの前後の状態など。
2. **パラメータ化する。** 実行ごとに変わったものを引数に変え、変わらなかったものがプログラムになる。
3. **リセット時に検証する。** 新しい環境でそれを再実行する（セクション23）。各ステップは実行前にチェックされ、実行後にもチェックされ、最後に状態チェックが行われる。
4. **リプレイする。** 次の一致するタスクでプログラムをそのまま実行する。モデル呼び出しはなく、速く、安価で、毎回同じである。
5. **無効化する。** 1つのチェックが失敗するとプログラムは引退する。タスクはモデルに戻され、新しいものをキャプチャできる。

ツールを作るのも同じライフサイクルである。エージェントは自分でできないことに遭遇し、ライブラリを見つけ、
それをツールとしてラップし、レジストリが受け入れる前に検証する（セクション2）。
どちらの操作も、高価な探索を確認可能な安価な能力に変えます。
どちらもステップ5が必要です。なぜなら、構築されたサイトやAPIが変更されるからです。

**harnessの編集。** ループが単なるプロンプトではなくharnessコードを変更したい場合、それはパッチを取得する前に契約が必要です。
変更契約には4つの事項が記載されます：どのトレースが失敗したかとその頻度、根本原因、変更によって何を改善すべきか、そしてそれを元に戻す方法。
契約なしではパッチはありません。人間が契約を読み、それが自己編集ループと誰も監査できないものを区別する要因です。
ループが編集できるコードは事前に宣言されます。権限、予算、およびゲートはその領域の外にあり、ループはそれらに到達できません（セクション3）。

ループが検索する場所ははしごです。最下段の段はプロンプト内の1つのルールです。
その上：コンテキストがどのように組み立てられるか、次にワークフロー、次にharnessコード、そして変更を提案するコード。
下の段が失敗した場合にのみ、1段上に登ります。上に行くほど検索範囲は広がり、チェックは弱くなります。
プロンプトルールは1日でA/Bテストが可能です。変更を提案するコードを入れ替えると、その後のすべての変更は異なる方法で提案されます。

**オンライン実行、オフライン学習者。** この2つは分けておきます。オンラインループはタスクを実行し、何が起こったかを記録します。
教訓を引き出したり、skillsを推奨したり、プロンプトを編集したりはしません。
別のオフラインループは、一度に多くの実行を読み取り、繰り返される失敗を見つけ、候補の変更を書き込み、それを検証し、バージョンをリリースします。

分割は、1回の実行がエージェントを書き換えるのを防ぐものです。ひとつのラッキーな経路はパターンではありません。
エージェントに何を記憶するかを伝えるウェブページは、証拠ではありません。
いくつかの実行で同じ信号を必要とすることに加え、検証ゲートを設けることで、両方ともリリースから除外されます。

分割はまた、測定するものを変えます。数字を1つではなく2つ読み取ります。

- **更新。** ループは良い候補を生成していますか。いくつ提案したか、いくつ検証を通過したか、いくつロールバックされたか。
- **利益。** リリースされた変更は役立っていますか。変更は対象となる実行で負荷をかけているか、エージェントはそれに従っているか、保持されたパフォーマンスは変化しているか。

両方を読みます。最初のものだけの場合、正しいが決して読み込まれない skill は、失敗したアップデートのように見え、ループは自分自身について間違った結論を導きます。

## 失敗モード

- **終了条件なし。** 上限のない再試行ループは、誰かが請求書に気づくまでトークンを消費し続けます。軽減策: ハーネスによる反復の強制、トークンおよび時間の予算管理。
- **自己評価。** ワーカーが自分の出力を合格とするため、検証ループでは何も確認されません。軽減策: ループ外で固定されたルーブリックと、別のチェッカーエージェントの利用。
- **無条件合格のルーブリック。** 常に合格する採点者は、存在しないよりも悪く、悪い出力を検証済みとしてラベル付けしてしまいます。
  軽減策: 反論を促すアドバーサリアル検証と、定期的な人間によるスポットチェック。
- **早すぎる無人運用。** ループがL1レポートをチェックする前にL3書き込み権限を取得してしまう場合。
  軽減策: 権限セクション3で制御された段階的な成熟度向上。
- **静かな逸脱。** 放置されたループは劣化し、その出力は誰にも読まれません。対策：ハートビート、必ず届けられるレポート、および合格率とコストのセクション20の指標。
- **状態健忘。** 各実行で同じ作業を再発見し、やり直します。対策：結果をメモリやタスク記録（セクション9、12）に保存し、実行開始時にそれらを読み取る。
- **自己編集harnessがゲートを抜け出す。** harnessコードを変更できる改善ループは、それを制御するコードも変更できます。
  対策：権限と予算はループが編集できるものの外に設定する（セクション3）。
- **代理目標の逸脱。** 開かれた作業では、ルーブリックは実際の目標の代わりに立っています。ループは代わりにルーブリックを満たすことを学習します：
  それは慣れたコードを再利用し、ノイズを発見として読み取り、合格した実行だけを保持します。スコアは上がりますが、真の目標はすり抜けていきます。
  対策: 失敗した実行を証拠として保持し、ホールドアウトセットを更新し、出力を本当の目標と照らし合わせて人間が確認します。
- **すべての教訓がプロンプトの編集になる。** プロンプトは書くのが最も簡単な場所なので、すべてがそこに集まります。それは自分自身のルールと矛盾するまで成長します。
  対策: 教訓に基づいて場所を選ぶ。事実は文書に、手順はプログラムに、プロンプトは繰り返さなければならない行動のために使用します。
- **コンパイルされたワークフローはその環境よりも長生きする。** サイトやAPIは変わったが、プログラムはそれでも再生します。モデルよりも速く間違った状態を書き込みます。
  軽減策：リプレイの各ステップの前後にチェックを行い、最初の失敗したチェックでプログラムを退役させること。
- **オンライン実行は独自の学習を促進する。** 実行中に学習を取り入れるエージェントは、ちょうど運が良かった経路を促進したり、覚えさせるために仕込まれた信頼できないページをテキスト化する可能性がある。
  軽減策：オンラインループには証拠のみを記録させ、他のことは行わない。リリース前に候補を検証するために別のオフラインパスを設ける。

  `docs/subsystems/core.md`、`packages/workflow/tool-ralph/README.md`、`packages/schedule/schedule/README.md`、`docs/subsystems/goal.md`。
- [cobusgreyling/loop-engineering](https://github.com/cobusgreyling/loop-engineering): ビルディングブロックと準備レベル。
- [LangChain · loop engineering のアート](https://www.langchain.com/blog/the-art-of-loop-engineering): 四重に重なったループ。
- [Addy Osmani · Loop engineering](https://addyosmani.com/blog/loop-engineering/): 組み合わされたビルディングブロック。
- [MindStudio · loop engineering とは](https://www.mindstudio.ai/blog/what-is-loop-engineering-autonomous-ai-agent-workflows): 目標条件。
- [Lilian Weng · 自己改善のための Harness engineering](https://lilianweng.github.io/posts/2026-07-04-harness/): 改善ループの詳細; ループ外のゲート。
- [ai-agent-book · 第8章](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter8.md) (《深入理解 AI Agent》, 李博杰; 中国語の原文が正典):
  三つの検証レイヤー、学習された変更がどこに適用されるかの選択とそのルール、プロンプト学習ゲート、変更契約,
  メタ最適化の階層、オンラインとオフラインの分離、進化指標の分離、そして検証可能ループの境界。
- [PreAct](https://arxiv.org/abs/2606.17929)：軌跡を事前・事後・事前保存チェックを伴うパラメータ化ワークフローにコンパイルし、モデルなしで再生する。
  最初の著者は書籍の著者と同じ名前を持つため、報告された再生速度向上（おおよそ8.5倍から13倍）を単一ソースとして読むべきである。
- [Alita](https://arxiv.org/abs/2505.20286)：能力ギャップがツール作成を引き起こし、ツールがライブラリに入る前に検証される。
- Karpathy · "system prompt 学習" (X, 2025年5月11日)：重みではなく単語を編集する、第三の学習パラダイムとして命名。
- [ACE](https://arxiv.org/abs/2510.04618)：完全なプロンプト書き直しではなく、安定したIDを持つ漸進的コンテキスト項目。
- [Lin et al.](https://arxiv.org/abs/2605.30621): harnessを更新し、harnessの利益を別々に測定し、モデルの入れ替えを使ってそれらを区別します。
- [AHE](https://arxiv.org/abs/2604.25850)および[Self-Harness](https://arxiv.org/abs/2606.09498): harnessが自身を編集するための契約変更と制限された候補空間。
- [Claude Code](https://code.claude.com/docs): `/loop`、`ScheduleWakeup`、`Workflow`スキーマ。ツールスキーマと文書化された動作に基づき、ソースバックアップからではありません。
- [Hermes Agentソース](https://github.com/NousResearch/hermes-agent):
  `agent/iteration_budget.py`、`cron/scheduler.py`、`tools/skill_manager_tool.py`、`hermes_cli/curator.py`、`agent/trajectory.py`。
- [mini-swe-agentソース](https://github.com/swe-agent/mini-swe-agent): `AgentConfig`と`query()`は`agents/default.py`、`agents/interactive.py`、`run/benchmarks/swebench.py`にあります。
