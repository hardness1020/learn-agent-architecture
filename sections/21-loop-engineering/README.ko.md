# 21 · Loop engineering

[English](README.md) · [繁體中文](README.zh-TW.md) · [简体中文](README.zh-CN.md) · [日本語](README.ja.md) · **한국어**

> 다음 프롬프트 작성을 중지하세요. 사용자가 없이 에이전트를 실행하는 루프를 설계하세요.

이전의 모든 섹션은 한 모델 호출 주위에 하나의 메커니즘을 추가합니다. 이 섹션에서는 그것들을 조합합니다.

Loop engineering는 엔지니어링 작업의 초점이 어디로 이동하는지를 이름붙입니다.
에이전트에게 차례차례로 프롬프트를 주는 대신, 작업을 발견하고, 에이전트를 실행하며, 출력물을 확인하고, 다음에 어떤 일이 일어날지 결정하는 외부 시스템을 구축합니다.
인간은 운영자에서 디자이너로 이동합니다.

외부 루프는 다음을 해야 합니다:

1. 사용자뿐만 아니라 트리거로부터 실행을 시작합니다 (섹션 14).
2. 완료된 것으로 간주되기 전에 출력을 확인합니다.
3. 희망이 아니라 예산에 따라 중지합니다.
4. 다음 실행이 재시작되지 않고 계속되도록 상태를 지속합니다 (섹션 9, 12).
5. 아무도 보고 있지 않아도 무슨 일이 일어났는지 보고합니다 (섹션 20).

이 계층이 없으면, 인간이 외부 루프가 됩니다. 그들은 직접 프롬프트를 하고, 읽고, 판단하며, 다시 시도하고, 에이전트는 그들이 멈추는 순간 작동을 멈춥니다.

---

## 메커니즘

![메커니즘 다이어그램](assets/21-loop-engineering.png)

간단한 버전: agent loop, 세 개의 루프로 감싸여 있습니다. 각 루프는 내부의 루프를 감싸고 있으며, 각 루프는 다른 질문에 답합니다.

1. **Agent loop** (섹션 1). 작업이 완료된 것처럼 보일 때까지 도구를 호출합니다. 답: 한 단계가 어떻게 완료되는가.
2. **검증 루프.** 출력물을 루브릭에 따라 평가합니다. 실패하면 재시도로 되돌아가며, 예산 한도까지 반복됩니다. 답: 실제로 완료되었는가.
3. **이벤트 루프.** Cron 스케줄, 웹후크, 채널이 실행을 시작합니다(섹션 14, 섹션 19). 답변: 작업은 언제 시작되나요.
4. **개선 루프.** 추적과 evals(섹션 20)이 harness 설정, skills 또는 모델에 변화를 제공합니다. 답변: 시스템이 개선되나요.
   이 루프가 성숙한 끝에 도달하면 harness 자체를 편집합니다: 추적에서 약점을 찾고, 제한된 수정을 제안하며, 회귀 세트에 대해 검증합니다.
   루프 구조는 수동으로 디자인된 템플릿이 아니라 검색 공간이 됩니다.

데이터가 바깥으로 이동합니다. 트리거가 발동하고 프롬프트를 큐에 넣습니다. agent loop가 후보를 생성합니다. 채점자가 점수를 매깁니다.
실패는 피드백을 추가하고 예산이 남아 있는 동안 재시도합니다. 통과는 작업의 채널을 통해 전달됩니다.
실행의 추적은 텔레메트리에 저장되며, 개선 루프가 그것을 읽습니다.

### 신규: 검증 루프

이전 섹션에서 만든 단일 루프는 구축되지 않았습니다. 내부 루프는 모델이 완료되었다고 말할 때 중지됩니다. 검증 루프는 "완료"를 확인된 주장으로 만듭니다:

```python
def verified_run(task, worker, checker, budget=2):    # src/verify.py
    feedback = ""
    attempts = []
    for n in range(1, budget + 1):                    # the ceiling: harness-enforced
        out = worker(task + feedback)                 # the inner loop (section 1)
        verdict = checker(task, out)                  # a separate checker (section 6)
        attempts.append({"attempt": n, "passed": verdict["passed"], "reason": verdict["reason"]})
        if verdict["passed"]:
            return {"ok": True, "output": out, "attempts": attempts}
        feedback = f"\n\nA prior attempt was rejected... Why it failed: {verdict['reason']}"
    return {"ok": False, "output": None, "attempts": attempts}   # budget spent: escalate
```

- 채점자는 섹션 6에 있는 새 컨텍스트를 가진 별도의 에이전트입니다. 자신의 출력물을 채점하는 작업자는 그것을 통과시키는 경향이 있습니다.
  `agent_checker`은 하나를 구축합니다: 각 채점은 PASS 또는 FAIL을 평결의 첫 단어로 사용하여 새로운 `messages[]`에서 내부 루프를 실행합니다.
- 루브릭은 루프 외부에서 고정됩니다. 모델은 그것을 만족시킬 수 있으며, 다시 작성하지 않습니다.
- 피드백은 데이터이다. 실패한 평결은 재시도 시 프롬프트의 일부로 들어가므로, 두 번째 시도는 첫 번째 시도가 무엇을 잘못했는지 알 수 있다.
- `ok: False`는 에스컬레이션 신호이다. 시도 기록은 사람에게 전달되며, 루프가 무한히 재시도하지는 않는다.

한 번의 합격 또는 불합격은 미약한 신호이다. 평결을 세 가지 질문으로 나누고, 각각의 질문에 증거를 이름붙이도록 하라:

- **결과(Outcome).** 실행이 올바른 상태를 남겼는가? 증거: 코드를 통해 체크할 수 있는 곳 어디서든 검증된 상태 자체 (섹션 23).
- **절차(Process).** 실행이 규칙을 준수했는가: 허용된 도구, 필요한 순서, 확인 누락 없음. 증거: 추적(trace) 내 도구 호출.
- **품질(Quality).** 코드 검사가 표현할 수 없는 부분에서 답변이 좋은가? 증거: 실패한 라인이 명시된 루브릭.

실행 가능한 항목은 세 번째 질문만 채점합니다. 결과와 과정 확인은 무슨 일이 일어났는지 기록하는 환경이 필요하며, 이것이 23절에서 구축하는 내용입니다.
그것들을 분리하면 무엇을 수정해야 하는지 알 수 있습니다. 결과는 통과했지만 과정이 실패했다면 실행이 우연히 성공한 것입니다. 과정은 통과했지만 결과가 실패했다면 규칙이 잘못된 것입니다.

### 예산과 중지 조건

모든 반복문에는 모델이 말로 지나칠 수 없는 한계가 필요합니다: 반복 횟수, 토큰 예산, 실제 시간 제한, 또는 새로 찾은 것이 없는 K회 반복 후 중지하는 건식 카운터입니다.

harness가 그 상한을 강제합니다. 모델에게 중지해 달라고 요청하는 것은 단서일 뿐 중지 조건이 아닙니다.
`verified_run`에서 상한은 `range()` 경계입니다: `budget + 1` 시도는 일어날 수 없습니다.

### 성숙도 수준

루프-엔지니어링 소스는 루프가 수행할 수 있는 신뢰 수준에 따라 루프를 등급화합니다:

- **L1 · 보고.** 루프가 읽고 보고합니다. 사람이 행동합니다.
- **L2 · 보조.** 루프가 변경 초안을 작성합니다. 사람이 이를 승인합니다.
- **L3 · 무인.** 루프가 행동합니다. 사람이 사후에 감사를 수행합니다.

등급(Level)은 권한 결정(섹션 3)입니다. 현재 등급에서 출력이 지루할 정도로 정확할 때만 루프를 한 단계 승격시키십시오.

### 통합 방식

이 섹션은 새로운 원시 요소를 추가하지 않습니다. 이전 요소들의 조합입니다:

- 트리거는 섹션 14 일정과 섹션 19 채널입니다.
- 작업자는 섹션 1 루프이며, 섹션 6 subagents가 제작자와 검토자 구분입니다.
- 병렬 루프는 섹션 15 worktrees에서 격리됩니다.
- 실행 간 상태는 섹션 9 메모리와 섹션 12 작업 기록에 저장됩니다.
- 보고서와 추적은 섹션 20입니다. 개선 루프는 섹션 20의 측정을 harness 변경 사항으로 다시 연결합니다.

실행 가능한 항목도 동일한 방식으로 연결됩니다. `run_turn`는 섹션 20과 바이트 단위로 동일하며, 검증은 외부에서 래핑됩니다:

```python
def worker(prompt):                                # src/demo.py · the inner loop, unchanged
    return run_turn([{"role": "user", "content": prompt}], model, reg, Session(mode=DEFAULT))

checker = agent_checker(RUBRIC, model)             # a fresh grader agent, no tools
result = verified_run("What is 27 + 15? Use the add tool.", worker, checker, budget=2)
```

새로운 점은 규율입니다: 완료 전에 등급, 시작 전에 예산, 항상 보고.

### 추가 읽기

이 모든 것은 `src/`에 없습니다. 이는 ai-agent-book와 발표된 자기개선 연구에서 나왔으며, 표에 있는 시스템에서 확인된 것은 아닙니다.

**학습된 변경 사항 라우팅하기.** 예를 들어 실행 중 스테이징 데이터베이스에 다른 연결 문자열이 필요하다고 발견하면, 그것은 어디에 가야 합니까?
개선 루프에서 어려운 부분은 교훈을 찾는 것이 아닙니다. 어려운 것은 교훈을 어디에 두느냐를 선택하는 것입니다. 교훈을 둘 수 있는 네 가지 장소가 있습니다:

- **지식 문서.** 실행에서 발견한 한 가지 사실입니다. 작성하기도 쉽고 삭제하기도 쉽습니다. 작업이 필요할 때 에이전트가 이를 다시 읽습니다(섹션 9).
- **프롬프트나 skill.** 반복되어야 하는 행동입니다. 이를 로드할 때마다 문맥 비용이 듭니다(섹션 7).
- **프로그램.** 매번 동일하게 실행되는 절차입니다. 추론 시 비용이 없으며 테스트할 수 있습니다(섹션 2).
- **가중치.** 최후의 수단입니다. 느리고, 비용이 많이 들며, 되돌리기 가장 어렵습니다. 이 저장소의 harness 논문의 범위를 벗어납니다.

규칙은 변화를 담을 수 있는 가장 작은 장소를 선택하는 것입니다. 가장 작다는 것은 또한 확인하기 쉽고 되돌리기 쉽다는 것을 의미합니다.
연결 문자열은 사실이므로 문서에 들어갑니다. system prompt에는 들어가지 않습니다.

두 번째 장소인 프롬프트나 skill은 가장 오용될 가능성이 있으므로, 자체 게이트가 필요합니다.
한 번의 잘못된 실행이 아닌, 여러 번 발생한 실패에서 편집을 작성하십시오.
언제 적용되는지 명시하여 관련 없는 실행에서는 조용히 있게 하세요. 그런 다음 두 번 확인하십시오: 편집과 가까운 경우와 작성하지 않은 유지 집합에서 확인합니다.
먼저 트래픽의 일부에 배포하고, 롤백을 준비하십시오.
Karpathy는 이를 system prompt 학습이라고 부릅니다: 가중치 대신 단어를 편집합니다.
ACE는 전체 프롬프트를 다시 작성하는 대신 번호가 매겨진 컨텍스트 항목을 수정하여 각 편집을 작게 유지합니다.

**도구 사용자에서 도구 제작자로.** 세 번째 장소인 프로그램은 이전 섹션에서 다루지 않은 것입니다.
skill은 모델이 여전히 읽고 따라야 하는 지침을 전달합니다(섹션 7). 컴파일된 워크플로우는 harness에 모델 없이 실행되는 프로그램을 전달합니다.
예를 들어 에이전트가 같은 종류의 티켓을 열 번 예약했다고 합시다. 다섯 단계가 이를 프로그램으로 바꿉니다:

1. **캡처.** 작동한 한 번의 실행을 기록합니다: 어떤 호출을 했는지, 어떤 순서로 했는지, 각 호출 전후 상태가 무엇인지.
2. **매개변수화.** 실행 간에 변경된 부분을 인수로 만듭니다. 변하지 않은 부분은 프로그램으로 남습니다.
3. **리셋 시 검증하세요.** 새로운 환경에서 다시 실행합니다(섹션 23). 각 단계는 실행 전에 확인을 받고, 실행 후에 확인을 받으며, 마지막 상태 확인도 받습니다.
4. **재실행하세요.** 다음 일치하는 작업에서 프로그램을 처음부터 끝까지 실행합니다. 모델 호출이 없으므로 빠르고, 저렴하며, 매번 동일합니다.
5. **무효화하세요.** 하나의 실패한 검증이 프로그램을 종료시킵니다. 작업은 모델로 되돌아가며, 모델은 새로운 작업을 캡처할 수 있습니다.

도구를 만드는 과정 또한 반대쪽에서 같은 생명주기를 따릅니다. 에이전트가 할 수 없는 작업을 만나면, 라이브러리를 찾고,
이를 도구로 포장한 뒤, 등록소가 수락하기 전에 검증합니다(섹션 2).
두 가지 방법 모두 하나의 비용이 많이 드는 탐험을 저렴하게 확인할 수 있는 기능으로 바꿉니다.
둘 다 5단계가 필요합니다. 왜냐하면 사이트나 API가 변경될 수 있기 때문입니다.

**harness 편집하기.** 루프가 단순한 프롬프트가 아니라 harness 코드를 변경하고 싶다고 가정해 봅시다. 그러면 패치를 받기 전에 계약이 필요합니다.
변경 계약에는 네 가지 사항이 명시되어 있습니다: 실패한 추적과 발생 빈도, 근본 원인, 변경이 개선해야 할 것, 그리고 이를 되돌리는 방법.
계약이 없으면 패치도 없습니다. 계약을 인간이 읽고 검토하며, 이것이 자기 수정 루프와 아무도 감사할 수 없는 루프를 구분하는 요소입니다.
루프가 편집할 수 있는 코드는 처음부터 선언됩니다. 권한, 예산, 게이트는 그 영역 밖에 위치하여 루프가 접근할 수 없습니다(섹션 3).

루프가 검색하는 위치는 사다리입니다. 가장 낮은 단계는 프롬프트의 한 가지 규칙입니다.
그 위에: 컨텍스트가 어떻게 조립되는지, 그 다음에 워크플로우, 그 다음에 harness 코드, 그리고 변경을 제안하는 코드.
아래 단계가 실패할 때에만 한 단계 올라가세요. 위 단계로 올라갈수록 검색 범위는 넓어지고 그에 대한 검사는 약해집니다.
프롬프트 규칙을 하루 만에 A/B 테스트할 수 있습니다. 변경을 제안하는 코드를 교체하면, 이후 모든 변경 제안이 다르게 이루어집니다.

**온라인 실행, 오프라인 학습기.** 둘을 분리하여 두세요. 온라인 루프는 작업을 실행하고 발생한 일을 기록합니다.
교훈을 도출하지 않으며, skills를 승격하지 않고, 프롬프트를 편집하지도 않습니다.
별도의 오프라인 루프는 여러 실행을 한 번에 읽고, 반복되는 실패를 찾아 후보 변경을 작성하고, 이를 검증한 뒤 버전을 배포합니다.

분할은 하나의 실행이 에이전트를 다시 쓰는 것을 막는 역할을 합니다. 하나의 운 좋은 경로는 패턴이 아닙니다.
에이전트에게 무엇을 기억해야 하는지 알려주는 웹페이지는 증거가 아닙니다.
여러 실행에서 동일한 신호를 요구하고 검증 게이트를 추가하면 둘 다 릴리스에서 제외됩니다.

분할은 측정할 항목도 변경합니다. 숫자 하나가 아니라 두 개를 읽으세요:

- **업데이트.** 루프가 좋은 후보를 만들어내고 있는가. 제안된 수, 검증을 통과한 수, 롤백된 수.
- **효과.** 출시된 변경사항이 도움이 되고 있는가. 변경사항이 목표로 하는 실행에 부담을 주는가, 에이전트가 이를 따르는가, 제외된 성능이 변하는가.

둘 다 읽으세요. 첫 번째만 있을 경우, 올바르지만 절대 로드되지 않는 skill은 실패한 업데이트처럼 보이며, 루프는 자신에 대해 잘못된 결론을 내립니다.

## 시스템별

각 에이전트가 외부 루프를 구성하는 방법.

| | Claude Code | Hermes Agent | mini-swe-agent | deepseek-harness |
| --- | --- | --- | --- | --- |
| **장점** | 스크립트화된 검증과 엄격한 예산. | 예산, 롤백을 포함한 개선 루프 추가. | 실행당 엄격한 청구서. | 외부 루프는 발행된 이벤트에 plugins로 첨부. |
| **단점** | 소스에 닫힌 개선 루프 없음. | 내장된 등급 평가 및 재시도 루프 없음. | 예산의 절반만 해당. | 작업을 확인하는 것이 없음; 라운드만이 유일한 예산. |
| **왜** | 외부 루프는 사용자가 스크립트로 작성하는 프로그램입니다. | 개선 사항은 모델에 반영되어야 합니다. | 한 번의 실행은 하나의 채점된 작업입니다. | 루프 자체가 plugin이므로 제어가 여기에 연결됩니다. |
| **방법: 검증** | 스크립트화된 단계, 심사 패널. | 제작자와 검토자, 그리고 오프라인 테스트. | 없음. SWE-벤치는 오프라인으로 채점합니다. | 내장된 것은 없음; 완료는 스스로 선언합니다. |
| **방법: 이벤트 루프** | Cron, 깨우기, 원격 트리거. | 제한된 도구 세트와 함께 Cron. | 없음. 실행자가 시간을 스케줄링하는 것이 아니라 작업을 스케줄링합니다. | 알림은 기록에서 한 턴으로 재생됩니다. |
| **방법: 개선 루프** | 재개 가능한 워크플로우가 캐시에서 재생됩니다. | 실행은 학습 데이터가 됩니다. | 없음. 예산만 존재합니다. | 배송된 것은 없으며; 연결 지점은 존재합니다. |

## 실패 모드

- **정지 조건 없음.** 상한 없는 재시도 루프는 누군가 송장을 확인할 때까지 토큰을 소모합니다. 완화: 하니스가 강제하는 반복, 토큰 및 시간 예산 사용.
- **자기 채점.** 작업자가 자신의 출력을 통과시키므로 검증 루프는 아무것도 검증하지 않습니다. 완화: 루프 외부에 고정된 루브릭과 별도의 검사 에이전트 사용.
- **무비판 루브릭.** 항상 통과시키는 채점자는 없느니만 못합니다. 나쁜 출력을 검증된 것으로 표시하기 때문입니다.
  완화: 적대적 검증(검사자가 반박하도록 프롬프트) 및 정기적인 인간 점검.
- **너무 일찍 방치됨.** 루프가 L1 보고서가 확인되기 전에 L3 쓰기 접근 권한을 얻습니다.
  완화: 섹션 3 권한으로 제한된 채 성숙도의 사다리를 한 단계씩 올라가십시오.
- **조용한 표류.** 방치된 루프는 퇴보하며 아무도 그 출력물을 읽지 않는다. 완화 방안: 하트비트, 항상 전달되는 보고서, 그리고 통과율과 비용에 대한 20절 지표.
- **상태 기억상실.** 각 실행마다 동일한 작업을 다시 발견하고 다시 수행한다. 완화 방안: 발견한 내용을 메모리나 작업 기록(9절, 12절)에 저장하고 실행 시작 시 읽는다.
- **자기 편집 harness가 게이트를 탈출함.** harness 코드를 수정할 수 있는 개선 루프가 이를 제한하는 코드를 수정할 수 있다.
  완화 방안: 권한과 예산은 루프가 편집할 수 없는 외부에 존재한다(3절).
- **대리 목표 표류.** 개방형 작업에서 루브릭은 실제 목표를 대신할 뿐이다. 루프는 대신 루브릭을 충족하는 법을 배우게 된다:
  익숙한 코드를 재사용하고, 노이즈를 발견으로 읽으며, 통과한 실행만 남깁니다. 점수는 오르지만 실제 목표는 멀어집니다.
  완화 방안: 실패한 실행을 증거에 남기고, 보류 집합을 새로 고치며, 사람이 실제 목표에 대해 출력을 확인하도록 합니다.
- **모든 수업은 프롬프트 편집이 됩니다.** 프롬프트는 작성하기 가장 쉬운 장소이므로 모든 것이 거기에 모이게 됩니다. 이것은 자체 규칙이 충돌할 때까지 커집니다.
  완화 방안: 수업의 내용에 따라 위치를 선택합니다. 사실은 문서에, 절차는 프로그램에, 반복되어야 하는 행동은 프롬프트에 넣습니다.
- **컴파일된 워크플로우는 환경보다 오래 살아남습니다.** 사이트나 API가 변경되었지만, 프로그램은 어쨌든 재실행됩니다. 모델보다 더 빠르게 잘못된 상태를 기록합니다.
  완화: 리플레이의 각 단계 전후로 확인하고, 첫 번째 확인 실패 시 프로그램을 종료합니다.
- **온라인 실행은 자체 학습을 촉진합니다.** 실행 중에 학습을 적용하는 에이전트는 단지 운이 좋았던 경로를 촉진하거나 기억하도록 심어진 신뢰할 수 없는 페이지를 텍스트로 다룰 수 있습니다.
  완화: 온라인 루프는 증거만 기록하고 다른 것은 하지 않도록 합니다. 별도의 오프라인 검증 과정이 후보를 릴리스 전에 검증합니다.

## 실행 가능

[`src/`](src/)는 20단계를 진행하며 다음을 추가합니다:

- [`verify.py`](src/verify.py): 검증 루프 (`verified_run`: 평가, 피드백 재시도, 예산, 에스컬레이션) 및 `agent_checker`, 평결마다 새로운 평가자.
- [`test.py`](src/test.py): 첫 시도 통과를 위한 오프라인 점검, 재시도 시 피드백 전달, 예산 상한, 그리고 PASS/FAIL 판정 계약.
- [`demo.py`](src/demo.py): 하나의 실시간 검증 실행: 추가 도구를 가진 작업자, 고정 루브릭을 채점하는 별도의 검사자, 예산이 소진되면 에스컬레이션.

루프는 변경되지 않음. 검증은 외부에서 이를 감쌉니다.

```bash
python sections/21-loop-engineering/src/test.py         # offline checks, no key
uv run python sections/21-loop-engineering/src/demo.py  # live demo, needs a key
```
