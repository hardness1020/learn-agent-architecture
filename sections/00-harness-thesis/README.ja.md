# 0 · Harness thesis

[English](README.md) · [繁體中文](README.zh-TW.md) · [简体中文](README.zh-CN.md) · **日本語** · [한국어](README.ko.md)

> モデルは何をするかを決定します。harness は、ツール、状態、および制限をモデルに提供します。

モデルは推論、ツールの選択、および停止のタイミングを所有します。harness はモデルの周りのコードです：ループ、ツール、メモリ、権限、およびインターフェース。

モデル呼び出しのみでは、1つの入力に対する1つの応答です。行動することを決定できますが、それ自体で行動することはできません。永続的な状態、ツール実行者、ファイルアクセス、または権限ゲートはありません。

harness は以下を行う必要があります：

1. アクションが実行される場所を提供すること。
2. モデルに有用な観察を提供すること。
3. 副作用が世界に到達する前に、それらを制御すること。
4. 状態を保持して、後の呼び出しが前の呼び出しの上に構築されるようにする。

harnessがない場合、モデルは回答することしかできません。ツールを実行したり、結果を観察したり、呼び出し間で作業を記憶したりすることはできません。

## メカニズム

![メカニズム図](assets/00-harness-thesis.png)

このセクションでは分解について説明します。小さなモデル呼び出しが中心に位置しています。harnessはその入力を提供し、出力を処理します。

モデルは判断を担当します。harnessは環境を担当します。

セクション1のループがコアの制御フローです。他のセクションはその周囲に入力、チェック、または状態を追加します。

- セクション2はtool runtimeとディスパッチを追加します。
- セクション3は権限とサンドボックスを追加します。
- セクション4では、ライフサイクルイベントをインターセプトするhooksが追加されます。
- セクション8と9では、context managementとメモリが追加されます。
- セクション10では、毎ターンsystem promptを組み立てます。
- 後のセクションでは、タスク、バックグラウンド作業、スケジューリング、および分離が追加されます。

これらの部分はループを置き換えるものではありません。ループに供給したり、ゲートしたり、状態を保持したりします。

### より多くのharnessは必ずしも良くない

各レイヤーは現在のモデルだけではできないことをカバーしています。それにより、各レイヤーには2つのコストが生じます：

1. 保守するコードが増え、バグが発生する可能性のある場所が増えること。
2. 1世代のモデルに依存した設計。新しいモデルは自分で計画、回復、または検証ができるかもしれません。古い回避策を無理に使用すると、性能が向上する代わりに低下してしまいます。

だから、harness engineeringは単に追加しているだけではありません。モデルが変わったときは、各レイヤーを再評価してください：まだ役立つものは残し、新しいモデルがカバーするものは削除します。
セクション20と21はこれの測定値を構築します。mini-swe-agentは極端なケースです：ほとんどharnessがなく、再評価するものはほとんどありません。

deepseek-harnessは同じ問題に別の観点から答えています。すべての部分がpluginで、ループも含め、どのコアもその他より特権を持ちません。
各機能は名前付きシームで公開され、1つのpluginがそれを主張します：あるシームではツール、別のシームでは権限、さらに別のシームではコンテキスト処理。
したがって、レイヤーを再評価することはフォークではなく設定変更です。レイヤーを削除するということは、そのpluginをロードしないことを意味します。

### さらなる読書

ai-agent-book からの2つのフレーミングです。これは検証用であり、このリポジトリ自身の発見ではありません。

**境界線のテスト。** モデルとharnessの間の線は、モデルが改善するにつれて変化します。本では確認できる2つの主張があります:

- **足場（スキャフォールディング）はモデルの強さに応じる。** 弱いモデルは強制的な計画、リトライ用の段階、およびスクリプト化されたチェックが必要です。強いモデルはその作業を自分で行います。
- **読み取りの閾値はモデルの方針による。** コードの読み取りを止めて編集を始めるタイミングは、訓練で学習されます。プロンプトの行やステップ制限はそれを促すものであり、決定するものではありません。

**両方の主張は1つのテストに変わる。** 同じ足場を2つのモデル生成で実行すると、スコアは逆方向に動くことがあります。
ある本の実験ではこれが報告されているため、サイズを信じるよりも方向性をテストしてください。
次に、各レイヤーが線のどちら側に位置するかを確認してください。もしモデルがすでにその判断を行っている場合、そのレイヤーは重複しており、トークンを無駄に消費するだけです。

**エージェントが最初に作業する場所。** 今日、タスクがエージェントに適しているかどうかを決めるのは2つの要素です：目標をどれだけ正確に記述できるか、そして機械が結果を確認できるかどうかです。
コーディングは両方の要素で高評価です。チケットや失敗したテストが目標を示します。テスト、型、リンター、そしてgitが作業完了の指標となります。
人々はそのインフラを自分たちのために構築し、エージェントはそれを既製の検証用 harness として再利用します。これがコーディングエージェントが最初に成熟した理由です。

**1つの性質が欠けている場合。** タスクは漠然と難しくなるわけではありません。特定の方法で失敗し、2つのケースがあります:

- **明確な目標、自動チェックなし。** ページを読みやすく書き直してください。ループには停止条件がないため、他に指示がなければ作業が完了したと見なされます。
- **自動チェック、明確な目標なし。** モジュールを整理してください。ループは目標ではなくチェックを目指しています。それにより何も壊れていないことが証明されますが、これはあなたが求めていることではありません。

**各ケースは異なる修正が必要です。** セクション21は、ドメインにチェックがない場合にチェックを構築します。チェックがないと、定義できない目標を修正することはできません。

## システムごと

モデルが決定することと、周囲のコードが構築することの違い。

| | Claude Code | mini-swe-agent |
| --- | --- | --- |
| **利点** | harness は安全性、永続性、subagents、およびオンデマンドの知識を追加します。 | ほとんどharnessコードがないため、維持するものはほとんどありません。 |
| **欠点** | harness が主要なコード領域になります。ほとんどの動作とほとんどのバグはそこに存在します。 | bash を実行する以外のすべての機能はモデルから来なければなりません。 |
| **理由** | モデル呼び出しは単独で動作できないため、harness が環境を所有します。 | 1つの bash ツールで十分であると仮定しています。Hooks、skills、メモリ、タスクは設計上存在しません。 |
| **方法: モデルが所有** | 判断、ツール選択、停止の決定。ツール名、スキーマ、および結果を見ることができます。 | 判断、編集戦略、提出のタイミング。 |
| **方法: harness が所有するもの** | ループ、ツール、権限、hooks、知識、タスク、調整。 | 1つのループ、1つの bash ツール、確認ゲート、ステップおよびコスト予算付き。 |
| **方法: サイズ信号** | ほとんどのコードはモデル呼び出しの外にあります。 | エージェントクラス全体は約150行です。 |

## 失敗モード

- **harness の行動に対してモデルを評価する。** 権限チェックとエラー回復は harness の行動です。失敗したときは harness を修正してください。
- **モデルが決定すべきことをハードコーディングする。** 順序固定のツールやスクリプト化された計画はモデルと衝突する可能性があります。判断が必要なときはモデルに決定させてください。
- **harnessが少なすぎる。** ツールや権限、context managementがないループは、モデルをチャットボットの動作にとどめます。欠けているレイヤーを追加してください。
- **harnessが多すぎる。** 各レイヤーはメンテナンスを追加し、古いモデル向けに作られたレイヤーは新しいモデルの性能を妨げることがあります。モデル変更時に再評価し、もはや役に立たないものは削除してください。
- **モデルポリシーをharness設定として扱う。** モデルは情報収集をいつ止めるかを学習します。プロンプトルールはそれを軽く促すだけです。保持する前にレイヤーを評価してください。
- **結果を確認できる機械がない場所でエージェントを実行する。** ループはタスクが完了したか、間違っているかを判断できません。チェッカーを追加するか、人間を経路に入れてください。
- **混合された責任。** ツール実行内の権限ロジックはテストや置換が難しいです。`Tool.ts`および`PreToolUse`のような明確な契約を保持してください。
