# 0 · Harness の主題

[English](README.md) · [繁體中文](README.zh-TW.md) · [简体中文](README.zh-CN.md) · **日本語** · [한국어](README.ko.md)

> 何をするか決めるのはモデルです。harness はモデルに tool と状態と制限を与えます。

推論、tool の選択、いつ止めるかはモデルが担います。harness はモデルを取り囲むコードです。loop、tool、memory、permission、そしてインターフェースを指します。

モデルを 1 回呼び出すだけなら、1 つの入力に対する 1 つの応答です。行動しようと決めることはできても、自分では行動できません。永続的な状態も、tool の実行系も、ファイルへのアクセスも、permission のゲートも持ちません。

harness は次のことをしなければなりません。

1. 行動を実行する場所を用意します。
2. モデルに役立つ観測を渡します。
3. 副作用が世界に届く前にゲートをかけます。
4. 状態を永続化し、後の呼び出しが前の呼び出しの上に積み上がるようにします。

harness がなければ、モデルは答えることしかできません。tool を実行することも、結果を観測することも、呼び出しをまたいで作業を覚えておくこともできません。

## 仕組み

![Mechanism diagram](assets/00-harness-thesis.png)

このセクションのテーマは分解です。中心には小さなモデル呼び出しが 1 つあります。harness はその入力を用意し、出力を処理します。

判断はモデルが担います。環境は harness が担います。

セクション 1 の loop が中心の制御フローです。他のセクションは、その周りに入力、検査、状態を足していきます。

- セクション 2 は tool runtime と dispatch を足します。
- セクション 3 は permission と sandbox 化を足します。
- セクション 4 はライフサイクルイベントを横取りする hook を足します。
- セクション 8 と 9 は context 管理と memory を足します。
- セクション 10 は turn ごとに system prompt を組み立てます。
- 後続のセクションは task、バックグラウンド作業、スケジューリング、分離を足します。

これらの部品は loop を置き換えません。loop に入力を送り、loop にゲートをかけ、loop のために状態を保存します。

### harness は多いほど良いわけではない

どの層も、今のモデルが単独ではできないことを補っています。そのため、どの層にも 2 つのコストが付いてきます。

1. 保守するコードが増え、バグが出る場所も増えます。
2. 設計が 1 つのモデル世代に縛られます。新しいモデルなら、自分で計画し、回復し、検証できるかもしれません。そこで古い回避策を押し付けると、性能は上がるどころか下がります。

つまり harness の設計は足すだけの作業ではありません。モデルが変わったら各層を評価し直してください。まだ役に立つものは残し、新しいモデルが自力でこなす層は消してください。
セクション 20 と 21 が、そのための測定を組み立てます。mini-swe-agent は極端な例です。harness がほとんどないので、評価し直すものもほとんどありません。

deepseek-harness は同じ問題に反対側から答えます。loop も含めてすべての部品が plugin で、他より特権を持つコアはありません。
どの能力も名前の付いた接合部で公開され、1 つの plugin がそれを引き受けます。tool はある接合部、permission は別の接合部、context の扱いは 3 つめの接合部です。
そのため、ある層を評価し直すのは設定の変更であって、fork ではありません。層を消すとは、その plugin を読み込まないということです。

### さらに読む

ai-agent-book からの 2 つの捉え方です。この repo 自身の知見ではなく、検証すべき主張として読んでください。

**境界を試す。** モデルと harness の境界がどこに引かれるかは、モデルが良くなるにつれて変わります。この本は、確かめられる主張を 2 つ出しています。

- **足場はモデルの強さに追随する。** 弱いモデルには、計画の強制、リトライの段取り、台本化された検査が必要です。強いモデルはその作業を自分でこなします。
- **どこまで読むかはモデルの方針です。** コードを読むのをやめて編集に入る境目は、訓練の中で身につきます。prompt の 1 行やステップ数の上限はそれを揺さぶるだけです。どちらも境目を決めはしません。

**2 つの主張は 1 つの検証になります。** 同じ足場を 2 つのモデル世代で走らせると、スコアは反対方向に動くことがあります。
本の実験の 1 つがこれを報告しているので、幅を信じるのではなく方向を検証してください。
そのうえで各層について、境界のどちら側にあるかを問うてください。モデルがすでにその判断をしているなら、その層は重複であり、token を燃やすだけです。

**agent が先に成果を出す領域。** ある仕事が今日の agent に向くかどうかは 2 つで決まります。目標をどれだけ正確に述べられるか、そして結果を機械が検査できるかです。
コーディングはどちらも高い点数です。チケットや失敗しているテストが目標を述べます。テスト、型、linter、git が、作業が終わったことを教えます。
人はこの基盤を自分たちのために作りました。agent はそれを既製の検証 harness として再利用します。コーディング agent が先に成熟したのはこのためです。

**片方の性質が欠けるとき。** 仕事は漠然と難しくなるのではありません。決まった形で失敗し、その形は 2 通りです。

- **目標は明確だが、自動の検査がない。** ページを読みやすく書き直す、といった仕事です。loop に終了条件がないので、否定するものがない以上、終わったと判断します。
- **自動の検査はあるが、目標が明確でない。** モジュールを整理する、といった仕事です。loop は目標ではなく検査を狙います。何も壊れていないことは証明しますが、それは頼んだ内容ではありません。

**それぞれに別の対処が要ります。** 領域に検査がない場合は、セクション 21 が検査を作ります。述べられない目標は、どんな検査でも直せません。

## システム別

モデルが決めることと、周りのコードが組み立てることの対比です。

| | Claude Code | mini-swe-agent |
| --- | --- | --- |
| **利点** | 安全性、永続性、subagent、必要に応じた知識を harness が追加。 | harness のコードがほぼなく、保守するものもほぼなし。 |
| **欠点** | harness が主要なコード面。挙動もバグもほとんどそこ。 | bash 実行を超える能力はすべてモデル任せ。 |
| **理由** | モデル呼び出しは単独で行動できないため、環境は harness の担当。 | bash tool 1 つで足りるという前提。hook、skill、memory、task は意図的に不在。 |
| **方法: model owns** | 判断、tool の選択、停止の決定。見えるのは tool 名、schema、結果。 | 判断、編集の進め方、いつ提出するか。 |
| **方法: harness owns** | loop、tool、permission、hook、知識、task、協調。 | loop 1 つ、bash tool 1 つ、確認ゲート、それにステップ数とコストの予算。 |
| **方法: size signal** | コードの大半はモデル呼び出しの外。 | agent クラス全体で約 150 行。 |

## 失敗モード

- **harness の挙動をモデルの手柄にする。** permission の検査もエラー回復も harness の挙動です。失敗したら harness を直してください。
- **モデルが決めるべきことをハードコードする。** tool の順序を固定したり計画を台本化したりすると、モデルと衝突しえます。判断が要る場面はモデルに決めさせてください。
- **harness が足りない。** tool も permission も context 管理もない loop では、モデルはチャットボットの挙動のままです。欠けている層を足してください。
- **harness が多すぎる。** どの層にも保守が付いてきますし、古いモデル向けに作った層は新しいモデルの足を引っ張りえます。モデルが変わったら評価し直し、役に立たなくなったものは消してください。
- **モデルの方針を harness の設定として扱う。** 情報収集をいつやめるかはモデルが学習しています。prompt の規則はそれを揺さぶるだけです。残すかどうかは測ってから決めてください。
- **結果を機械が検査できない領域で agent を走らせる。** loop は終わった仕事と間違った仕事を区別できません。検査器を足すか、人を経路に残してください。
- **責務が混ざる。** tool の実行の中に permission のロジックがあると、テストも差し替えも難しくなります。`Tool.ts` や `PreToolUse` のような明確な契約を保ってください。
