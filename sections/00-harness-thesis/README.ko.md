# 0 · Harness thesis

[English](README.md) · [繁體中文](README.zh-TW.md) · [简体中文](README.zh-CN.md) · [日本語](README.ja.md) · **한국어**

> 모델이 무엇을 할지 결정합니다. harness는 모델에 도구, 상태, 한계를 제공합니다.

모델은 추론, 도구 선택, 언제 멈출지 결정하는 것을 소유합니다. harness는 모델 주변의 코드입니다: 루프, 도구, 메모리, 권한, 인터페이스.

모델 호출만으로는 하나의 입력에 대한 하나의 응답일 뿐입니다. 행동을 결정할 수는 있지만 혼자 행동할 수는 없습니다. 지속적인 상태도, 도구 실행기도, 파일 접근권도, 권한 게이트도 없습니다.

harness는 다음을 수행해야 합니다:

1. 행동이 실행될 장소를 제공합니다.
2. 모델에 유용한 관찰을 제공합니다.
3. 부작용이 세상에 도달하기 전에 차단합니다.
4. 이후 호출이 이전 호출을 기반으로 하도록 상태를 유지합니다.

harness 없이는 모델이 오직 답변만 할 수 있습니다. 도구를 실행하거나, 결과를 관찰하거나, 호출 간 작업을 기억할 수 없습니다.

## 메커니즘

![메커니즘 다이어그램](assets/00-harness-thesis.png)

이 섹션은 분해에 관한 것입니다. 작은 모델 호출이 중심에 있습니다. harness는 입력을 제공하고 출력을 처리합니다.

모델이 판단을 소유합니다. harness가 환경을 소유합니다.

섹션 1의 루프가 핵심 제어 흐름입니다. 다른 섹션은 그 주위에 입력, 검사 또는 상태를 추가합니다:

- 섹션 2는 tool runtime과 디스패치를 추가합니다.
- 섹션 3은 권한과 샌드박싱을 추가합니다.
- 섹션 4는 라이프사이클 이벤트를 가로채는 hooks를 추가합니다.
- 섹션 8과 9는 context management와 메모리를 추가합니다.
- 섹션 10은 매 회전마다 system prompt를 조립합니다.
- 이후 섹션들은 작업, 백그라운드 작업, 스케줄링, 그리고 분리를 추가합니다.

이 부분들은 루프를 대체하지 않습니다. 루프에 데이터를 공급하거나, 제어하거나, 상태를 유지합니다.

### 더 많은 harness가 더 좋은 것은 아닙니다

각 레이어는 현재 모델이 단독으로 수행할 수 없는 것을 다룹니다. 이것은 각 레이어에 두 가지 비용을 부과합니다:

1. 유지해야 하는 코드가 많아지고, 버그가 나타날 수 있는 장소가 더 많습니다.
2. 한 세대 모델에 묶인 설계입니다. 새로운 모델은 스스로 계획하고, 복구하며, 검증할 수 있습니다. 이전의 우회 방법을 강제로 적용하면 성능이 향상되는 대신 낮아집니다.

그래서 harness engineering는 단순한 추가가 아닙니다. 모델이 변경되면 각 레이어를 재평가하세요: 여전히 도움이 되는 것은 유지하고, 새로운 모델이 포함하는 것은 삭제합니다.
섹션 20과 21은 이를 위한 측정을 구축합니다. mini-swe-agent는 극단적인 경우입니다: 거의 harness가 없으므로 재평가할 거의 아무것도 없습니다.

deepseek-harness는 동일한 문제를 다른 쪽에서 해결합니다. 모든 부분이 plugin이며, 루프도 포함되어 있고, 어떤 코어도 나머지보다 특권을 갖지 않습니다.
각 기능은 이름 있는 심에서 공개되고, 하나의 plugin이 이를 주장합니다: 하나의 심에서는 도구, 다른 심에서는 권한, 세 번째 심에서는 컨텍스트 처리가 존재합니다.
따라서 레이어를 재평가하는 것은 포크가 아닌 구성 변경입니다. 레이어를 삭제한다는 것은 해당 plugin을 로드하지 않는 것을 의미합니다.

### 추가 읽기

ai-agent-book에서 나온 두 가지 프레이밍. 이 저장소 자체의 발견이 아니라 테스트한다고 주장함.

**경계 테스트.** 모델과 harness 사이의 선은 모델이 향상됨에 따라 변함. 책에서는 확인할 수 있는 두 가지 주장을 제시함:

- **스캐폴딩은 모델 강도를 따라간다.** 약한 모델은 강제 계획, 재시도 단계, 스크립트 확인이 필요함. 강한 모델은 그 작업을 스스로 수행함.
- **읽기 임계값은 모델 정책이다.** 코드를 읽는 것을 멈추고 편집을 시작할 시점은 학습 과정에서 학습됨. 프롬프트 줄이나 단계 제한이 이를 살짝 유도함. 하지만 이를 설정하지는 않음.

**두 가지 주장은 하나의 테스트로 변함.** 두 모델 생성에서 동일한 스캐폴드를 실행하면 점수가 반대 방향으로 움직일 수 있음.
한 책 실험에서 이를 보고했으므로 크기를 믿기보다는 방향을 테스트해야 함.
그런 다음 각 계층에 대해 그것이 선의 어느 쪽에 위치하는지 물어보세요. 모델이 이미 그 판단을 한다면, 그 계층은 중복이며 토큰만 소모합니다.

**에이전트가 먼저 작업하는 곳.** 오늘날 어떤 작업이 에이전트에 적합한지는 두 가지에 달려 있습니다: 목표를 얼마나 정확하게 명시할 수 있는지, 그리고 기계가 결과를 확인할 수 있는지 여부입니다.
코딩은 두 가지 모두에서 높은 평가를 받습니다. 티켓이나 실패한 테스트가 목표를 명시합니다. 테스트, 타입, 린터 및 git가 작업이 완료되었는지 알려줍니다.
사람들이 그 인프라를 스스로 구축했고, 에이전트는 이를 기성 검증 harness로 재사용합니다. 이것이 코딩 에이전트가 먼저 성숙한 이유입니다.

**하나의 속성이 부족할 때.** 작업이 막연하게 어려워지는 것은 아닙니다. 특정한 방식으로 실패하며, 두 가지 경우가 있습니다:

- **명확한 목표, 자동 검사 없음.** 페이지를 더 읽기 쉽게 다시 작성하세요. 반복문에는 종료 조건이 없으므로 달리 지시가 없는 한 작업이 완료되었다고 호출됩니다.
- **자동 검사, 명확한 목표 없음.** 모듈을 정리하세요. 반복문은 목표 대신 검사를 향합니다. 이것은 아무 것도 깨지지 않았음을 증명하지만, 당신이 요청한 것은 아닙니다.

**각 경우마다 다른 수정이 필요합니다.** 섹션 21은 도메인에 체크가 없을 때 체크를 만듭니다. 체크가 없는 것은 명시할 수 없는 목표를 수정하지 않습니다.

## 시스템별

모델이 결정하는 것과 주변 코드가 구성하는 것.

| | Claude Code | mini-swe-agent |
| --- | --- | --- |
| **장점** | harness는 안전성, 지속성, subagents 및 필요 시 지식을 추가합니다. | 거의 harness 코드가 없으므로 유지 관리할 것이 거의 없습니다. |
| **단점** | harness가 주요 코드 표면이 됩니다. 대부분의 동작과 대부분의 버그가 그곳에 존재합니다. | bash를 실행하는 것 이상 모든 기능은 모델에서 나와야 합니다. |
| **이유** | 모델 호출은 스스로 행동할 수 없으므로 harness가 환경을 소유합니다. | 한 개의 bash 도구로 충분하다고 가정합니다. Hooks, skills, 메모리 및 작업은 설계상 없습니다. |
| **방법: 모델 소유** | 판단, 도구 선택 및 중지 결정. 도구 이름, 스키마 및 결과를 확인합니다. | 판단, 편집 전략 및 제출 시기. |
| **방법: harness 소유** | Loop, 도구, 권한, hooks, 지식, 작업, 그리고 조정. | 하나의 루프, 하나의 bash 도구, 확인 게이트, 그리고 단계 및 비용 예산. |
| **방법: 크기 신호** | 대부분의 코드는 모델 호출 외부에 있습니다. | 전체 에이전트 클래스는 약 150줄입니다. |

## 실패 모드

- **harness 행동에 대해 모델에 크레딧을 주는 것.** 권한 확인과 오류 복구는 harness 행동입니다. 실패할 경우 harness를 수정하세요.
- **모델이 결정해야 할 것을 하드코딩하는 것.** 경직된 도구 순서와 스크립트화된 계획은 모델과 충돌할 수 있습니다. 판단이 필요할 때 모델이 결정하도록 하세요.
- **harness가 너무 적음.** 도구, 권한, 또는 context management이 없는 루프는 모델을 챗봇 행동 상태로 유지합니다. 누락된 레이어를 추가하세요.
- **harness가 너무 많음.** 각 레이어는 유지보수가 필요하며, 이전 모델용으로 만들어진 레이어는 새로운 모델의 성능을 저해할 수 있습니다. 모델 변경 시 재평가하고 더 이상 도움이 되지 않는 것은 삭제하세요.
- **모델 정책을 harness 설정으로 취급함.** 모델은 언제 정보를 수집을 중단할지 학습합니다. 프롬프트 규칙은 단지 그것을 살짝 유도할 뿐입니다. 레이어를 유지하기 전 반드시 측정하세요.
- **결과를 확인할 수 있는 기계가 없는 곳에서 에이전트를 실행함.** 루프는 완료된 작업과 잘못된 작업을 구분할 수 없습니다. 검사기를 추가하거나 경로에 사람을 포함시키세요.
- **혼합된 책임.** 도구 실행 내의 권한 로직은 테스트하거나 교체하기 더 어렵습니다. `Tool.ts` 및 `PreToolUse`와 같은 명확한 계약을 유지하세요.
