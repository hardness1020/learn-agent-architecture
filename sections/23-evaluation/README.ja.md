# 23 · Evaluation

[English](README.md) · [繁體中文](README.zh-TW.md) · [简体中文](README.zh-CN.md) · **日本語** · [한국어](README.ko.md)

> 合格率は、それを支える環境の価値にしか価値がない。

セクション20は生産を監視する。それは何が起こったかを示すが、それが良かったかどうかは決して示さない。このセクションは別の質問に答える：この変更によってエージェントは良くなったか。

単一モデル呼び出しの場合、その質問は簡単だ。プロンプトを送信し、回答を参照と比較し、数を数える。

エージェントはそのすべての部分を壊す。複数のターンを実行する。タスクに記載されていない情報をユーザーに尋ねる。保存されたデータを変更するツールを呼び出す。
異なるルートで同じ結果に到達する。同じタスクで同じビルドを2回実行しても結果が異なることがある。

したがって、エージェントのスコアにはプロンプトのリストではなく、テストベッドが必要だ：状態をリセットするもの、ユーザーの代わりとなるもの、会話を段階的に進めるプロトコル、
そして、世界が残したランを採点するルーブリック。

それを飛ばしても数字は届く。ただ、何の意味もない。タスクがトレーニングに漏れたスイート。3ポイントの差は単なるサンプリングノイズ。
よくスコアされ、顧客が指定していない注文を返金するビルド。

## メカニズム

![機構図](assets/23-evaluation.png)

evaluation 環境は5つの部分で構成されている。4つはデータ、1つは制御フロー。

- **データセット。** タスクの記録。それぞれ開始状態、ユーザーの希望、ランのチェック方法を保持。
- **環境状態。** タスクが開始し、終了する可変データ：注文、ファイル、データベース。
  十分に現実的で重要である必要があり、リセット可能な程度に制御されていること。
- **ツール.** エージェントが実行できる操作。これらは原子操作に保つ（注文を読む、注文を返金する）、
  「顧客の問題を解決する」という名前の1つのツールではない。
- **ルブリック.** 完了した実行がどのようにスコアに変換されるか。
- **インタラクションプロトコル.** 誰がいつ話すか、エピソードがいつ終了するか。

セクション20のevalは`(input, grade)`ペアを取りました：1つの文字列入力、1つの文字列出力、1つの合格率。このセクションはそのエントリーポイントを保持し、その下に環境を置きます。

### 新: 環境とそのリセット

環境は状態を保持し、それを変更する唯一の方法を所有しています：

```python
def reset(self):                                       # src/evaluation.py
    self.state = deepcopy(self.initial)                # a fresh copy per episode
    self.calls = []

def call(self, name, **args):
    tool = self.tools.get(name)
    if tool is None:
        self.calls.append((name, False))               # illegal: no such tool
        return f"error: no tool named {name}"
    try:
        out = tool(self.state, **args)
    except Exception as e:                             # illegal: wrong arguments
        self.calls.append((name, False))
        return f"error: {type(e).__name__}: {e}"
    self.calls.append((name, True))
    return str(out)
```

- `reset` は開始スナップショットをディープコピーするため、エピソード2はエピソード1の書き込みを決して見ません。
  それがなければ、返金タスクの2回目の実行は、すでに返金済みの注文から始まります。
- 拒否された呼び出しは、単なる失敗フラグではなく、理由を示すメッセージを返します。その回復は、テスト対象の動作の一部です。
- すべての呼び出しは、それが合法かどうかと共にログに記録されます。そのログはプロセスメトリクスです：違法な呼び出しとステップ数、結果チェックが通った場合でも利用可能です。

### 新規: シミュレートされたユーザーとプロトコル

ほとんどのベンチマークは最初のメッセージでエージェントに完全なリクエストを渡します。実際のユーザーはそうしません。
彼らは「注文に問題があります」と切り出し、尋ねられた時に残りを教えます。

そのため、シミュレートされたユーザーはスクリプトを保持し、ターンごとに一つの事実だけを公表します。それが、採点されたskillを尋ねることを可能にするのです。

```python
def run_episode(env, task, agent, max_turns=8):        # src/evaluation.py
    env.reset()
    user = task["user"]()                              # a fresh simulated user per episode
    transcript, said = [], user()
    for _ in range(max_turns):                         # the ceiling: an episode always terminates
        if said is None:
            break
        reply = agent(said, env)
        transcript.append((said, reply))
        said = user(reply)
    return {"transcript": transcript, "state": env.state, "calls": list(env.calls)}
```

実行可能ファイルは固定されたスクリプトを使用するため、オフラインでのチェックは決定的に保たれます。ライブバージョンは同じスクリプトでLLMです。
キャラクターのままで答えるよう指示されており、現在のステップで必要な情報だけを提供し、何も創作しないようにされています。表現は異なる場合がありますが、開示の順序は変わりません。

強化版では、同じ状態でシミュレートされたユーザーに独自のツールが与えられます。その後、エージェントは他の人に行動を促さなければならず、実際のサポートコールと同じ状況になります。
また、ユーザーがエージェントに気づかせなければならない変更を加えることができるため、状態はエージェントのプライベートsandboxではなくなります。

### 新規: 1エピソードの評価

順番に3つのチェック:

```python
def grade(task, run):                                  # src/evaluation.py
    checks = {name: bool(fn(run["state"])) for name, fn in task["checks"]}       # the outcome
    said = " ".join(reply for _, reply in run["transcript"]).lower()
    told = {s: s.lower() in said for s in task.get("must_say", [])}              # what was communicated
    unsafe = [name for name, fn in task.get("veto", []) if fn(run)]              # zero tolerance
    return {"passed": all(checks.values()) and all(told.values()) and not unsafe, ...}
```

- **結果、手順ではない。** チェックは最終状態を読み取るので、それに到達するルートはどれでも通過します。参照解法はタスクを解く一つの方法であり、必須の方法ではありません。
- **言われたこと。** 顧客に金額を一度も伝えずに金額を返金するだけの実行は完了していません。
  状態だけを確認するとこれを見逃し、トランスクリプトだけを確認すると「請求したが実行しなかった」を見逃します。
- **拒否権。** 一つの安全違反があれば、他に何がスコアされても実行は失敗します：顧客が指定していない注文を返金する、秘密を印刷する、外部に郵送する。
  他の次元ではこれを取り戻すことはできません。

### 指標：k回の実行の意味

1回の実行は判定を出します。同じタスクを複数回実行すると、重要な数値が得られます:

- **Pass@k**: k回の実行のうち少なくとも1回は成功。回答は「できるかどうか」で、探索的タスクに適した指標です。
- **Pass^k**: k回の実行すべてが成功。回答は「信頼できるか」で、回帰ゲートに適した指標です。
- **Best@k**: k回の実行のうち最良のスコアで、2値判定ではなく段階評価のあるオープンタスク向けです。

両者は急速に乖離します。単一実行の成功率が60％の場合、Pass@5 は約99％、Pass^5 は約8％です。
誤った指標を報告すると、コイン投げがまるで正規の機能のように見えます。

それらと並んで、コールログには既にプロセス指標が存在します：合法コールの割合、既知の正常ベースラインに対するステップ数、再試行回数、タスクごとのコストです。
これらが、成功した実行が安価に達成されたのか、それとも力ずくで達成されたのかを教えてくれる指標です。

### 自由回答形式の作業の評価

州のチェックは、チェック可能な最終状態を持つタスクをカバーします。書面の回答にはハッシュ化するものがないため、モデルはルーブリックに基づいて採点します。
採点がどれだけうまく機能するかは、ルーブリックの書き方にかかっています:

1. **専門家に基づく。** 表面的な流暢さではなく、領域の専門家がチェックする内容をエンコードします。
2. **完全なカバレッジ。** 正確性、完全性、安全性を含み、一般的な失敗は暗示ではなく明示的に名前を挙げます。
3. **重み付けと拒否権。** 基準は必須、重要、任意に分けられ、作り話の事実などの拒否項目はスコアをゼロにします。
4. **自己完結。** 各項目は評価者自身の意見なしでチェック可能です。「少なくとも二つの情報源を引用し、それぞれが結論をどのように支持しているか説明する」は有効です。
   「深い理解を示す」は示さない。

判定者はモデルであり、モデルの失敗を持つ。より長い回答を好む。最初に読んだ候補を優先する。
エージェントと同じファミリーの判定者はその盲点を共有するため、エージェントが犯すのと同じエラーを正確に許す。

緩和策は安価である。異なるファミリーの判定者を使う。二重に評価し、順序を入れ替える。
スケールで信頼する前に、人間がラベル付けしたゴールドセットで判定者を校正し、意見不一致は人間に送る。

### データセットがスコアの意味を決める

悪いデータセットで完璧な環境を実行してもノイズが返る。ベンチマークで生き残る4つのルール。

- **検証可能。** 答えや最終状態は人間が読まなくても確認できる。
- **段階別。** 簡単、中程度、難しいタスクが分けられているので、簡単なタスクだけに有利な変更が平均値に隠れることはない。
- **人間による確認済み。** 誰かがタスクが解けることとチェックが公平であることを確認する。
  元のタスクが不十分に定義されていたり、不公平なテストで採点されたために、ベンチマークのサブセット全体が存在する。
- **汚染防御。** 公開タスクが次の訓練セットに入る。防御策: 各タスクファイルにカナリア文字列を入れる、解答を秘匿する、
  モデルのカットオフ後に収集されたタスク、1つの形状から新しいインスタンスを生成するパラメータ化されたテンプレート。

### 違いを読み取る

2つのビルド、100タスク、70パーセント対73パーセント。それは結果ではない。

- **ノイズ帯。** n 個のタスクにおける率の標準誤差は、`p(1-p)/n` の平方根程度です。
  100 個のタスクで 70 パーセントの場合、それはおおよそ 4.6 ポイントなので、3 ポイントの差はノイズの範囲内です。
- **繰り返す。** サンプリングやツールのタイミングはスコアを実行ごとに変動させます。設定ごとに 3〜5 回実行し、1 つの数値ではなくその広がりを報告します。
- **ペアで。** 両方のビルドは同じタスクを実行したので、タスクごとに比較し、異なる箇所だけに注目します。
  ペアリングは比較からタスクの難易度を除外するため、2 つの独立したレートを使うよりもはるかに少ないサンプルで済みます。
- **仮説を数える。** 95% の信頼度で 6 つの変更をテストすると、1 つが偶然有意に見える確率は約 26% です。
  信じる前に、閾値を厳しくするか、勝者を再実行してください。

期待する改善が、スイートが解決できる範囲よりも小さい場合、次の作業はエージェントを調整することではなく、スイートを拡張することです。

### レポートから変更へ

ベンチマークレポートは、次に何を変更するかという決定の入力です。

1. **まずharnessを疑う。** 停止したプロセス、バグのある評価者、またはもはや本番に一致しないタスクは、単に劣ったエージェントのように見えます。
   エージェントに触れる前に、失敗している軌跡を確認してください。
2. **クラスタを見つける。** 全体で88パーセントの成功率でも、関連する4つのタスクのうち3つが失敗している場合、それは一般的な弱点ではなく、1つの欠けている能力です。
3. **変数を1つ変更する。** モデル、シード、タスクセット、ステップ制限を固定し、それからラウンドごとに1つの要素を変更します。3つの要素を同時に変更するラウンドでは、何も説明できません。
4. **属性を確認する。** モデルをharnessに置き換えて、モデルがどれだけの情報を保持しているかを確認します。モデルを固定したままharnessの1つのコンポーネントを無効にして、そのコンポーネントの価値を確認します。
   このリポジトリの主張は、両方の数値が存在するということです。
5. **証拠を意思決定にスケーリングする。** 4つのタスクは、より大きな実行を正当化できます。しかし、デプロイを正当化することはできません。

製品内では、これは恒常的なインフラになります。マスタースイッチは機能を無効にして、ベアモデルの基準を取得します。
機能フラグはABテストのアームを保持し、同時にキルスイッチとしても機能します。
コミットごとの完全レンダリングされたsystem promptのスナップショットにより、プロンプト編集はevalスイートを他のコード変更と同じように実行できます。

ABテストの場合、移動したメカニズム指標（計画の長さ、プロンプトサイズ）を関心のある目標指標（タスク成功率、セッションコスト）から分けてください。
目標指標が改善しても実験を停止するguardrailの指標を維持してください。

### 統合方法

Evaluationはharnessを追加するのではなく再利用します：

- 環境のツールインターフェースはセクション2のレジストリであり、ハンドラは現実世界ではなくevalの状態を指しています。
- テスト対象のエージェントはセクション1のループで、変更は加えられていません。ループ内の何もが評価されていることを知りません。
- 裁判官はセクション21のチェッカーです：別のエージェント、新しいコンテキスト、満たすことはできても書き換えることはできない固定されたルーブリックです。
- セクション20は入力を提供します。洗浄された生成の痕跡は新しいタスクとなり、そのコストトラッカーはタスクごとのコストを提供します。
- 改善ループは証拠を添付したセクション21の外側ループです：測定、1つの変更、再測定。

## 障害モード

- **世界ではなくトランスクリプトを採点。** 「払い戻し済み」と言ったエージェントは、実際に払い戻しを行ったエージェントと同じスコア。
  緩和策：最終状態を確認し、エージェントが伝達しなければならなかった内容について別途チェックを保持。
- **汚染されたタスク。** 公開ベンチマークが次のトレーニングセットに到達するため、高スコアは能力ではなく再現率である可能性。
  軽減策: タスクファイル内のカナリア文字列、保留された回答、カットオフ後に収集されたタスク、およびパラメータ化されたテンプレート。
- **読み取りノイズの結果として。** 100個のタスクでそれぞれ1回ずつの実行で3ポイントの差があっても、何も決まらない。
  軽減策: 実行を繰り返し、タスクごとにペアで比較し、ノイズ帯内の差は無視して、多くの変更を同時にテストする場合は閾値を厳しくする。
- **壊れたharnessの原因をエージェントのせいにすること。** リソース不足のランナー、バグのある評価者、または古いタスクは、まさに品質低下のように見える。
  軽減策: エージェントを変更する前に失敗した軌跡を確認する。
- **エージェントの盲点を共有する審査員。** 同じ系統の審査員は、エージェントが犯すエラーを許容し、より長い回答を好み、どの候補が先に来たかに関係なく有利に扱う。
  軽減策: 異なる家系の審査員、順序を入れ替えて2回採点し、人間がラベル付けしたゴールドセットと較正。
- **報酬ハッキング。** エージェントが作業をスキップしてスコアを得るルートを見つける: キーワードの詰め込み、審査員へのお世辞、難しいケースを拒否。
  軽減策: ルーブリックの項目を拒否、結果指標以外のプロセスメトリック、定期的な人間によるスポットチェック。
- **変化を認識できないスイート。** 40タスクで2ポイントの改善は測定不可能なので、毎ラウンドが結論なしとして読み取られる。
  軽減策: さらに繰り返す前にタスクセットを増やす。
- **実行間での状態リーク。** リセットがないか、浅いリセットしかないため、あるタスクの書き込みが次のタスクのスコアを決定する。
  緩和策: 各エピソードごとの深いコピー、そして各実行ごとの独立した環境（第15節）。

## 実行可能

[`src/`](src/)は22を引き継ぎ、次を追加:

- [`evaluation.py`](src/evaluation.py): `reset`を備えた環境と記録されたツールインターフェース、1ターンごとに1つの事実を解放するシミュレートされたユーザー、エピソードプロトコル、
  評価（状態チェック、発言内容、拒否権）、Pass@kおよびPass^k、二項ノイズバンド、ならびに2つのビルドのペア比較。
- [`test.py`](src/test.py): 状態復元のリセットのオフラインチェック、エージェントが注文番号を尋ねる必要があるプロトコル実行、
  実行の結果チェックが合格した場合でも失敗させる安全拒否権、Pass@k対Pass^kの不安定なビルド上での比較,
  そして、回帰したビルドはペア比較で何が壊れたかを示す名前付けで低いスコアを付けます。
- [`demo.py`](src/demo.py)：1つの評価済みエピソード。モデルはサポートエージェントを操作し、そのツールコールは環境に投げ込まれます、
  そして harness は、残された状態をスコアリングします。

ループ自体は変更されません。スコアが意味を持つのは環境によるものです。

```bash
python sections/23-evaluation/src/test.py         # offline checks, no key
uv run python sections/23-evaluation/src/demo.py  # live demo, needs a key
```

## ソース

- [ai-agent-book · 第6章](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter6.md)（『深入理解 AI Agent』、李博杰; 中国語の原文が正典です）：
  evaluation 環境の5つの要素、段階的な情報開示、メトリック辞書、ルブリック基準、
  統計的有意性、ベンチマークから改善へのループ、そして内部 eval インフラ。
- [τ-bench](https://arxiv.org/abs/2406.12045)（シエラ）：言語モデルによってシミュレートされたユーザーで、最終的なデータベースの状態を
  注釈付きの目標状態と比較することで成功が判断され、信頼性のために Pass^k を使用。
- [τ²-bench](https://arxiv.org/abs/2506.07982) および [そのソース](https://github.com/sierra-research/tau2-bench)：シミュレートされたユーザーもツールを持つ二重制御環境
  で、報酬の基礎（ゴールドリプレイとハッシュされたデータベース状態、必要なフレーズ、
  任意のLLM評価によるアサーション）の構成要素が乗算される。
- [Verifier](https://github.com/willccbb/verifiers)：エージェント間の制御フローとしての環境、IDによってロードされるタスクセット、タスクごとのロールアウト、
  欠落またはエラーが発生したロールアウトの再開、およびランのアーティファクトに対してコードを実行するジャッジエージェント。
- [mini-swe-agent ソース](https://github.com/swe-agent/mini-swe-agent): `run/benchmarks/swebench.py`、インスタンスごとに1つのコンテナイメージ、
  インスタンスごとの軌跡および予測記録。
- [SWE-bench Verified](https://huggingface.co/datasets/princeton-nlp/SWE-bench_Verified): 500の人間によって検証されたインスタンス、
  新たに合格する必要のあるテストと、引き続き合格し続ける必要のあるテストによって評価。
- [GAIA](https://arxiv.org/abs/2311.12983): 466の質問のうち300件は回答が非公開、したがってリーダーボードはスクレイピングできない。
- [BIG-bench](https://github.com/google/BIG-bench): ベンチマークタスクをウェブスクレイプされた学習データから排除するために、すべてのタスクファイルに含まれるカナリア文字列。
- [Rubrics as Rewards](https://arxiv.org/abs/2507.17746) (Scale AI): 必須事実、必須の推論ステップ、ペナルティを課すべき落とし穴を記載したチェックリスト形式のルーブリック。
- [Claude Code](https://code.claude.com/docs): ワークフロー契約におけるレビュアーおよび審査員のステージは、ツールスキーマおよび文書化された動作に基づいており、ソースバックアップに基づくものではありません。
  Evaluation のスイートはソースに存在しないため、これらのセルは再構築としてマークされています。
