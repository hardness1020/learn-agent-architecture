# 23 · Evaluation

[English](README.md) · [繁體中文](README.zh-TW.md) · [简体中文](README.zh-CN.md) · **日本語** · [한국어](README.ko.md)

> 合格率の価値は、その裏にある環境の価値を超えません。

セクション 20 は本番を見張ります。何が起きたかは言いますが、それが良かったかどうかは決して言いません。このセクションはもう一方の問いに答えます。この変更で agent は良くなったのか。

モデル呼び出しが 1 回だけなら、この問いは簡単です。prompt を送り、答えを参照解と比べ、数えるだけです。

agent はその前提をことごとく壊します。複数の turn にわたって動きます。タスクに書かれていない情報を user に尋ねます。保存されたデータを変える tool を呼びます。
同じ結果に別の経路で到達します。同じビルドの同じタスクでも、2 回の実行が食い違うことがあります。

ですから agent のスコアには、prompt の一覧ではなくテストベッドが要ります。リセットされる状態、user の代役、会話を進める protocol、
そして実行が残した世界を採点する rubric です。

省いても数字は出てきます。ただ、その数字に意味がないだけです。タスクが学習データに漏れているスイート。サンプリングノイズでしかない 3 ポイントの差。
スコアは良いのに、顧客が一度も指定していない注文を返金するビルド。

## 仕組み

![Mechanism diagram](assets/23-evaluation.png)

評価環境は 5 つの部分からなります。4 つはデータで、1 つは制御フローです。

- **データセット。** タスクのレコードです。各レコードは開始状態、user が何を望むか、そして実行をどう検査するかを持ちます。
- **環境の状態。** タスクが開始時に持ち、終了時に残す可変データです。注文、ファイル、データベースなど。
  意味を持つ程度に現実的で、リセットできる程度に統制されている必要があります。
- **tool。** agent が実行してよい操作です。粒度は原子的に保ちます (注文を読む、注文を返金する)。
  「顧客の問題を解決する」という名前の tool 1 つ、ではありません。
- **rubric。** 終わった実行をどうスコアに変えるか。
- **対話 protocol。** 誰がいつ話し、いつエピソードが終わるか。

セクション 20 の eval は `(input, grade)` の組を取りました。文字列を 1 つ入れ、1 つ出し、合格率が 1 つ出ます。このセクションはそのエントリポイントを保ったまま、その下に環境を置きます。

### 本節の新規: 環境とそのリセット

環境が状態を保持し、それを変える唯一の手段を握ります。

```python
def reset(self):                                       # src/evaluation.py
    self.state = deepcopy(self.initial)                # a fresh copy per episode
    self.calls = []

def call(self, name, **args):
    tool = self.tools.get(name)
    if tool is None:
        self.calls.append((name, False))               # illegal: no such tool
        return f"error: no tool named {name}"
    try:
        out = tool(self.state, **args)
    except Exception as e:                             # illegal: wrong arguments
        self.calls.append((name, False))
        return f"error: {type(e).__name__}: {e}"
    self.calls.append((name, True))
    return str(out)
```

- `reset` は開始スナップショットを deep copy するので、エピソード 2 がエピソード 1 の書き込みを見ることはありません。
  これがないと、返金タスクの 2 回目の実行は、注文が既に返金済みの状態から始まります。
- 拒否された呼び出しは、素っ気ない失敗フラグではなく、理由を述べたメッセージを返します。そこから立ち直れるかどうかも、試験対象の振る舞いの一部です。
- すべての呼び出しは、それが正当だったかどうかとともに記録されます。そのログが過程のメトリクスです。不正な呼び出しとステップ数は、結果の検査が合格したときでも取れます。

### 本節の新規: シミュレートされた user と protocol

たいていの benchmark は、最初のメッセージで agent に要求の全文を渡します。現実の user はそうしません。
「注文が何かおかしい」と切り出し、残りは訊かれてから話します。

ですからシミュレートされた user は台本を持ち、1 turn につき 1 つの事実だけを出します。これが、尋ねることを採点対象のスキルにします。

```python
def run_episode(env, task, agent, max_turns=8):        # src/evaluation.py
    env.reset()
    user = task["user"]()                              # a fresh simulated user per episode
    transcript, said = [], user()
    for _ in range(max_turns):                         # the ceiling: an episode always terminates
        if said is None:
            break
        reply = agent(said, env)
        transcript.append((said, reply))
        said = user(reply)
    return {"transcript": transcript, "state": env.state, "calls": list(env.calls)}
```

実行可能コードは固定の台本を使うので、オフラインの検査は決定的なままです。live 版は、同じ台本を渡された LLM です。
その LLM には、役になりきって答えること、今の段階が必要とするものだけを出すこと、何も創作しないことが指示されます。言い回しは変わりますが、開示の順序は変わりません。

より強い版では、シミュレートされた user にも同じ状態に対する tool を持たせます。すると agent は、行動するよう相手を説得しなければなりません。サポートの電話とは実際そういうものです。
それはまた、user が状態を変え、agent がそれに気付かなければならないことも意味します。ですから状態は agent 専用の砂場ではなくなります。

### 本節の新規: 1 エピソードの採点

3 つの検査を、この順で行います。

```python
def grade(task, run):                                  # src/evaluation.py
    checks = {name: bool(fn(run["state"])) for name, fn in task["checks"]}       # the outcome
    said = " ".join(reply for _, reply in run["transcript"]).lower()
    told = {s: s.lower() in said for s in task.get("must_say", [])}              # what was communicated
    unsafe = [name for name, fn in task.get("veto", []) if fn(run)]              # zero tolerance
    return {"passed": all(checks.values()) and all(told.values()) and not unsafe, ...}
```

- **経路ではなく結果。** 検査は最終状態を読むので、そこに到達した経路はどれでも合格します。参照解はタスクを解く一つの方法であって、必須の方法ではありません。
- **何を伝えたか。** 返金はしたのに顧客に金額を伝えなかった実行は、終わっていません。
  状態だけを見るとそれを取りこぼし、transcript だけを見ると「言ったのにやっていない」を取りこぼします。
- **veto。** 安全性に 1 つでも触れれば、他が何点であろうと実行は不合格です。顧客が一度も指定していない注文の返金、秘密情報の出力、部外者へのメール送信などです。
  他のどの観点でも取り返せません。

### メトリクス: k 回の実行は何のためにあるか

1 回の実行は 1 つの判定を出します。同じタスクを何回か実行すると、意味のある数字が出ます。

- **Pass@k**: k 回のうち少なくとも 1 回が合格。「できるか」に答えます。探索的なタスクに適したメトリクスです。
- **Pass^k**: k 回すべてが合格。「信頼できるか」に答えます。回帰ゲートに適したメトリクスです。
- **Best@k**: k 回のうち最良のスコア。二値の判定ではなく段階的なスケールで採点する、開かれたタスク向けです。

この 2 つはすぐに乖離します。1 回あたりの成功率が 60 パーセントなら、Pass@5 はおよそ 99 パーセント、Pass^5 はおよそ 8 パーセントです。
間違った方を報告すれば、コイン投げがリリース済みの機能に見えます。

その横には、呼び出しログが既に持っている過程のメトリクスがあります。正当な呼び出しの割合、既知の良好なベースラインに対するステップ数、やり直し回数、タスクあたりのコストです。
合格した実行が安く合格したのか、力任せで合格したのかを教えてくれるのがこれらです。

### 終わりの決まっていない仕事を採点する

状態の検査は、終了状態を検査できるタスクをカバーします。文章で書かれた答えにはハッシュにするものがないので、モデルが rubric に照らして採点します。
採点がどれだけうまくいくかは、rubric の書き方で決まります。

1. **専門家に根ざしている。** 表面的な流暢さではなく、その分野の専門家が検査することを書き表しています。
2. **網羅している。** 正確さ、網羅性、安全性を扱い、よくある失敗をほのめかすのではなく明示的に名指しします。
3. **重み付けと veto がある。** 基準を必須、重要、任意に分け、事実の捏造のような veto 項目はスコアをゼロにします。
4. **自己完結している。** 各項目が、判定器自身の意見なしに検査できます。「少なくとも 2 つの出典を引用し、それぞれが結論をどう支えるか説明している」は機能します。
   「深い理解を示している」は機能しません。

判定器はモデルなので、モデル特有の失敗をします。長い答えを好みます。先に読んだ方の候補を優遇します。
agent と同じモデルファミリーの判定器は死角も共有するので、agent が犯す誤りをちょうどそのまま見逃します。

緩和は安く済みます。異なるモデルファミリーの判定器を使います。組にして順序を入れ替え、2 回採点します。
大規模に信頼する前に、人手でラベル付けした gold セットで判定器を較正し、食い違いは人間に回します。

[EvalGrill](https://github.com/hardness1020/EvalGrill) はこの流れをツールにまとめたものです。agent を使う実際の事例から eval を作り、判定器を較正してから信頼します。

### スコアの意味を決めるのはデータセット

完璧な環境でも、悪いデータセットを動かせば返ってくるのはノイズです。benchmark をまたいで通用する規則が 4 つあります。

- **検証可能。** 答えか終了状態が、人間が読まなくても検査できます。
- **段階分け。** 易しい、中くらい、難しいタスクを分けます。そうすれば、易しいタスクにしか効かない変更が平均の中に隠れられません。
- **人手で確認済み。** 誰かが、そのタスクが解けることと検査が公正であることを確かめます。
  元のタスクの記述が不十分だったり、不公正なテストで採点されていたりしたために作られた benchmark の部分集合が、いくつも存在します。
- **汚染対策済み。** 公開されたタスクは次の学習データに入ります。対策は、各タスクファイルに入れる canary 文字列、答えの非公開、
  モデルのカットオフより後に集めたタスク、そして 1 つの型から新しいインスタンスを生成するパラメータ化されたテンプレートです。

### 差を読む

2 つのビルド、100 タスク、70 パーセント対 73 パーセント。これは結果ではありません。

- **ノイズの幅。** n タスクの比率に対する標準誤差は、およそ `p(1-p)/n` の平方根です。
  100 タスクで 70 パーセントならおよそ 4.6 ポイントなので、3 ポイントの差はノイズの中に収まります。
- **繰り返す。** サンプリングと tool のタイミングで、スコアは実行ごとに動きます。設定ごとに 3 回から 5 回実行し、1 つの数字ではなくばらつきを報告します。
- **対にする。** 両方のビルドが同じタスクを走らせているので、タスクごとに突き合わせ、食い違ったところだけを見ます。
  対にするとタスクの難易度が比較から外れるので、独立した 2 つの比率を比べるよりはるかに少ないサンプルで済みます。
- **仮説の数を数える。** 6 つの変更を 95 パーセント信頼度で検定すれば、まぐれでどれか 1 つが有意に見える確率はおよそ 26 パーセントです。
  しきい値を厳しくするか、勝った方をもう一度走らせてから信じます。

期待している改善幅が、スイートが分解できる幅より小さいなら、次にやるべきことは agent の調整ではなくスイートを大きくすることです。

### レポートから変更へ

benchmark のレポートは、たった 1 つの判断への入力です。次に何を変えるか。

1. **まず harness を疑う。** 強制終了されたプロセス、バグのある採点器、本番と合わなくなったタスクは、agent が悪くなったのとまったく同じに見えます。
   agent に手を付ける前に、失敗した trajectory を読みます。
2. **かたまりを見つける。** 全体 88 パーセントで、関連する 4 タスクのうち 3 つが落ちているなら、それは全般的な弱さではなく、能力が 1 つ欠けているということです。
3. **変数を 1 つだけ変える。** モデル、シード、タスクセット、ステップ上限を固定し、1 ラウンドにつき 1 つだけ変えます。3 つ変えたラウンドは何も説明しません。
4. **寄与を切り分ける。** harness を固定してモデルを入れ替え、モデルがどれだけ担っているかを見ます。モデルを固定して harness の構成要素を 1 つ無効にし、その構成要素の価値を見ます。
   このリポジトリの主題は、その両方の数字が存在するということです。
5. **証拠の量を判断の重さに合わせる。** 4 タスクは、より大きな実行を正当化できます。デプロイを正当化することはできません。

プロダクトの中では、これは常設のインフラになります。マスタースイッチが機能を無効化して、素のモデルのベースラインを取れるようにします。
feature flag が AB テストの各群を担い、kill switch も兼ねます。
commit ごとに完全に展開された system prompt のスナップショットを取っておけば、prompt の編集も他のコード変更と同じように eval スイートを走らせられます。

AB テストでは、動かした機構のメトリクス (計画の長さ、prompt のサイズ) と、本当に気にしている目標のメトリクス (タスク成功率、session コスト) を分けます。
目標のメトリクスが改善していても実験を止められる guardrail メトリクスを持っておきます。

### 既存の構成への組み込み方

評価は harness に足すのではなく、harness を再利用します。

- 環境の tool インターフェースはセクション 2 の registry で、ハンドラの向き先を現実世界ではなく eval の状態にしたものです。
- 試験対象の agent はセクション 1 の loop そのままです。loop の中の何も、自分が評価されていることを知りません。
- 判定器はセクション 21 の checker です。別の agent、まっさらな context、満たすことはできても書き換えられない固定の rubric。
- 入力を供給するのはセクション 20 です。スクラブ済みの本番 trace が新しいタスクになり、そのコスト追跡器がタスクあたりのコストを与えます。
- 改善 loop は、根拠を添えたセクション 21 の外側の loop です。測り、1 つだけ変え、もう一度測ります。

各システムが、スコアの出どころとなるテストベッドをどう作るか。

| **利点** | まずい仕事が着地する前に捕まる。 | benchmark ランナーが agent に同梱されている。 | 正しい経路ならどれでも合格する。 | 1 つのタスクセットで、どのモデルや harness も採点できる。 |

## 失敗モード

- **世界ではなく transcript を採点する。** 「返金しました」と言う agent が、実際に返金した agent と同じスコアになります。
  緩和策: 終了状態を検査し、agent が伝えるべきだったことは別の検査として残します。
- **汚染されたタスク。** 公開 benchmark が次の学習データに入るので、高いスコアが能力ではなく recall でありうるということです。
  緩和策: タスクファイルの canary 文字列、答えの非公開、カットオフより後に集めたタスク、パラメータ化されたテンプレート。
- **ノイズを結果として読む。** 100 タスクを 1 回ずつ走らせた 3 ポイントの差は、何も決めません。
  緩和策: 実行を繰り返し、タスクごとに対にして比べ、ノイズの幅の中に収まる差は無視し、多くの変更を同時に検定するときはしきい値を厳しくします。
- **壊れた harness の責任を agent に着せる。** リソース不足のランナー、バグのある採点器、古びたタスクは、品質低下とまったく同じに見えます。
  緩和策: agent を変える前に、失敗した trajectory を読みます。
- **agent と死角を共有する判定器。** 同じモデルファミリーの判定器は、agent が犯す誤りを見逃し、長い答えを好み、先に来た候補を優遇します。
  緩和策: 異なるモデルファミリーの判定器、順序を入れ替えて 2 回採点すること、人手でラベル付けした gold セットでの較正。
- **報酬ハッキング。** agent が、仕事を飛ばしてスコアに至る経路を見つけます。キーワードの詰め込み、判定器へのお世辞、難しいケースの拒否などです。
  緩和策: rubric の veto 項目、結果のメトリクスと並べた過程のメトリクス、定期的な人間の抜き取り検査。
- **変化が見えないスイート。** 40 タスクでの 2 ポイントの改善は測定不能なので、どのラウンドも結論なしと読めてしまいます。
  緩和策: これ以上反復する前に、タスクセットを大きくします。
- **実行と実行の間で状態が漏れる。** リセットがない、あるいは浅いので、あるタスクの書き込みが次のタスクのスコアを決めてしまいます。
  緩和策: エピソードごとの deep copy と、実行ごとに隔離された環境 1 つ (セクション 15)。

## 実行

[`src/`](src/) は 22 を引き継ぎ、次を追加します。

- [`evaluation.py`](src/evaluation.py): `reset` と記録付き tool インターフェースを持つ環境、1 turn につき 1 つの事実を出すシミュレートされた user、エピソードの protocol、
  採点 (状態の検査、何を伝えたか、veto)、Pass@k と Pass^k、二項分布のノイズ幅、2 つのビルドの対比較。
- [`test.py`](src/test.py): 状態を復元する reset、agent が注文番号を尋ねなければならない protocol の実行、
  結果の検査が合格した実行を安全性の veto が落とすこと、不安定なビルドでの Pass@k と Pass^k の対比、
  そして退化したビルドが対比較で低いスコアになり、何が壊れたかを名指しすることのオフライン検査。
- [`demo.py`](src/demo.py): 採点されるエピソードを 1 つ。モデルがサポート担当を演じ、その tool call が環境に届き、
  harness がそれが残した状態を採点します。

loop は変わりません。スコアに意味を与えるのは環境です。

```bash
python sections/23-evaluation/src/test.py         # offline checks, no key
uv run python sections/23-evaluation/src/demo.py  # live demo, needs a key
```

  統計的有意性、benchmark から改善への loop、社内の eval インフラ。
- [τ-bench](https://arxiv.org/abs/2406.12045) (Sierra): 言語モデルにシミュレートさせた user、注釈付きの目標状態と最終データベース状態の比較による成否判定、
  そして信頼性のための Pass^k。
- [τ²-bench](https://arxiv.org/abs/2506.07982) と [そのソース](https://github.com/sierra-research/tau2-bench): シミュレートされた user も tool を持つ
  デュアルコントロール環境と、構成要素が掛け合わさる報酬の基礎 (gold の再生に対してハッシュ化されたデータベース状態、必須の言い回し、
  任意の LLM 判定によるアサーション)。
- [Verifiers](https://github.com/willccbb/verifiers): agent 間の制御フローとしての環境、id で読み込むタスクセット、タスクあたりの rollout、
  欠落したりエラーになったりした rollout の再開、そして実行の成果物に対してコードを実行する判定 agent。
- [mini-swe-agent source](https://github.com/swe-agent/mini-swe-agent): `run/benchmarks/swebench.py`、インスタンスごとに 1 つのコンテナイメージ、
  インスタンスごとの trajectory と予測のレコード。
- [SWE-bench Verified](https://huggingface.co/datasets/princeton-nlp/SWE-bench_Verified): 人手で検証した 500 インスタンス。
  新たに通るようになるべきテストと、通り続けるべきテストで採点されます。
- [GAIA](https://arxiv.org/abs/2311.12983): 466 問。うち 300 問は答えを非公開にして、リーダーボードをスクレイプできないようにしています。
- [BIG-bench](https://github.com/google/BIG-bench): benchmark のタスクを web スクレイプの学習データから守るために、各タスクファイルに入れる canary 文字列。
- [Rubrics as Rewards](https://arxiv.org/abs/2507.17746) (Scale AI): 必須の事実、必須の推論ステップ、そして減点されるべき落とし穴を名指しするチェックリスト形式の rubric。
- [Claude Code](https://code.claude.com/docs): workflow 契約におけるレビュー段階と判定段階。ソースのバックアップではなく、tool スキーマと文書化された挙動から。
  評価スイートはソースに存在しないので、それらのセルは再構成と印を付けています。
