# 23 · Evaluation

[English](README.md) · [繁體中文](README.zh-TW.md) · [简体中文](README.zh-CN.md) · [日本語](README.ja.md) · **한국어**

> 합격률은 그 뒤에 있는 환경만큼의 가치가 있을 뿐이다.

섹션 20은 생산을 관찰한다. 무슨 일이 일어났는지는 말하지만, 그것이 좋았는지는 절대 말하지 않는다. 이 섹션은 다른 질문에 답한다: 이 변화가 에이전트를 더 나아지게 만들었는가.

단일 모델 호출에서는 그 질문이 쉽다. 프롬프트를 보내고, 답변을 참조와 비교하고, 계산한다.

에이전트는 그 모든 부분을 깨뜨린다. 여러 차례 실행한다. 작업에서 결코 명시하지 않은 정보를 사용자에게 요청한다. 저장된 데이터를 변경하는 도구를 호출한다.
다른 경로로 동일한 결과에 도달한다. 동일한 빌드의 두 실행이 동일한 작업에서 일치하지 않을 수 있다.

그래서 에이전트 점수에는 프롬프트 목록이 아니라 테스트 베드가 필요하다: 상태를 재설정하는 장치, 사용자를 대신하는 장치, 대화를 진행하는 프로토콜,
그리고 세상의 결과를 평가하는 루브릭.

그것을 건너뛰어도 숫자는 여전히 나타난다. 단지 아무 의미가 없을 뿐이다. 훈련에 누수가 생긴 작업의 모음. 단지 샘플링 노이즈에 불과한 3점 차이.
점수가 잘 나오고 고객이 지정하지 않은 주문을 환불하는 빌드.

## 메커니즘

![메커니즘 다이어그램](assets/23-evaluation.png)

evaluation 환경은 다섯 부분으로 구성된다. 네 개는 데이터, 하나는 제어 흐름.

- **데이터셋.** 작업 기록. 각 기록은 시작 상태, 사용자가 원하는 것, 실행이 어떻게 검증되는지를 담고 있다.
- **환경 상태.** 작업이 시작하고 끝나는 변할 수 있는 데이터: 주문, 파일, 데이터베이스.
  충분히 중요할 정도로 현실적이어야 하며, 재설정이 가능할 정도로 제어되어야 한다.
- **도구.** 에이전트가 실행할 수 있는 작업들입니다. 작업을 원자적으로 유지하세요 (주문 조회, 주문 환불).
  '고객 문제 해결'이라는 하나의 도구 같은 것은 아닙니다.
- **루브릭.** 실행 완료가 점수로 전환되는 방식입니다.
- **상호작용 프로토콜.** 누가 언제 말하는지, 그리고 에피소드가 언제 끝나는지를 규정합니다.

섹션 20의 eval은 `(input, grade)` 쌍을 가져왔습니다: 하나의 문자열 입력, 하나의 문자열 출력, 하나의 통과율. 이 섹션은 해당 진입점을 유지하고 그 아래 환경을 배치합니다.

### 새롭게: 환경과 그 초기화

환경은 상태를 유지하며 상태를 변경할 수 있는 유일한 방법을 소유합니다:

```python
def reset(self):                                       # src/evaluation.py
    self.state = deepcopy(self.initial)                # a fresh copy per episode
    self.calls = []

def call(self, name, **args):
    tool = self.tools.get(name)
    if tool is None:
        self.calls.append((name, False))               # illegal: no such tool
        return f"error: no tool named {name}"
    try:
        out = tool(self.state, **args)
    except Exception as e:                             # illegal: wrong arguments
        self.calls.append((name, False))
        return f"error: {type(e).__name__}: {e}"
    self.calls.append((name, True))
    return str(out)
```

- `reset`은 시작 스냅샷을 깊은 복사하므로, 두 번째 에피소드는 첫 번째 에피소드의 기록을 볼 수 없습니다.
  그것이 없으면, 환불 작업의 두 번째 실행은 이미 환불된 주문으로 시작됩니다.
- 거부된 호출은 실패 플래그만 반환하지 않고, 이유를 설명하는 메시지를 반환합니다. 이에 대한 복구는 테스트 중인 동작의 일부입니다.
- 모든 호출은 합법적인지 여부와 함께 기록됩니다. 이 로그는 프로세스 지표로, 불법 호출과 단계 수를 나타내며, 결과 검사 통과 시에도 확인할 수 있습니다.

### 새로 추가: 시뮬레이션 사용자와 프로토콜

대부분의 벤치마크에서는 에이전트에게 첫 번째 메시지에서 전체 요청을 전달합니다. 실제 사용자는 그렇지 않습니다.
그들은 "내 주문에 문제가 있습니다"라고 시작하고 요청 시 나머지를 제공합니다.

따라서 시뮬레이션 사용자는 스크립트를 가지고 있으며, 한 차례에 한 가지 사실만 공개합니다. 이것이 등급이 매겨진 skill을 요청하게 만드는 이유입니다.

```python
def run_episode(env, task, agent, max_turns=8):        # src/evaluation.py
    env.reset()
    user = task["user"]()                              # a fresh simulated user per episode
    transcript, said = [], user()
    for _ in range(max_turns):                         # the ceiling: an episode always terminates
        if said is None:
            break
        reply = agent(said, env)
        transcript.append((said, reply))
        said = user(reply)
    return {"transcript": transcript, "state": env.state, "calls": list(env.calls)}
```

이 실행 파일은 오프라인 검사가 결정론적으로 유지되도록 고정된 스크립트를 사용합니다. 라이브 버전은 동일한 스크립트를 사용하면 LLM입니다.
캐릭터에 맞게 답변하도록 지시되며, 현재 단계에 필요한 것만 공개하고 아무것도 발명하지 않도록 합니다. 표현은 다를 수 있지만 공개 순서는 다르지 않습니다.

강화된 버전은 동일한 상태에서 시뮬레이션된 사용자에게 자체 도구를 제공합니다. 그 후 에이전트는 실제 지원 통화에서처럼 다른 사람이 행동하도록 설득해야 합니다.
또한 사용자가 에이전트가 알아차려야 하는 것들을 변경할 수 있으므로 상태가 더 이상 에이전트의 개인 sandbox가 되지 않습니다.

### 새로움: 한 에피소드 채점하기

세 가지 확인, 순서대로:

```python
def grade(task, run):                                  # src/evaluation.py
    checks = {name: bool(fn(run["state"])) for name, fn in task["checks"]}       # the outcome
    said = " ".join(reply for _, reply in run["transcript"]).lower()
    told = {s: s.lower() in said for s in task.get("must_say", [])}              # what was communicated
    unsafe = [name for name, fn in task.get("veto", []) if fn(run)]              # zero tolerance
    return {"passed": all(checks.values()) and all(told.values()) and not unsafe, ...}
```

- **결과, 경로가 아니라.** 검사는 최종 상태를 읽으므로 그 상태에 도달하는 어떤 경로든 통과합니다. 참조 솔루션은 과제를 해결하는 한 가지 방법일 뿐, 반드시 따라야 하는 방법은 아닙니다.
- **말한 것.** 돈을 환불하고 고객에게 금액을 절대 알리지 않는 실행은 완료된 것이 아닙니다.
  상태만 확인하면 이를 놓치고, 대본만 확인하면 "말했지만 하지 않은 것"을 놓칩니다.
- **거부권.** 안전 규칙 하나라도 실패하면 실행이 실패로 간주됩니다: 고객이 요청하지 않은 주문 환불, 비밀 출력, 외부인에게 우편 발송.
  다른 어떤 기준도 이를 만회하지 못합니다.

### 지표: 실행 k가 하는 일

하나의 실행은 판정을 제공합니다. 동일 과제를 여러 번 실행하면 중요한 숫자를 제공합니다:

- **Pass@k**: 최소한 하나의 k 실행이 성공했습니다. '할 수 있는가(can it)'라고 대답하며, 탐색적 작업에 적합한 지표입니다.
- **Pass^k**: 모든 k 실행이 성공했습니다. '신뢰할 수 있는가(is it reliable)'라고 대답하며, 회귀 게이트에 적합한 지표입니다.
- **Best@k**: 이진 판정이 아닌 등급화된 척도가 있는 개방형 작업에서 k 실행 중 최고 점수입니다.

두 지표는 빠르게 차이가 납니다. 단일 실행 성공률이 60%일 때, Pass@5는 약 99%이고 Pass^5는 약 8%입니다.
잘못된 지표를 보고하면 동전 던지기가 마치 배포된 기능처럼 보일 수 있습니다.

이와 함께 호출 로그가 이미 가지고 있는 프로세스 지표들이 있습니다: 합법적 호출 비율, 알려진 정상 기준 대비 단계, 재시도 횟수, 작업당 비용.
이 지표들은 성공한 실행이 비용 효율적으로 성공했는지, 아니면 무리하게 성공했는지를 알려줍니다.

### 개방형 작업 채점

상태 점검(state checks)은 확인 가능한 최종 상태가 있는 작업을 포함합니다. 서면 답변은 해시할 것이 없으므로 모델이 루브릭을 기준으로 채점합니다.
채점이 얼마나 잘 작동하는지는 루브릭 작성 방식에 달려 있습니다:

1. **전문가 기반.** 표면적인 유창성이 아니라 도메인 전문가가 확인하는 내용을 인코딩합니다.
2. **완전한 범위.** 정확성, 완전성, 안전성을 포함하며, 일반적인 실패는 암시하지 않고 명시적으로 명시합니다.
3. **가중치와 거부권.** 기준을 필수, 중요, 선택 사항으로 나누고, 거짓 사실과 같은 거부 항목은 점수를 0으로 만듭니다.
4. **자체 포함.** 각 항목은 평가자의 개인적인 의견 없이 확인 가능해야 합니다. "최소 두 개의 출처를 인용하고 각 출처가 결론을 어떻게 뒷받침하는지 설명"과 같은 항목이 이에 해당합니다.
   "깊은 이해를 보여준다"는 그렇지 않습니다.

판사는 모델이므로 모델의 실패가 있습니다. 더 긴 답변을 선호합니다. 처음 읽은 후보를 선호합니다.
에이전트와 같은 계열의 판사는 그 맹점을 공유하므로 에이전트가 저지르는 실수를 정확히 용서합니다.

완화 방법은 저렴합니다. 다른 계열의 판사를 사용하세요. 쌍을 두 번 채점하고 순서를 바꿔보세요.
판사를 대규모로 신뢰하기 전에 인간이 라벨링한 골드 세트와 비교하여 보정하고, 의견 불일치는 인간에게 보내세요.

### 데이터셋이 점수가 의미하는 바를 결정합니다

나쁜 데이터셋에서 실행되는 완벽한 환경은 잡음을 반환합니다. 네 가지 규칙이 벤치마크 전반에서 살아남습니다.

- **검증 가능함.** 답변이나 최종 상태는 사람이 읽지 않고도 확인할 수 있습니다.
- **계층화됨.** 쉬운, 중간, 어려운 과제가 분리되어 있어, 쉬운 과제에만 도움이 되는 변화가 평균에 숨겨지지 않습니다.
- **인간 확인.** 누군가 과제가 해결 가능하고 검사가 공정함을 확인합니다.
  원래의 과제가 명확하지 않거나 불공정한 테스트로 채점되었기 때문에 전체 벤치마크 하위 집합이 존재합니다.
- **오염 방어.** 공개 과제가 다음 훈련 세트에 도달합니다. 방어 방법: 각 과제 파일에 카나리아 문자열 포함, 답변 비공개,
  모델의 컷오프 이후 수집된 과제, 하나의 형식에서 새로운 인스턴스를 생성하는 파라미터화된 템플릿.

### 차이 읽기

두 빌드, 100개의 과제, 70퍼센트 대 73퍼센트. 그것은 결과가 아닙니다.

- **잡음 범위.** n개의 작업에 대한 비율의 표준 오차는 대략 `p(1-p)/n`의 제곱근 정도입니다.
  100개의 작업에서 70퍼센트일 경우 대략 4.6점 정도이므로, 3점 차이는 잡음 범위 안에 있습니다.
- **반복.** 샘플링과 도구 타이밍은 실행마다 점수를 변동시킵니다. 구성마다 3~5번 실행하고 단일 숫자가 아닌 범위를 보고하세요.
- **쌍 비교.** 두 빌드 모두 동일한 작업을 수행했으므로, 작업별로 비교하고 서로 다른 경우만 보세요.
  쌍 비교는 비교에서 작업 난이도를 제거하므로, 두 개의 독립적인 비율보다 훨씬 적은 샘플로 가능합니다.
- **가설을 계산하세요.** 95퍼센트 신뢰도로 여섯 가지 변경 사항을 테스트하면, 우연히 하나가 유의미해 보일 확률이 약 26퍼센트입니다.
  믿기 전에 기준을 강화하거나 우승자를 다시 실행하세요.

예상되는 개선이 당신의 테스트 스위트가 해결할 수 있는 범위보다 작다면, 다음 작업은 에이전트 튜닝이 아니라 스위트를 확장하는 것입니다.

### 보고서에서 변경으로

벤치마크 보고서는 다음 결정을 위한 입력입니다: 다음에 무엇을 변경할 것인가.

1. **먼저 harness를 의심하세요.** 종료된 프로세스, 버그 있는 그레이더, 또는 더 이상 프로덕션과 일치하지 않는 작업은 단지 성능이 떨어진 에이전트처럼 보입니다.
   에이전트를 만지기 전에 실패한 경로를 읽으세요.
2. **클러스터를 찾으세요.** 관련된 네 가지 작업 중 세 가지가 실패한 상태에서 전체 88%의 비율은 일반적인 약점이 아니라 하나의 부족한 기능입니다.
3. **하나의 변수를 변경하세요.** 모델, 시드, 작업 집합, 스텝 제한을 고정한 다음, 한 번에 한 가지씩만 변경하세요. 세 가지를 동시에 변경하는 라운드는 아무 것도 설명하지 못합니다.
4. **속성화.** 모델을 harness로 교체하여 모델이 얼마나 많은 것을 가지고 있는지 확인하세요. 모델을 고정한 상태에서 harness 구성 요소 하나를 비활성화하여 해당 구성 요소의 가치를 확인하세요.
   이 저장소의 논지는 두 숫자가 모두 존재한다는 것입니다.
5. **증거를 결정에 맞추세요.** 네 가지 작업은 더 큰 실행을 정당화할 수 있습니다. 그러나 배포를 정당화할 수는 없습니다.

제품 내부에서는 이것이 상시 인프라가 됩니다. 마스터 스위치는 기능을 비활성화하여 기본 모델 기준선을 얻습니다.
기능 플래그는 AB 테스트의 암(arm)을 운반하고 동시에 긴급 중지 스위치 역할을 합니다.
커밋별로 완전히 렌더링된 system prompt의 스냅샷은 프롬프트 편집이 eval 스위트를 다른 코드 변경처럼 실행하도록 합니다.

AB 테스트의 경우, 이동한 메커니즘 지표(계획 길이, 프롬프트 크기)를 관심 있는 목표 지표(작업 성공, 세션 비용)와 분리하세요.
목표 지표가 개선되더라도 실험을 중단시키는 guardrail 지표는 유지하세요.

### 통합 방식

Evaluation은 harness를 추가하는 대신 재사용합니다:

- 환경의 도구 인터페이스는 섹션 2의 레지스트리이며, 핸들러는 실제 세계 대신 eval 상태를 가리킵니다.
- 테스트 중인 에이전트는 수정되지 않은 섹션 1 루프입니다. 루프 내에는 평가를 받고 있다는 사실을 아는 것이 없습니다.
- 판사는 섹션 21의 확인자입니다: 별도의 에이전트, 새로운 맥락, 만족할 수는 있지만 다시 쓸 수 없는 고정된 평가 척도입니다.
- 섹션 20은 입력을 제공합니다. 세정된 생산 흔적은 새로운 작업이 되며, 그 비용 추적기는 작업당 비용을 제공합니다.
- 개선 루프는 증거가 첨부된 섹션 21의 외부 루프입니다: 측정, 한 가지 변경, 다시 측정.

각 시스템이 테스트 베드를 구축하는 방식은 점수가 어디서 오는지를 보여줍니다.

## 실패 모드

- **세계를 평가하는 대신 기록을 평가.** '환불됨'이라고 말하는 에이전트는 실제로 환불한 에이전트와 동일하게 점수.
  완화: 최종 상태 확인 및 에이전트가 전달해야 했던 사항을 별도로 검증.
- **오염된 작업.** 공개 벤치마크가 다음 학습 세트에 포함되어 높은 점수가 능력이 아닌 회상일 수 있음.
  완화: 작업 파일의 카나리아 문자열, 보류된 답변, 컷오프 이후 수집된 작업, 매개변수화된 템플릿.
- **결과로 나타난 읽기 잡음.** 각 100개의 작업에서 한 번씩 수행한 실행에서 3점 차이는 아무것도 결정하지 않는다.
  완화: 반복 실행, 작업별로 쌍 비교, 잡음 범위 내의 차이는 무시, 여러 변경을 동시에 테스트할 때 임계값 강화.
- ** harness가 깨졌다고 에이전트를 탓함.** 굶주린 러너, 버그 있는 채점기, 혹은 오래된 작업은 품질 저하처럼 보인다.
  완화: 에이전트를 변경하기 전에 실패한 경로를 읽는다.
- **에이전트의 맹점을 공유하는 심사관.** 동일 계열의 심사관은 에이전트가 저지른 오류를 용서하고, 더 긴 답변을 선호하며, 먼저 온 후보를 선호한다.
  완화: 서로 다른 가족의 판사를 사용하고, 순서를 바꾸어 두 번 채점하며, 인간이 라벨링한 골드 세트와 비교하여 보정.
- **보상 해킹.** 에이전트가 작업을 건너뛰고 점수를 얻는 방법을 찾음: 키워드 채우기, 판사 아첨, 어려운 사례 거부.
  완화: 평가 기준에서 항목 거부, 결과 지표 외에 과정 지표 사용, 주기적인 인간 샘플 점검.
- **변화를 볼 수 없는 스위트.** 40개 작업에서 2점 향상은 측정할 수 없어서, 모든 라운드가 결정되지 않은 것으로 나타남.
  완화: 추가로 반복하기 전 작업 세트를 확장.
- **실행 간 상태 누출.** 리셋이 없거나 얕게 되어 있어, 한 작업의 출력이 다음 작업의 점수를 결정.
  완화: 에피소드별로 깊은 복사 수행, 실행당 하나의 격리된 환경 (섹션 15).

## 실행 가능

[`src/`](src/)은 22를 전달하고 다음을 추가합니다:

- [`evaluation.py`](src/evaluation.py): `reset`와 기록된 도구 인터페이스를 가진 환경, 턴마다 하나의 사실을 공개하는 시뮬레이션 사용자인, 에피소드 프로토콜,
  채점(상태 확인, 말한 내용, 거부), Pass@k 및 Pass^k, 이항 잡음 밴드, 그리고 두 빌드의 짝 비교.
- [`test.py`](src/test.py): 상태 복원을 위한 오프라인 확인, 에이전트가 주문 번호를 요청해야 하는 프로토콜 실행,
  결과 확인이 통과한 실행을 실패시키는 안전 거부, 불안정한 빌드에서의 Pass@k 대 Pass^k,
  그리고 쌍 비교에서 점수가 낮게 나온 회귀된 빌드는 무엇이 고장났는지 명명합니다.
- [`demo.py`](src/demo.py): 하나의 평가된 에피소드. 모델은 지원 에이전트를 수행하며, 그 도구 호출이 환경에 도달하고,
  harness는 그가 남긴 상태를 점수화합니다.

루프는 변경되지 않았습니다. 점수가 의미 있게 되는 것은 환경입니다.

```bash
python sections/23-evaluation/src/test.py         # offline checks, no key
uv run python sections/23-evaluation/src/demo.py  # live demo, needs a key
```
