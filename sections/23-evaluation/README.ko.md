# 23 · Evaluation

[English](README.md) · [繁體中文](README.zh-TW.md) · [简体中文](README.zh-CN.md) · [日本語](README.ja.md) · **한국어**

> 통과율은 그 뒤에 있는 환경만큼의 가치밖에 없습니다.

섹션 20은 프로덕션을 지켜봅니다. 무슨 일이 있었는지는 말하지만, 그것이 좋았는지는 말하지 않습니다. 이 섹션은 나머지 질문에 답합니다: 이 변경이 agent를 더 낫게 만들었는가.

모델 호출 하나라면 그 질문은 쉽습니다. prompt를 보내고, 답을 기준 답과 비교하고, 셉니다.

agent는 그 모든 부분을 깨뜨립니다. 여러 turn을 실행합니다. task에 적혀 있지 않은 정보를 사용자에게 물어봅니다. 저장된 데이터를 바꾸는 tool을 호출합니다.
같은 결과에 서로 다른 경로로 도달합니다. 같은 빌드로 같은 task를 두 번 실행해도 결과가 갈릴 수 있습니다.

그래서 agent 점수에는 prompt 목록이 아니라 시험대가 필요합니다: 리셋되는 상태, 사용자를 대신하는 것, 대화를 한 걸음씩 진행시키는 protocol,
그리고 실행이 남긴 세계를 채점하는 rubric.

이것을 건너뛰어도 숫자는 나옵니다. 다만 아무 의미가 없을 뿐입니다. task가 학습 데이터로 새어 들어간 스위트. 표본 잡음일 뿐인 3점 차이.
점수는 잘 나오면서 고객이 말한 적 없는 주문을 환불해 주는 빌드.

---

## 메커니즘

![Mechanism diagram](assets/23-evaluation.png)

평가 환경은 다섯 부분으로 이루어집니다. 넷은 데이터이고, 하나는 제어 흐름입니다.

- **데이터셋.** task 레코드입니다. 각 레코드는 시작 상태, 사용자가 원하는 것, 그리고 실행을 어떻게 검사하는지를 담습니다.
- **환경 상태.** task가 거기서 시작해 거기서 끝나는, 바뀔 수 있는 데이터입니다: 주문, 파일, 데이터베이스.
  의미가 있을 만큼 현실적이어야 하고, 리셋할 수 있을 만큼 통제되어야 합니다.
- **tool.** agent가 실행해도 되는 연산입니다. "고객의 문제를 해결한다"는 tool 하나가 아니라,
  원자적인 단위로 유지합니다(주문 읽기, 주문 환불).
- **rubric.** 끝난 실행이 점수로 바뀌는 방식입니다.
- **상호작용 protocol.** 누가 언제 말하는지, 그리고 에피소드가 언제 끝나는지입니다.

섹션 20의 eval은 `(input, grade)` 쌍을 받았습니다: 문자열 하나가 들어가고, 문자열 하나가 나오고, 통과율 하나가 나옵니다. 이 섹션은 그 진입점을 그대로 두고 그 아래에 환경을 놓습니다.

### 새로 추가: 환경과 그 리셋

환경이 상태를 쥐고, 그것을 바꾸는 유일한 통로를 소유합니다:

```python
def reset(self):                                       # src/evaluation.py
    self.state = deepcopy(self.initial)                # a fresh copy per episode
    self.calls = []

def call(self, name, **args):
    tool = self.tools.get(name)
    if tool is None:
        self.calls.append((name, False))               # illegal: no such tool
        return f"error: no tool named {name}"
    try:
        out = tool(self.state, **args)
    except Exception as e:                             # illegal: wrong arguments
        self.calls.append((name, False))
        return f"error: {type(e).__name__}: {e}"
    self.calls.append((name, True))
    return str(out)
```

- `reset`은 시작 스냅샷을 깊은 복사하므로, 두 번째 에피소드가 첫 번째 에피소드의 쓰기를 절대 보지 않습니다.
  이것이 없으면 환불 task의 두 번째 실행은 이미 환불된 주문에서 시작합니다.
- 거절된 호출은 맨 실패 플래그가 아니라 이유를 말하는 메시지를 돌려줍니다. 거기서 회복하는 것도 시험 대상 행동의 일부입니다.
- 모든 호출은 그것이 적법했는지와 함께 기록됩니다. 그 로그가 과정 지표이고, 부적법 호출 수와 단계 수는 결과 검사가 통과할 때에도 볼 수 있습니다.

### 새로 추가: 모의 사용자와 protocol

대부분의 benchmark는 첫 메시지에서 agent에게 요청 전체를 건넵니다. 실제 사용자는 그러지 않습니다.
"주문에 뭔가 문제가 있어요"로 말을 꺼내고, 나머지는 물어보면 줍니다.

그래서 모의 사용자는 스크립트를 쥐고 turn마다 사실 하나씩만 내놓습니다. 그래서 묻는 일 자체가 채점되는 능력이 됩니다:

```python
def run_episode(env, task, agent, max_turns=8):        # src/evaluation.py
    env.reset()
    user = task["user"]()                              # a fresh simulated user per episode
    transcript, said = [], user()
    for _ in range(max_turns):                         # the ceiling: an episode always terminates
        if said is None:
            break
        reply = agent(said, env)
        transcript.append((said, reply))
        said = user(reply)
    return {"transcript": transcript, "state": env.state, "calls": list(env.calls)}
```

실행 가능한 코드는 오프라인 검사가 결정적으로 유지되도록 고정된 스크립트를 씁니다. 실제 버전은 같은 스크립트를 받은 LLM입니다.
LLM은 배역에 맞게 답하고, 지금 단계에 필요한 것만 내놓고, 아무것도 지어내지 말라는 지시를 받습니다. 표현은 달라져도 공개 순서는 달라지지 않습니다.

더 강한 버전은 모의 사용자에게 같은 상태를 다루는 자기 tool을 줍니다. 그러면 agent는 다른 사람을 설득해 움직이게 해야 하고, 그것이 실제 고객 지원 통화의 모습입니다.
또한 사용자가 agent가 알아차려야 할 것을 바꿀 수 있다는 뜻이므로, 상태는 더 이상 agent의 사설 sandbox가 아니게 됩니다.

### 새로 추가: 에피소드 하나 채점하기

검사는 셋이고, 순서가 있습니다:

```python
def grade(task, run):                                  # src/evaluation.py
    checks = {name: bool(fn(run["state"])) for name, fn in task["checks"]}       # the outcome
    said = " ".join(reply for _, reply in run["transcript"]).lower()
    told = {s: s.lower() in said for s in task.get("must_say", [])}              # what was communicated
    unsafe = [name for name, fn in task.get("veto", []) if fn(run)]              # zero tolerance
    return {"passed": all(checks.values()) and all(told.values()) and not unsafe, ...}
```

- **경로가 아니라 결과.** 검사는 최종 상태를 읽으므로, 거기에 도달하는 어떤 경로든 통과합니다. 참조 해답은 task를 푸는 한 가지 방법이지 요구되는 방법이 아닙니다.
- **무엇을 말했는지.** 돈을 환불하고도 고객에게 금액을 말해 주지 않은 실행은 끝난 것이 아닙니다.
  상태만 검사하면 그것을 놓치고, transcript만 검사하면 "했다고 말했지만 하지 않은" 경우를 놓칩니다.
- **거부권.** 안전 항목에 하나라도 걸리면 다른 점수가 어떻든 실행은 실패합니다: 고객이 말한 적 없는 주문을 환불하거나, 비밀을 출력하거나, 외부인에게 메일을 보내는 것.
  다른 어떤 차원으로도 되살 수 없습니다.

### 지표: k번 실행하는 이유

실행 한 번은 판정 하나를 줍니다. 같은 task를 여러 번 실행하면 정말 중요한 숫자가 나옵니다:

- **Pass@k**: k번 실행 중 최소 한 번이 통과. "할 수 있는가"에 답하며, 탐색적 task에 맞는 지표입니다.
- **Pass^k**: k번 실행이 모두 통과. "믿을 수 있는가"에 답하며, 회귀 게이트에 맞는 지표입니다.
- **Best@k**: k번 실행 중 가장 좋은 점수이며, 이분법 판정이 아니라 등급 척도가 있는 열린 task에 씁니다.

둘은 빠르게 벌어집니다. 단일 실행 성공률이 60퍼센트일 때 Pass@5는 약 99퍼센트이고 Pass^5는 약 8퍼센트입니다.
잘못된 쪽을 보고하면 동전 던지기가 출시된 기능처럼 보입니다.

그 옆에는 호출 로그가 이미 담고 있는 과정 지표가 있습니다: 적법 호출 비율, 알려진 정상 기준선 대비 단계 수, 재시도 횟수, task별 비용.
통과한 실행이 싸게 통과했는지 힘으로 밀어붙여 통과했는지는 그것들이 알려 줍니다.

### 열린 작업 채점하기

상태 검사는 최종 상태를 검사할 수 있는 task를 다룹니다. 글로 쓴 답에는 해시할 것이 없으므로, 모델이 rubric에 비추어 채점합니다.
채점이 얼마나 잘 되는지는 rubric을 어떻게 썼는지로 갈립니다:

1. **전문가에 근거함.** 표면적인 유창함이 아니라 그 분야 전문가가 검사하는 것을 담습니다.
2. **빠짐없이 다룸.** 정확성, 완전성, 안전성을 다루고, 흔한 실패는 암시하지 말고 명시적으로 이름을 붙입니다.
3. **가중치와 거부권.** 기준을 필수, 중요, 선택으로 나누고, 사실 날조 같은 거부 항목은 점수를 0으로 만듭니다.
4. **자체 완결적.** 각 항목은 판정기 자신의 의견 없이 검사할 수 있어야 합니다. "출처를 최소 두 개 인용하고 각각이 결론을 어떻게 뒷받침하는지 설명한다"는 됩니다.
   "깊은 이해를 보여 준다"는 안 됩니다.

판정기도 모델이므로 모델의 실패를 그대로 갖습니다. 더 긴 답을 선호합니다. 먼저 읽은 후보를 편듭니다.
agent와 같은 모델 계열의 판정기는 agent의 맹점을 공유하므로, agent가 저지르는 바로 그 오류를 봐줍니다.

완화책은 쌉니다. 서로 다른 계열의 판정기를 씁니다. 쌍은 순서를 바꿔 두 번 채점합니다.
대규모로 믿기 전에 사람이 라벨을 붙인 골드 세트로 판정기를 보정하고, 의견이 갈리는 건은 사람에게 넘깁니다.

[EvalGrill](https://github.com/hardness1020/EvalGrill)은 이 흐름을 도구로 묶은 것입니다. agent를 실제로 쓴 사례에서 eval을 만들고, 판정기를 보정한 뒤에 믿습니다.

### 점수의 의미는 데이터셋이 정합니다

완벽한 환경이라도 나쁜 데이터셋을 돌리면 잡음이 나옵니다. benchmark를 가로질러 살아남은 규칙이 넷 있습니다.

- **검증 가능함.** 답이나 최종 상태를 사람이 읽지 않고도 검사할 수 있습니다.
- **난이도 구분.** 쉬움, 보통, 어려움 task를 분리해서, 쉬운 task에만 도움이 되는 변경이 평균 뒤에 숨지 못하게 합니다.
- **사람이 확인함.** 누군가 그 task가 풀 수 있는 것인지, 그 검사가 공정한지 확인합니다.
  원래 task의 명세가 부실했거나 불공정한 테스트로 채점되었다는 이유로 benchmark의 부분 집합이 통째로 만들어진 사례들이 있습니다.
- **오염 방어.** 공개된 task는 다음 학습 데이터로 들어갑니다. 방어책: 모든 task 파일에 넣는 카나리 문자열, 정답 비공개,
  모델의 cutoff 이후에 수집한 task, 그리고 하나의 형태에서 새 인스턴스를 만들어 내는 매개변수화된 템플릿.

### 차이를 읽는 법

빌드 둘, task 100개, 70퍼센트 대 73퍼센트. 그것은 결과가 아닙니다.

- **잡음 구간.** n개 task에 대한 비율의 표준오차는 대략 `p(1-p)/n`의 제곱근입니다.
  task 100개에서 70퍼센트라면 대략 4.6점이므로, 3점 차이는 잡음 안에 들어갑니다.
- **반복.** 샘플링과 tool 타이밍 때문에 점수는 실행마다 움직입니다. 설정마다 3회에서 5회 실행하고, 숫자 하나가 아니라 퍼짐을 보고합니다.
- **짝짓기.** 두 빌드가 같은 task를 돌았으므로, task별로 비교하고 결과가 갈린 곳만 봅니다.
  짝짓기는 비교에서 task 난이도를 걷어 내므로, 독립된 두 비율보다 훨씬 적은 표본으로 충분합니다.
- **가설 수를 셈.** 95퍼센트 신뢰도로 여섯 가지 변경을 시험하면, 그중 하나가 운으로 유의해 보일 확률이 약 26퍼센트입니다.
  기준을 더 조이거나, 믿기 전에 이긴 쪽을 다시 실행합니다.

기대하는 개선폭이 스위트가 분간할 수 있는 구간보다 작다면, 다음에 할 일은 agent를 손보는 것이 아니라 스위트를 키우는 것입니다.

### 보고서에서 변경으로

benchmark 보고서는 단 하나의 결정을 위한 입력입니다: 다음에 무엇을 바꿀 것인가.

1. **harness를 먼저 의심합니다.** 죽은 프로세스, 버그 있는 채점기, 더 이상 프로덕션과 맞지 않는 task는 agent가 나빠진 것과 똑같아 보입니다.
   agent를 건드리기 전에 실패한 trajectory를 읽습니다.
2. **뭉친 곳을 찾습니다.** 전체 88퍼센트인데 관련된 task 넷 중 셋이 실패했다면, 그것은 전반적인 약점이 아니라 빠진 능력 하나입니다.
3. **한 번에 한 변수만 바꿉니다.** 모델, 시드, task 세트, 단계 제한을 고정하고 라운드마다 하나만 바꿉니다. 세 가지를 한꺼번에 바꾼 라운드는 아무것도 설명하지 못합니다.
4. **귀속시킵니다.** harness를 고정한 채 모델을 바꿔서 모델이 얼마나 떠받치는지 봅니다. 모델을 고정한 채 harness 구성 요소 하나를 꺼서 그 구성 요소의 값어치를 봅니다.
   이 저장소의 주제는 그 두 숫자가 모두 존재한다는 것입니다.
5. **근거를 결정의 크기에 맞춥니다.** task 넷은 더 큰 실행을 정당화할 수 있습니다. 배포를 정당화할 수는 없습니다.

제품 안에서 이것은 상시 인프라가 됩니다. 마스터 스위치가 기능들을 꺼서 맨 모델 기준선을 얻습니다.
기능 플래그가 AB 테스트의 각 갈래를 담고, 동시에 킬 스위치 역할도 합니다.
커밋마다 완전히 렌더링된 system prompt의 스냅샷을 남겨 두면, prompt 수정도 다른 코드 변경과 똑같이 eval 스위트를 돌릴 수 있습니다.

AB 테스트에서는 직접 움직인 메커니즘 지표(계획 길이, prompt 크기)와 실제로 신경 쓰는 목표 지표(task 성공, session 비용)를 구분합니다.
목표 지표가 좋아지더라도 실험을 멈추게 하는 가드레일 지표를 함께 둡니다.

### 통합 방식

평가는 harness에 무언가를 더하기보다 그것을 재사용합니다:

- 환경의 tool 인터페이스는 섹션 2의 registry이고, 핸들러가 실제 세계 대신 eval 상태를 가리킵니다.
- 시험 대상 agent는 섹션 1의 loop 그대로입니다. loop 안의 어떤 것도 자기가 평가받는 중이라는 것을 모릅니다.
- 판정기는 섹션 21의 검사기입니다: 별도의 agent, 새 context, 그리고 만족시킬 수는 있어도 다시 쓸 수는 없는 고정된 rubric.
- 섹션 20이 입력을 공급합니다. 마스킹된 프로덕션 trace가 새 task가 되고, 섹션 20의 비용 추적기가 task별 비용을 줍니다.
- 개선 loop는 근거가 붙은 섹션 21의 바깥 loop입니다: 측정하고, 하나를 바꾸고, 다시 측정합니다.

각 시스템이 점수가 나오는 시험대를 만드는 방식입니다.

## 실패 모드

- **세계가 아니라 transcript를 채점함.** "환불했습니다"라고 말한 agent가 실제로 환불한 agent와 같은 점수를 받습니다.
  완화: 최종 상태를 검사하고, agent가 반드시 전달해야 했던 내용은 별도의 검사로 둡니다.
- **오염된 task.** 공개된 benchmark는 다음 학습 데이터로 들어가므로, 높은 점수가 능력이 아니라 recall일 수 있습니다.
  완화: task 파일의 카나리 문자열, 정답 비공개, cutoff 이후에 수집한 task, 매개변수화된 템플릿.
- **잡음을 결과로 읽음.** task 100개에서 각각 한 번씩 실행해 나온 3점 차이는 아무것도 결정하지 못합니다.
  완화: 반복 실행, task별 짝지은 비교, 잡음 구간 안의 차이는 무시, 여러 변경을 한꺼번에 시험할 때는 기준을 더 조이기.
- **망가진 harness를 두고 agent를 탓함.** 리소스 부족인 실행기, 버그 있는 채점기, 오래된 task는 품질 하락과 똑같아 보입니다.
  완화: agent를 바꾸기 전에 실패한 trajectory를 읽습니다.
- **agent와 맹점을 공유하는 판정기.** 같은 계열의 판정기는 agent가 저지르는 오류를 봐주고, 더 긴 답을 선호하고, 먼저 온 후보를 편듭니다.
  완화: 서로 다른 계열의 판정기, 순서를 바꿔 두 번 채점하기, 사람이 라벨을 붙인 골드 세트로 보정하기.
- **보상 해킹.** agent가 일을 건너뛰고 점수로 가는 지름길을 찾습니다: 키워드 채우기, 판정기 비위 맞추기, 어려운 사례 거절하기.
  완화: rubric의 거부 항목, 결과 지표 옆에 두는 과정 지표, 그리고 주기적인 사람의 표본 검사.
- **변화를 볼 수 없는 스위트.** task 40개에서 2점 개선은 측정할 수 없으므로, 모든 라운드가 결론 없음으로 읽힙니다.
  완화: 더 반복하기 전에 task 세트를 키웁니다.
- **실행 사이로 새는 상태.** 리셋이 없거나 얕아서, 한 task의 쓰기가 다음 task의 점수를 좌우합니다.
  완화: 에피소드마다 깊은 복사, 그리고 실행마다 격리된 환경 하나(섹션 15).

## 실행 방법

[`src/`](src/)는 22를 이어받고 다음을 추가합니다:

- [`evaluation.py`](src/evaluation.py): `reset`과 로그가 남는 tool 인터페이스를 갖춘 환경, turn마다 사실 하나씩 내놓는 모의 사용자, 에피소드 protocol,
  채점(상태 검사, 무엇을 말했는지, 거부권), Pass@k와 Pass^k, 이항 잡음 구간, 그리고 두 빌드의 짝지은 비교.
- [`test.py`](src/test.py): 상태를 되돌리는 리셋, agent가 주문 번호를 물어봐야 하는 protocol 실행,
  결과 검사는 통과했지만 안전 거부권으로 실패하는 실행, 불안정한 빌드에서의 Pass@k 대 Pass^k,
  그리고 짝지은 비교가 무엇이 깨졌는지 짚어 내며 회귀한 빌드에 더 낮은 점수를 주는 것에 대한 오프라인 검사.
- [`demo.py`](src/demo.py): 채점되는 에피소드 하나. 모델이 고객 지원 담당자를 연기하고, 그 tool 호출이 환경에 반영되며,
  harness가 그것이 남긴 상태를 채점합니다.

loop는 바뀌지 않습니다. 점수에 의미를 부여하는 것은 환경입니다.

```bash
python sections/23-evaluation/src/test.py         # offline checks, no key
uv run python sections/23-evaluation/src/demo.py  # live demo, needs a key
```

## 출처

- [ai-agent-book · chapter 6](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter6.md) (《深入理解 AI Agent》, 李博杰. 중국어 원문이 기준):
  평가 환경의 다섯 요소, 정보를 점진적으로 공개하기, 지표 사전, rubric 기준,
  통계적 유의성, benchmark에서 개선으로 이어지는 loop, 그리고 내부 eval 인프라.
- [τ-bench](https://arxiv.org/abs/2406.12045) (Sierra): 언어 모델이 연기하는 사용자, 최종 데이터베이스 상태를 주석된 목표 상태와 대조해 판정하는 성공 여부,
  그리고 신뢰도를 재는 Pass^k.
- [τ²-bench](https://arxiv.org/abs/2506.07982)와 [그 소스](https://github.com/sierra-research/tau2-bench): 모의 사용자도 tool을 쥐는 이중 제어 환경,
  그리고 서로 곱해지는 보상 요소들(골드 재생과 대조해 해시한 데이터베이스 상태, 반드시 나와야 하는 문구,
  선택적인 LLM 판정 항목).
- [Verifiers](https://github.com/willccbb/verifiers): agent 사이의 제어 흐름으로서의 환경, id로 불러오는 task 세트, task별 rollout,
  빠졌거나 오류가 난 rollout의 재개, 그리고 실행 산출물에 코드를 돌려 보는 판정기 agent.
- [mini-swe-agent source](https://github.com/swe-agent/mini-swe-agent): `run/benchmarks/swebench.py`, 인스턴스마다 컨테이너 이미지 하나,
  인스턴스별 trajectory와 예측 기록.
- [SWE-bench Verified](https://huggingface.co/datasets/princeton-nlp/SWE-bench_Verified): 사람이 검증한 인스턴스 500개이며,
  새로 통과해야 하는 테스트와 계속 통과해야 하는 테스트로 채점합니다.
- [GAIA](https://arxiv.org/abs/2311.12983): 질문 466개이고 그중 300개는 정답을 공개하지 않아서, 리더보드를 긁어낼 수 없습니다.
- [BIG-bench](https://github.com/google/BIG-bench): benchmark task가 웹 스크래핑 학습 데이터에 들어가지 않도록 모든 task 파일에 넣는 카나리 문자열.
- [Rubrics as Rewards](https://arxiv.org/abs/2507.17746) (Scale AI): 반드시 포함할 사실, 반드시 거칠 추론 단계, 반드시 감점할 함정을 적어 둔 체크리스트 rubric.
- [Claude Code](https://code.claude.com/docs): workflow 계약에 있는 검토자 단계와 판정기 단계이며, 소스 백업이 아니라 tool 스키마와 문서화된 동작에서 가져왔습니다.
  평가 스위트는 소스에 없으므로, 해당 칸들은 재구성으로 표시했습니다.
