# 14 · Scheduling

[English](README.md) · [繁體中文](README.zh-TW.md) · [简体中文](README.zh-CN.md) · **日本語** · [한국어](README.ko.md)

> エージェントの開始は、ユーザー入力だけでなく、時計からも開始されます。

バックグラウンド作業を開始するには、依然として誰かまたは何かが必要です。レポート、リマインダー、投票タスクなど、多くのタスクは後で実行するか、繰り返す必要があります。

スケジュールには将来のトリガーが保存されます。起動すると、プロンプトがキューに入れられます。通常のループは、そのプロンプトを新しいターンとして処理します。

スケジュール設定では次のことを行う必要があります。

1. スケジュールを 1 ターン外に保存します。
2. ループとは独立して時間を監視します。
3. スケジュールが起動したら、プロンプトをキューに入れます。
4. オプションで、再起動後もスケジュールを保持します。

この層がないと、エージェントはユーザー入力にのみ反応できます。

## メカニズム

![機構図](assets/14-scheduling.png)

クロックをループから分離します。スケジューラは時間を監視します。モデルを直接呼び出すわけではありません。

起動時に、スケジューラはプロンプトのみをキューに入れます。運転手は、ターンの合間に、飛行中のターンがないときにキューを空にします。
そして、ユーザー入力を処理する同じ agent loop を通じて各プロンプトを実行します。

- スケジュールはデータです。つまり、実行するプロンプト、起動時間、およびオプションの繰り返し間隔です。スケジューラはそれぞれをタスクとして保存します。
- ワンショットは 1 回発射され、その後それ自体を削除します。
- 定期的なスケジュールは次の間隔に再準備されます。
- 永続的なスケジュールは再起動後も存続しますが、ホストがオフの間は起動されません。
- ハートビートは、質問を行う定期的なスケジュールです。起動してソースをチェックし、通常は何も言うことがないと判断します。

### 新機能: スケジューラとファイアキュー

`tick` は期限が切れたタスクをチェックします。起動とは、プロンプトをキューに入れることを意味します。

```python
def tick(self):                                       # src/scheduler.py; called by a daemon thread
    now = self._clock()
    for tid, t in list(self._tasks.items()):
        if now >= t["due"]:
            self._pending.put({"prompt": t["prompt"], "channel": t.get("channel")})
            if t["every"]:                            # enqueue, do not run the model here
                t["due"] = now + t["every"]
            else:
                self._tasks.pop(tid, None)
    self._save()                                      # durable tasks only
```

- クロックは注入可能であるため、テストでは偽のクロックが使用されます。
- `run()` は、デーモン スレッドで `tick` を呼び出します。
- `_save` は、耐久タスクを JSON に永続化します。
- 同じパス上の新しい `Scheduler` は永続タスクをリロードし、ID を再開します。

### 新機能: 答えを提供する

発射されたランには待っている人はいないため、答えを得るには出口が必要です。各タスクはチャネルに名前を付けることができます。
チャネルはタスクのフィールドです。`create(..., channel="console")` はそれを保存し、`tick` はそれをプロンプトとともにキューに入れます。
排出された各アイテムはすでに `{"prompt": ..., "channel": ...}` であるため、ドライバーは答えがどこにあるかを検索することはありません。

`deliver` はターンの回答をルーティングします (Hermes は cron 出力をジョブのチャット プラットフォームに配信します)。

```python
SILENT = "[SILENT]"                              # a fired run may decide nothing is worth sending

def deliver(channels, fired, text) -> bool:      # src/scheduler.py
    if not fired.get("channel") or text.lstrip().startswith(SILENT):
        return False
    channels[fired["channel"]](text)
    return True
```

- `channels` は、チャネル名を送信呼び出し可能にマップします (ここに印刷します。実際のアダプターはセクション 19 の仕事です)。
  タスクはチャネルに名前を付けます。運転手は地図を所有しています。どちらも相手の詳細を知りません。
- アンサーが `[SILENT]` で始まる場合、`deliver` はチャネル送信をスキップします。これは、ユーザーに伝える価値のあるものが何も見つからなかったスケジュールされたチェックの規則です。
  （世論調査では変化は見られませんでした）。ドライバーは依然としてフルテキストを保持しており、ログに記録できます。
- チャネルがないことは、応答がローカルに留まり、配信前の動作を意味します。
- `bool` リターンにより、ドライバーは応答をサイレントに失うのではなく、フォールバック (デモでは未配信の応答が出力されます) できます。

### ハートビート

一部の情報源は決してプッシュしません。 Webhook のないメールボックス、フィードのないページ、求められた場合にのみ応答するサービス。
これらの場合、残された唯一のトリガーは時計です。パターンはハートビートです。つまり、プロンプトがエージェントに行動するのではなく見るように指示する定期的なスケジュールです。
ソースを確認し、メッセージに値するほどの変更があったかどうかを判断し、それ以外は何も言いません。

報告する価値のあるものが何も見つからないハートビートの実行では、`[SILENT]` が返されます。上記のルールにより、`deliver` は何も送信しません。
ティックには 1 つのモデル呼び出しがかかり、メッセージは発生しないため、チャネルをあふれさせることなくスケジュールを頻繁に実行できます。

ここでは、ハートビートと cron エントリは、プロンプト、繰り返し間隔、およびチャネルという同じ部分を使用します。プロンプトのみが異なります。
cron プロンプトが命令を出します。ハートビートプロンプトは質問をします。

### 統合方法

スケジュールは2分割です。 `tick` は独自のデーモン スレッドで実行されます (セクション 13 の background execution)。モデルには決して触れず、火をキューに入れるだけです。

```python
def run(self):                                        # src/scheduler.py; started by sched.run()
    def loop():
        while not self._stop.wait(self.CHECK_INTERVAL):   # wakes once per second
            self.tick()
    threading.Thread(target=loop, daemon=True).start()    # daemon: never keeps the process alive
```

ターン自体はフォアグラウンドで実行されます。ドライバーはターンの間にキューを排出し、起動されたタスクごとに `run_turn` を呼び出します。

```python
for task in sched.drain():                            # src/demo.py · between turns
    messages = [{"role": "user", "content": task["prompt"]}]
    deliver(channels, task, run_turn(messages, model, reg, session))
```

起動されたプロンプトは、新しいユーザー スタイルのターンになります。同じループ、権限、hooks、メモリ、context management、および回復パスを使用します。その回答はタスクのチャネルにルーティングされます。

### さらに読む

これは `src/` にはありません。これは ai-agent-book からのものであり、表内のシステムについては確認されていません。

**時計の限界** ハートビートには、間隔という重要な設定が 1 つあります。
それは法案と最悪の場合の遅延を同時に設定し、これら 2 つが互いに引っ張り合います。
短い間隔でモデルが頻繁に起動されますが、ほとんどの場合は何も見つかりません。間隔が長いと安くて遅いです。
これを修正するには間隔を設けません。クロックはイベントを監視するのではなく状態をサンプリングするため、物事がいつ起こったかではなく、最後に見たのがいつであるかを認識します。

**入手可能な場合はプッシュを優先してください。** ソースがエージェントを呼び出すことができる場合、イベントが発生するとトリガーが起動され、ポーリング コストがゼロに下がります。
したがって、ソースがサポートしている場合はプッシュ、サポートしていない場合はハートビート、月曜日のレポートなど実際に時間ベースの作業の場合は cron という順序になります。
セクション 19 では、インバウンドプッシュ側について説明します。

## 障害モード

- **ダブルファイア。** 高速ティックは、同じ cron 分に複数回一致する可能性があります。最後の発射時間を追跡します。
- **多くのスケジュールが同時に実行されます。** 定期的なタスクに決定的なジッターが追加されます。
- **耐久性とは、常時オンを意味します。** ローカルの耐久性スケジュールは再起動のみで存続します。オフライン起動にはリモート トリガーまたは OS タイマーを使用します。
- **不正な cron 式。** 作成時に検証し、ロードされた無効なエントリをスキップします。
- **ループがビジーです。** プロンプトをキューに入れ、ターンの間にプロンプトを排出します。
- **疲労を警告します。** ティックごとに報告するハートビートは、ユーザーにそれを無視するよう教えます。何を送信する価値があるかをプロンプトに判断させ、そうでない場合は沈黙を保ちます。
- **ティック間のイベント。** クロックは状態をサンプリングします。 2 ティック間で現れたり元に戻ったりする変化は目に見えません。ログやカーソルを読み込んだり、プッシュするソースを移動したりします。

## 実行可能

[`src/`](src/) 13 を前方に繰り上げて次を追加します。

- [`scheduler.py`](src/scheduler.py): スケジューラ、ファイアキュー、定期的な再準備、ワンショット削除、耐久性のある JSON ストア、およびチャネル配信 (`deliver`、`SILENT`)。
- [`test.py`](src/test.py): 偽の時計を使用して、ワンショット、繰り返し、リロード、および配信の動作をテストします。
- [`demo.py`](src/demo.py): プロンプトを 1 秒後にスケジュールし、新しいターンとして実行し、回答をコンソール チャネルに配信します。

ループは変更されません。スケジューリングはその外側からターンを開始します。

```bash
python sections/14-scheduling/src/test.py         # offline checks, no key
uv run python sections/14-scheduling/src/demo.py  # live demo, needs a key
```
