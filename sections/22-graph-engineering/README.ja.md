# 22 · Graph engineering

[English](README.md) · [繁體中文](README.zh-TW.md) · [简体中文](README.zh-CN.md) · **日本語** · [한국어](README.ko.md)

> モデルに次に何を実行するかを尋ねるのをやめる。すでに知っているルートをエンコードし、判断が必要な場合にのみモデルを使用する。

セクション21は、1つのエージェントの周りにループを重ねている。このセクションは、モデル呼び出しの間の作業を形作る。

多くのタスクには、モデルを呼び出す前に知っている構造がある：チケットを行動する前に分類する、コミットする前に差分を確認する、外部の何かを行う前に承認を得る。
単純なagent loopは、毎回モデルに次に何をするかを尋ねることで、その構造を再発見する。モデル駆動型ルーティングは遅く、トークンを消費し、実行ごとに変わる。

Graph engineeringは、既知の構造をコード内の有向グラフとしてエンコードする：

1. ノードが作業を行う。ノードは単純なコード、1回のモデル呼び出し、または完全なエージェント実行のいずれかである。
2. エッジは次のノードを選択します。harness はモデル呼び出しではなく、コードでそれらを評価します。
3. サイクルは許可されています。リトライ、レビュー後の修正、および人間の一時停止はすべて後戻りするパスを必要とします。
4. ステートはグラフを通過する一つのレコードです。各ノードはそれを読み取り、更新を書き込みます。

コードは構造を保持します。モデルは判断を提供します。ループ（セクション21）はその最小のグラフです：2つのノードと1つのバックエッジ。このセクションはそれを一般化します。

## メカニズム

![機構図](assets/22-graph-engineering.png)

単純なバージョンは三つの部分からなります：各ノード名を関数にマッピングするディクショナリ、各ノードから次に実行されるものにマッピングするディクショナリ、そしてすべてのノードが読み書きする1つのステートディクショナリです。

```python
def run_graph(nodes, edges, state, start, budget=20):  # src/graph.py
    state = dict(state)
    trace = []
    node = start
    for _ in range(budget):                        # the ceiling: harness-enforced
        state.update(nodes[node](state) or {})     # a node returns only its updates
        trace.append(node)
        step = edges.get(node, END)
        node = step(state) if callable(step) else step   # a coded edge: no model call
        if node == END:
            return {"ok": True, "state": state, "trace": trace}
    return {"ok": False, "state": state, "trace": trace}   # budget spent: escalate
```

- `nodes` はディスパッチマップです（セクション2）。ノードはステートを読み取り、変更したキーのみを返します。
- エッジは固定された名前（決定的）か、状態に対する呼び出し可能なもの（条件付き）です。いずれにせよ、harness はコード内で評価します。ルーティングにはトークンは不要です。
- エッジを持たないノードはグラフを終了します。予算はセクション21の上限であり、サイクルはカウントで停止し、`ok: False` によりエスカレートします。
- `trace` はどのノードが実行されたかを順序通りに記録します。これはセクション20の実行記録です。

### ノード：決定性からエージェンシーへのスケール

各ノードはスケール上の一点を選びます：

- **コードノード。** API の固定された呼び出しを解析・検証します。決定的で、トークンは不要です。
- **モデルノード。** 分類器のような LLM の呼び出しを一度行います。判断は制限されています。
- **エージェントノード。** ツールを備えた完全なセクション1ループ。固定されたスロット内でのオープンエンドの判断。

`agent_node`は内部ループをノードとしてマウントします。各訪問では`run_turn`を、状態から構築された新しい`messages[]`上で実行します。
そのため、ノードはプロンプトビルダーが渡すものだけを見て、全体の実行を見たりはしません。

規模は予算管理：分岐が予測可能な場合はコードでルートし、判断が必要なノード内でのみモデル呼び出しを使用します。

### 名前付きシェイプ

ソースが名前を付けたワークフローパターンはグラフ形状です：

- **プロンプトチェイニング。** ノードのパスで、その間にコードゲートがあります。
- **ルーティング。** 条件付きエッジが専門ノードに分岐します。
- **並列化。** 同時に実行され、1つのノードで統合される兄弟ブランチ。タスクを分割する（セクション化）か、投票のために繰り返す（投票）場合がある。
- **オーケストレータ-ワーカー。** runtimeでファンアウトを決定するノード、その後にマージノード。エッジセットは動的で、形状は依然としてグラフである。
- **評価者-最適化者。** ワーカーノードと1つの逆向きエッジを持つチェッカーノード。これはセクション21の検証ループをサブグラフとして示している。

名前はソース間で確定していない。`ai-agent-book`では「コラボレーショントポロジー」と「オーケストレーション」の下で同じ内容を扱っており、
「graph engineering」は用語に関する注記でのみ言及している。このセクションは独自の名前を保持する。なぜならここで説明されているのはコードで書かれたグラフだからである。
二番目の情報源を読むときは、単語ではなく仕組みによって一致させること。

### グラフを描くべきでないとき

オープンエンドの作業は、あらかじめ決められた道筋に従うことを拒む。深いリサーチや難しいデバッグには、runtimeで現れる計画が必要であり、事前に描かれたグラフは解決策が必要とする道筋を禁止する。
情報源からのルール: 実際に強制する構造だけをコード化する（行動の前に分類、コミットの前にレビュー、送信の前に承認）、
そして、結果が明らかに改善される場合にのみ構造を追加する。他のすべての場合は、単純なループを使用し、モデルに計画させる。

ハイブリッドが一般的なケースである: 1つのノードとして固定されたグラフ内に存在するエージェント。グラフはレビューが行われることを保証し、エージェントは自分のスロット内でどのように作業するかを決定する。

### 統合方法

このセクションでは、1つの小さなプリミティブ（エッジマップ）を追加し、残りを再利用します:

- ノードの作業はセクション1のループです; `agent_node`は`run_turn`を変更せずにラップします。
- コード化されたエッジはセクション2のディスパッチ規律に従います: マップであり、モデル出力ではありません。
- ノード間で分割されたワーカーとチェッカーはセクション6です; 兄弟ブランチはセクション15で分離されます worktrees。
- ステップ予算とエスカレーション契約はセクション21です。
- トレースはセクション20のテレメトリにフィードします。どのエッジが発火したかで、どのブランチが死んでいるかがわかります。

実行可能なものは、上の図からデモグラフを配線します:

```python
nodes = {                                          # src/demo.py
    "classify": lambda s: {"route": "math" if any(c.isdigit() for c in s["task"]) else "prose"},
    "math": agent_node(prompt, model, math_reg),   # a full agent run as one node

edges = {

    "math": "check",
    "prose": "check",
    "check": lambda s: END if s["verdict"]["passed"] else s["route"],   # the cycle
}
```

### さらに読む

これは `src/` にはありません。これは ai-agent-book からのものであり、表内のシステムについては確認されていません。

**フェーズノード。** フェーズノードは1つのジョブを一連のステージとして実行し、すべてのステージが1つの`messages[]`を共有します。
「探索」「実装」「レビュー」は、3つの別々の仕事ではなく、単一作業の段階です。
この経路は、ある段階で得られたものを次の段階に運ぶので、どの段階もタスクを最初から読み直すことはありません。

**各段階のツール。** 各段階には自分専用のsystem promptとツールセットがあり、段階が変わるとharnessが両方を切り替えます。
履歴はその場に残るので、次の段階に詰め込まれることはありません。本の記述にある3つの段階:

- **探索。** 読んで検索する。
- **実装。** 編集して実行する。
- **レビュー。** 読み、さらに判定を返すツールを使う。

**ゲートツール。** モデルは`finish_exploring`のようなゲートツールを呼び出すことで段階を終了します。
harnessはその呼び出しをエッジとして読み取り、次のフェーズを開始します。ゲートは唯一の出口なので、フェーズが終了するタイミングはモデルではなくharnessが決定します。

**ルート。** まず探索を行い、その後実装し、最後にレビューを行います。レビューに失敗すると、実行は再び実装に戻されます。
実行は既にレビューのノートを軌道に取り入れて再開します。このセクションの表現では、それは1つの後退エッジを持つパスです。
上記の評価者-最適化器と同じ形状です。

**どれをマウントするか。** ブランチが関連していない場合は新しい`messages[]`を使用します。ノードが1つのジョブのステージである場合は、1つの軌道を使用します。
新しい`messages[]`は、それぞれのノードのウィンドウを小さく保ち、そのブランチを独立させます。
ある軌道は、以前のすべての発見を見失わずに保持し、軌道が長くなるにつれてウィンドウの表示領域を広げていきます。選択は文脈に関する質問です（セクション8）。

**マルチエージェントとみなされるもの。** この本では、プロンプトとツールが各段階で変わるため、この設計をマルチエージェントと呼んでいます。
このリポジトリでは、プロンプトとツールが変わる一つのエージェントと呼んでいます。いずれの場合も仕組みは同じなので、結果を引用する際にはどの定義を指しているかを明示してください。

**一つの情報源。** この解説は、本自体の実験に基づいています。独立した報告による確認はありません。

## システムごと

各エージェントが次に何を実行するかをどのように決めるか。

| | Claude Code | Hermes Agent | mini-swe-agent |
| --- | --- | --- | --- |
| **利点** | コード化されたルーティング：トークン不要、変動なし。 ノード終了後の再開時に再生可能。 | 著者にグラフの作成は不要。構造はタスクに適合。 | グラフ全体を一目で監査可能。 |
| **欠点** | グラフは実行ごとのスクリプトであり、再利用可能な宣言型グラフではない。 | ルーティングはトークンを消費し、実行ごとに変動する可能性がある。 | タスクごとに一つの形状。分岐は専門化できない。 |
| **理由** | オーケストレーションはプログラム：一度書けば、決定的に実行可能。 | アシスタント作業はあまりにも自由度が高く、事前宣言は不可。 | 選択肢はモデル内に保持、一サイクル harness。 |
| **方法：ノード** | ノードごとに subagent、スキーマチェックされた構造化出力。 | 委譲 subagents、深さと並行性に上限あり。 | 二つ：モデルステップと環境ステップ。 |
| **方法：ルーティング** | ステージ間のプレーンなコード：条件分岐、ループ、ファンアウト。 | モデルはツール呼び出しによってルーティングされる。コード化されたエッジはない。 | 提出または予算停止までの固定サイクル。 |
| **方法：状態** | 返り値は前方にスレッドされる；ノード出力を再開用に記録するジャーナル。 | 結果は完了キューを通じて戻る。 | メッセージリストが全体の状態。 |

## 障害モード

- **ルーターとしてのモデル。** モデルに送られるルーティングはトークンを消費し、レイテンシを追加し、実行ごとに異なる。トップでの誤ルートはその後のすべてを誤誘導する。
  緩和策：コード内で遷移を評価し、判断が必要なノードにモデル呼び出しを予約する。
- **過剰グラフ化。** 探索が必要なタスクに固定グラフを使用すると、解決に必要な経路が禁止される。
  緩和策：強制的に適用する構造のみをエンコードし、それ以外の作業は単純なループに任せる。
- **失敗エッジなし。** FAIL を送る先がないチェックノードは、悪い出力を下流に流してしまう。
  緩和策：すべてのチェックノードに予算付きの後退エッジを与える（セクション21）。
- **無限ループ。** 天井のない再試行エッジは、永遠にループする。  緩和策：ハーネスで強制されたステップ予算；予算を使い果たしたらエスカレーションする。
- **状態の膨張。** すべてのノードが完全な出力を共有状態に吐き出し、後のノードがその中で溺れる。
  緩和策：厳格な状態境界；ノードは必要なサブセットだけを読み取り、自身の更新のみを返す（セクション8）。
- **中途停止。** 長いグラフがノード7で停止し、ノード1で再起動する。
  緩和策：各ノードの出力を記録する; 再開時には、記録から完了したノードを再生する（セクション11、12）。
- **終わらないフェーズ。** モデルがゲートツールを呼び出さないため、フェーズは同じプロンプトと同じツールで作業を続ける。予算だけがそれを止める。
  緩和策：ゲートを唯一の出口にする; 各フェーズに独自のステップ予算を与える; 使用済み予算は次のフェーズに移動するか、エスカレートさせる。
- **すべてのフェーズを運ぶ軌跡。** 1つの軌跡が各フェーズとともに成長する。現在のフェーズが使用しないツールへの呼び出しも保持しており、モデルはそれを再び試みる可能性がある。
  緩和策：フェーズプロンプトで現在のフェーズとそのツールに名前を付ける; マウントされていないツールへの呼び出しは明確なエラーで拒否する; 完了したフェーズを圧縮する（セクション8）。

## 実行可能

[`src/`](src/) は 21 を引き継ぎ、次を追加します：

- [`graph.py`](src/graph.py)：`run_graph`（ノードのディスパッチマップ、固定および条件付きエッジ、スレッド化された状態、ステップ予算）と `agent_node`、ノードとして搭載された内部ループ。
- [`test.py`](src/test.py)：チェーン順序と状態マージのオフラインチェック、コードのみのルーティング、予算で停止するサイクル、エージェントノード訪問ごとの新しい `messages[]`。
- [`demo.py`](src/demo.py)：1 回のルーティング実行：コードノードが分類し、コード化されたエッジがルートし、エージェントノードが応答、
  セクション 21 のチェッカーが採点し、失敗判定はフィードバックとともにサイクルバックします。

ループは変更されていません。グラフが実行タイミングを決定します。

```bash
python sections/22-graph-engineering/src/test.py         # offline checks, no key
uv run python sections/22-graph-engineering/src/demo.py  # live demo, needs a key
```
