# 22 · Graph engineering

[English](README.md) · [繁體中文](README.zh-TW.md) · [简体中文](README.zh-CN.md) · [日本語](README.ja.md) · **한국어**

> 다음에 무엇을 실행할지 모델에게 계속 묻지 마세요. 이미 알고 있는 경로를 인코딩하고, 판단이 필요한 곳에서만 모델을 사용하세요.

섹션 21은 한 에이전트를 중심으로 루프를 쌓아 올립니다. 이 섹션은 모델 호출 사이의 작업을 구성합니다.

많은 작업들은 모델을 호출하기 전에 이미 알고 있는 구조를 가지고 있습니다: 작업을 수행하기 전에 티켓을 분류하고, 커밋하기 전에 diff를 검토하며, 외부 작업 전에 승인을 받는 것처럼요.
일반적인 agent loop는 매번 모델에게 다음에 무엇을 해야 하는지 물어봄으로써 그 구조를 다시 발견합니다. 모델 주도 라우팅은 느리고, 토큰을 소비하며, 실행마다 달라집니다.

Graph engineering는 코드 내에서 이미 알고 있는 구조를 방향성 그래프로 인코딩합니다:

1. 노드가 작업을 수행합니다. 노드는 일반 코드, 한 번의 모델 호출, 또는 전체 에이전트 실행이 될 수 있습니다.
2. 엣지는 다음 노드를 선택합니다. harness는 모델 호출이 아닌 코드에서 이를 평가합니다.
3. 사이클이 허용됩니다. 재시도, 검토 후 수정, 사람의 일시 정지 모두 되돌아가는 경로가 필요합니다.
4. 상태는 그래프를 통과하는 하나의 기록입니다. 각 노드는 이를 읽고 자신의 업데이트를 작성합니다.

코드는 구조를 보유합니다. 모델은 판단을 제공합니다. 루프(섹션 21)는 이러한 그래프의 가장 작은 예입니다: 두 개의 노드와 하나의 되돌아가는 엣지. 이 섹션은 이를 일반화합니다.

## 메커니즘

![메커니즘 다이어그램](assets/22-graph-engineering.png)

간단한 버전은 세 부분으로 구성됩니다: 각 노드 이름을 함수에 매핑하는 딕셔너리, 각 노드를 다음에 실행될 항목에 매핑하는 딕셔너리, 모든 노드가 읽고 쓰는 하나의 상태 딕셔너리.

```python
def run_graph(nodes, edges, state, start, budget=20):  # src/graph.py
    state = dict(state)
    trace = []
    node = start
    for _ in range(budget):                        # the ceiling: harness-enforced
        state.update(nodes[node](state) or {})     # a node returns only its updates
        trace.append(node)
        step = edges.get(node, END)
        node = step(state) if callable(step) else step   # a coded edge: no model call
        if node == END:
            return {"ok": True, "state": state, "trace": trace}
    return {"ok": False, "state": state, "trace": trace}   # budget spent: escalate
```

- `nodes`는 디스패치 맵(섹션 2)입니다. 노드는 상태를 읽고 자신이 변경한 키만 반환합니다.
- 엣지는 고정된 이름(결정적) 혹은 상태에 대한 호출 가능(callable, 조건적)입니다. 어느 쪽이든 harness가 코드에서 이를 평가합니다. 라우팅에는 토큰이 필요하지 않습니다.
- 엣지가 없는 노드는 그래프를 종료합니다. 예산은 21조 상한입니다: 사이클은 횟수에서 멈추고 `ok: False`로 상승합니다.
- `trace`는 실행된 노드를 순서대로 기록합니다. 이는 20조 실행 기록입니다.

### 노드: 결정성-에이전시 척도

각 노드는 척도의 한 지점을 선택합니다:

- **코드 노드.** 구문 분석, 검증, 고정된 API 호출. 결정적, 토큰 없음.
- **모델 노드.** 하나의 LLM 호출, 예를 들어 분류기. 제한된 판단.
- **에이전트 노드.** 도구를 갖춘 전체 섹션 1 루프. 고정 슬롯 안에서의 개방형 판단.

`agent_node`는 내측 루프를 노드로 장착합니다. 각 방문은 상태에서 생성된 새로운 `messages[]`에서 `run_turn`를 실행합니다.
그래서 노드는 전체 실행이 아니라, 오직 프롬프트 빌더가 전달하는 것만 봅니다.

규모는 예산 규율입니다: 분기가 예측 가능한 경우에는 코드를 사용하는 경로를 따르고, 판단이 필요한 노드 안에서만 모델 호출을 사용합니다.

### 명명된 형태

소스가 이름 붙인 워크플로우 패턴은 그래프 형태입니다:

- **프롬프트 체이닝.** 코드 게이트가 있는 노드 경로입니다.
- **라우팅.** 하나의 조건부 엣지가 전문 노드로 확장되는 경우.
- **병렬화.** 동시에 실행되고 한 노드에서 병합되는 형제 브랜치들로, 작업을 나누기(섹션 나누기) 혹은 투표를 위해 반복하기(투표) 중 하나를 수행합니다.
- **오케스트레이터-워커.** runtime에서 팬아웃을 결정한 후 병합 노드로 연결되는 노드입니다. 엣지 집합은 동적이며, 형태는 여전히 그래프입니다.
- **평가자-최적화기.** 하나의 후방 엣지를 가진 워커 노드와 검사자 노드입니다. 이는 섹션 21의 검증 루프를 서브그래프로 표현한 것입니다.

이 이름들은 출처별로 정해져 있지 않습니다. `ai-agent-book`는 "협업 토폴로지"와 "오케스트레이션"이라는 용어 하에 같은 내용을 다룹니다.
그리고 "graph engineering"는 용어 주석에서만 언급됩니다. 이 섹션은 코드로 작성된 그래프를 설명하기 때문에 자체 이름을 유지합니다.
두 번째 출처를 읽을 때, 단어가 아니라 메커니즘에 따라 맞추세요.

### 그래프를 그리지 말아야 할 때

열린 형태의 작업은 미리 정해진 경로를 거부합니다. 깊은 연구와 철저한 디버깅은 runtime에서 나타나는 계획을 필요로 합니다; 미리 그린 그래프는 해결책에 필요한 경로를 금지합니다.
출처에서의 규칙: 어쨌든 적용할 구조만 인코딩하세요 (행동 전에 분류, 커밋 전에 검토, 전송 전에 승인),
그리고 결과를 실제로 향상시키는 경우에만 구조를 추가하세요. 그 외의 모든 경우에는 단순한 루프를 사용하고 모델이 계획을 세우도록 하세요.

혼합형이 일반적인 사례입니다: 고정된 그래프 안의 한 노드로서의 에이전트. 그래프는 검토가 이루어지도록 보장하고, 에이전트는 그 슬롯 안에서 어떻게 작업할지 결정합니다.

### 통합 방식

이 섹션은 하나의 작은 기본 요소(엣지 맵)를 추가하고 나머지는 재사용합니다:

- 노드의 작업은 섹션 1 루프입니다; `agent_node`는 `run_turn`를 변경 없이 감쌉니다.
- 코딩된 엣지는 섹션 2의 디스패치 규칙을 따릅니다: 모델 출력이 아니라 맵입니다.
- 워커와 체커의 노드 간 분할은 섹션 6에 있으며; 형제 브랜치는 섹션 15 worktrees에서 격리됩니다.
- 단계 예산과 에스컬레이션 계약은 섹션 21입니다.
- 트레이스는 섹션 20의 텔레메트리에 정보를 제공합니다. 어떤 엣지가 작동했는지 알면 어떤 분기가 죽었는지 알 수 있습니다.

실행 가능한 것은 위 도표에서 데모 그래프를 연결합니다:

```python
nodes = {                                          # src/demo.py
    "classify": lambda s: {"route": "math" if any(c.isdigit() for c in s["task"]) else "prose"},
    "math": agent_node(prompt, model, math_reg),   # a full agent run as one node
    "prose": agent_node(prompt, model, Registry()),
    "check": check_node,                           # section 21's checker, now a node
}
edges = {
    "classify": lambda s: s["route"],              # a coded edge: routing costs no tokens
    "math": "check",
    "prose": "check",
    "check": lambda s: END if s["verdict"]["passed"] else s["route"],   # the cycle
}
```

### 추가 읽기

이 모든 것은 `src/`에 없습니다. 이것은 ai-agent-book에서 나온 것이며, 표에 있는 시스템들에 대한 확인은 되지 않았습니다.

**페이즈 노드.** 페이즈 노드는 하나의 작업을 여러 단계로 실행하며, 모든 단계는 하나의 `messages[]`를 공유합니다.
탐색, 구현, 검토는 각각 별개의 작업이 아니라 단일 작업의 단계입니다.
이 궤적은 한 단계에서 찾은 것을 다음 단계로 전달하므로, 어느 단계도 작업을 처음부터 다시 읽지 않습니다.

**단계별 도구.** 각 단계는 고유한 system prompt와 고유한 도구 세트를 가지고 있으며, 단계가 변경될 때 harness가 둘 다 교체합니다.
히스토리는 제자리에 유지되므로, 다음 단계로 포장되는 것은 없습니다. 책에서의 세 단계 작성 내용:

- **탐색.** 읽고 검색합니다.
- **구현.** 편집하고 실행합니다.
- **검토.** 읽고, 결과를 반환하는 도구를 사용합니다.

**게이트 도구.** 모델은 `finish_exploring`와 같은 게이트 도구를 호출하여 단계를 종료합니다.
harness는 그 호출을 엣지로 읽고 다음 단계를 시작합니다. 게이트는 유일한 출구이므로, harness가 단계가 끝나는 시점을 결정하며, 모델은 결정하지 않습니다.

**경로.** 먼저 실행(run)을 탐색한 후, 구현하고, 그 다음 검토합니다. 검토가 실패하면 실행이 다시 구현 단계로 돌아갑니다.
이때 이미 검토의 메모가 경로 안에 포함되어 있습니다. 이 섹션의 용어로는 한 개의 역방향 엣지를 가진 경로입니다.
위의 평가자-최적화기와 같은 형태입니다.

**어떤 것을 장착할지.** 브랜치가 관련이 없을 때는 새로운 `messages[]`를 사용합니다. 노드가 하나의 작업 단계일 때는 하나의 경로를 사용합니다.
새로운 `messages[]`는 각 노드의 창(window)을 작게 유지하고 브랜치를 독립적으로 만듭니다.
하나의 궤적은 이전의 모든 발견을 계속 주시하며, 경로가 길어질수록 창을 더 많이 채운다. 선택은 맥락에 따른 질문이다 (섹션 8).

**멀티 에이전트로 간주되는 것.** 이 책에서는 프롬프트와 도구가 각 단계마다 바뀌기 때문에 이 설계를 멀티 에이전트라고 부른다.
이 저장소에서는 프롬프트와 도구가 바뀌는 하나의 에이전트라고 부른다. 메커니즘은 어느 이름을 사용하든 동일하므로 결과를 인용할 때 어떤 정의를 의미하는지 명시해야 한다.

**단일 출처.** 작성 내용은 책 자체 실험에 기반한다. 독립적인 보고서가 이를 확인한 바 없다.

## 시스템별

각 에이전트가 다음에 실행할 것을 어떻게 결정하는지.

| | Claude Code | Hermes Agent | mini-swe-agent |
| --- | --- | --- | --- |
| **장점** | 코드화된 라우팅: 토큰 없음, 변동 없음. 완료된 노드는 재개 시 재실행됨. | 작성자에게 그래프 필요 없음. 구조가 작업에 적합함. | 전체 그래프를 한눈에 감사 가능. |
| **단점** | 그래프는 실행마다 생성되는 스크립트이며, 재사용 가능한 선언된 그래프가 아님. | 라우팅은 토큰을 소모하며 실행마다 달라질 수 있음. | 모든 작업에 하나의 형태 사용. 분기는 전문화될 수 없음. |
| **이유** | 오케스트레이션은 프로그램임: 한 번 작성하면 결정론적으로 실행됨. | 어시스턴트 작업은 너무 개방적이어서 미리 선언할 수 없음. | 선택은 모델에 유지; 한 사이클 harness. |
| **방법: 노드** | 노드별 subagent, 스키마 검증된 구조화된 출력 포함. | 위임된 subagents, 깊이와 동시성 제한. | 두 가지: 모델 단계와 환경 단계. |
| **방법: 라우팅** | 단계 간 일반 코드: 조건문, 반복문, 분기. | 모델은 도구 호출로 라우팅합니다. 코드화된 엣지는 없습니다. | 제출 또는 예산 종료까지 한 번의 고정된 사이클. |
| **방법: 상태** | 반환 값이 앞으로 전달되고, 저널이 재개를 위해 노드 출력을 기록합니다. | 결과는 완료 큐를 통해 돌아옵니다. | 메시지 목록이 전체 상태입니다. |

## 실패 모드

- **모델을 라우터로 사용.** 라우팅을 모델에 보내면 토큰이 소모되고 지연이 추가되며 실행마다 달라집니다. 상단에서의 잘못된 라우팅은 그 이후 모든 것을 잘못 유도합니다.
  완화: 코드에서 전환을 평가하고 판단이 필요한 노드에 대해서만 모델 호출을 예약합니다.
- **과도한 그래프화.** 탐색이 필요한 작업에 고정된 그래프는 솔루션이 필요한 경로를 금지합니다.
  완화: 어차피 적용할 구조만 인코딩하고, 열린 작업은 일반 루프에 맡기십시오.
- **실패 경로 없음.** FAIL을 보낼 곳이 없는 검사 노드는 잘못된 출력을 하류로 흘립니다.
  완화: 모든 검사 노드에 예산이 있는 역방향 경로를 제공합니다(섹션 21).
- **무한 사이클.** 상한 없는 재시도 경로는 무한 반복됩니다. 완화: 하네스로 강제하는 단계 예산; 예산이 소진되면 에스컬레이션합니다.
- **상태 팽창.** 모든 노드는 전체 출력을 공유 상태에 덤프하고, 나중 노드는 그 안에서 질식합니다.
  완화: 엄격한 상태 경계; 노드는 필요한 부분 집합만 읽고 자신의 업데이트만 반환합니다(섹션 8).
- **실행 중간 종료.** 긴 그래프가 노드 7에서 죽고 노드 1에서 다시 시작합니다.
  완화: 각 노드의 출력을 기록합니다; 재개 시, 기록에서 완료된 노드를 재생합니다(섹션 11, 12).
- **절대 끝나지 않는 단계.** 모델이 게이트 도구를 호출하지 않으므로, 같은 프롬프트와 같은 도구 아래에서 단계가 계속 진행됩니다. 예산만이 이를 중단시킵니다.
  완화: 게이트를 유일한 종료 지점으로 만듭니다; 각 단계에 고유한 단계 예산을 제공합니다; 소진된 예산은 다음 단계로 이동하거나 상승합니다.
- **모든 단계를 포괄하는 궤적.** 하나의 궤적이 각 단계마다 성장합니다. 여전히 현재 단계에서 사용하지 않는 도구 호출을 포함하고 있으며, 모델이 이를 다시 시도할 수도 있습니다.
  완화: 현재 단계와 그 도구들을 단계 프롬프트에 명시합니다; 장착되지 않은 도구 호출은 명확한 오류와 함께 거부합니다; 완료된 단계를 압축합니다(섹션 8).

## 실행 가능

[`src/`](src/)는 21을 전달하고 다음을 추가합니다:

- [`graph.py`](src/graph.py): `run_graph`(노드의 디스패치 맵, 고정 및 조건부 엣지, 스레드 상태, 단계 예산) 그리고 내부 루프가 노드로 장착된 `agent_node`
- [`test.py`](src/test.py): 체인 순서 및 상태 병합에 대한 오프라인 검사, 코드 전용 라우팅, 예산에서 멈추는 사이클, 그리고 에이전트-노드 방문마다 새 `messages[]`
- [`demo.py`](src/demo.py): 하나의 라우팅된 실행: 코드 노드가 분류하고, 코드 엣지가 라우팅하며, 에이전트 노드가 답변하고,
  섹션 21의 체크어가 등급을 매기고, 실패한 평결은 피드백과 함께 다시 사이클을 돕니다.

루프는 변경되지 않았습니다. 그래프가 언제 실행될지 결정합니다.

```bash
python sections/22-graph-engineering/src/test.py         # offline checks, no key
uv run python sections/22-graph-engineering/src/demo.py  # live demo, needs a key
```
