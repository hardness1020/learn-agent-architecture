# 10 · System prompt assembly

[English](README.md) · [繁體中文](README.zh-TW.md) · [简体中文](README.zh-CN.md) · **日本語** · [한국어](README.ko.md)

> 毎ターンライブ状態からプロンプトを構築します。

system prompt は、エージェントの既存の命令セットです。アイデンティティ、ルール、ツール、プロジェクトのコンテキスト、アクティブな機能について説明します。

実際のエージェントでは、これを 1 つのハードコードされた文字列のままにすることはできません。

ツール、メモリ、出力スタイル、MCP サーバー、およびモードはセッションによって異なる場合があります。プロンプトには、実際に何がアクティブであるかを説明する必要があります。

プロンプト アセンブラは、次の 3 つの問題を解決します。

1. 新しい特集テキストには明確な居場所があります。
2. 非アクティブな機能テキストはスキップできます。
3. 安定したセクションでは、prompt caching を使用できます。

アセンブリを行わないと、プロンプトが古くなったり、肥大化したり、安全に変更することが困難になります。

## メカニズム

![機構図](assets/10-system-prompt-assembly.png)

プロンプトを名前付きセクションとして定義します。一部のセクションは静的です。他のものはライブ状態からテキストを計算し、適用されない場合に `None` を返します。

アセンブリは簡単です。すべてのセクションを解決し、`None` を削除し、残りを結合します。

```python
sections = [
    intro, system_rules, doing_tasks, tools_section,
    session_guidance(), memory(), env_info(),
    output_style(), mcp_instructions(),
]
prompt = [s for s in resolve(sections) if s is not None]
```

2 つのルールにより管理が容易になります。

1. キーワードの推測ではなく、状態ごとのセクションを含めます。
2. 揮発性コンテンツを安定したプロンプト接頭辞から遠ざけてください。

### 新機能: セクションとアセンブル

```python
@dataclass
class Section:                                          # src/prompt.py
    name: str
    compute: Callable    # (state) -> str | None ; static sections ignore state

def static(name, text) -> Section:
    return Section(name, lambda _state: text)

def assemble(sections, state) -> str:                  # the prompt for this turn
    parts = (s.compute(state) for s in sections)
    return "\n\n".join(p for p in parts if p is not None)
```

セクション リストは状態駆動型の包含を所有します。

```python
DEMO_SECTIONS = [
    static("intro", "You are a tiny agent. ..."),
    Section("tools", lambda s: "Tools: " + ", ".join(s["tools"]) if s.get("tools") else None),
    Section("env", lambda s: f"cwd: {s['cwd']}" if s.get("cwd") else None),
    Section("mcp", lambda s: "MCP servers connected; ..." if s.get("mcp") else None),
]
```

思い出された記憶はこのプロンプトの一部ではありません。これは、セクション 9 によって `<system-reminder>` メッセージとして挿入されます。これにより、プロンプト プレフィックスがより安定した状態に保たれます。

### Prompt caching

ほとんどの system prompt セクションはセッション中安定しています。デモでは、トップレベルのキャッシュ ブレークポイントを設定します。

```python
client.messages.create(model=MODEL, system=assemble(DEMO_SECTIONS, state),
                       messages=messages, cache_control={"type": "ephemeral"})
```

安定したコンテンツは、揮発性のコンテンツの前に来る必要があります。変化する値が早期に現れると、より多くのキャッシュが無効になる可能性があります。

そのルールを厳格にするのが価格表です。キャッシュは正確なトークン プレフィックスに基づいてキー化されます。
1 つのトークンと、キャッシュされたすべてのトークンがなくなった後に変更します。キャッシュ読み取りのコストは新しい入力トークンの約 10 分の 1 であり、キャッシュ書き込みのコストは新しい入力トークンよりも高くなります。
したがって、1 つの単語を移動すると、キャッシュされた通話が正規料金の通話に変わる可能性があります。
この問題は 2 つのことが原因で何度も発生します。それは、プロンプトの上部近くに出力されるタイムスタンプまたはトークン数、もう 1 つは実行ごとに順序が変わるツール リストです。

Claude Code も明示的な動的境界を使用します。これにより、小さな動的テールが変更されたときに、大きな静的プレフィックスが保護されます。

### 統合方法

このループは、各モデルを呼び出す前にプロンプトを組み立てます。

```python
for _ in range(max_steps):                             # src/loop.py
    messages = context.manage(messages, summarizer=summarizer)
    system = prompt(registry, session) if prompt else None   # 10 · assemble from live state
    response = model(messages, registry, system)
    ...
```

- `prompt` は、セクション リストを閉じる呼び出し可能オブジェクトです。
- 有効なツールやセッション モードなどのライブ状態を読み取ります。
- `prompt=None` を渡すと、セクション 9 の動作が維持されます。

### コントラスト: セクションレジストリ

上記のリストは 1 つのファイルに固定されています。セクションの追加はそのファイルを編集することを意味し、ファイルの順序はプロンプトの順序になります。

deepseek-harness は代わりに登録からアセンブルします。各 plugin は、名前付きセクションと、そのセクションの行き先を示す番号を登録します。
数字は規則に従って帯域に分類されます。最初に harness ID、次に展開ペルソナ、その次にツール ガイダンスです。
アセンブリは番号によってソートされるため、他に何が登録されているかを知らなくても、plugin がその場所を選択します。

レジストリにはさらに 2 つのルールが付属しています。

- 1 つのエージェントは、すでに存在する名前で独自のセクションを登録できます。そのエージェントはそのバージョンを確認し、他の人は共有バージョンを保持します。
- セクション テキストには `{{variables}}` を含めることができ、レンダリングは厳密です。不明な名前は、出荷されたプロンプトに穴を与える代わりに表示されます。

動的な事実はこのプロンプトには含まれません。これらは、レンダリングされたテキストが実際に変更された場合にのみ、スナップショットとして会話に追加されるため、プレフィックスはキャッシュに安定したままになります。

[`src/registry.py`](src/registry.py) はこれを取り除いたものです。これはコントラスト デモであり、`assemble()` に接続されていないため、後のセクションでは同じプロンプト コードが続きます。

### さらに読む

これは `src/` にはありません。これは ai-agent-book からのものであり、表内のシステムについては確認されていません。

**境界前の条件はプレフィックスを乗算します。** 境界の前に runtime 条件を 1 つ配置すると、キャッシュは結果ごとに 1 つずつ、合計 2 つのプレフィックスを保持する必要があります。
3 つの条件で 8 になります。 10 個で 1,000 個以上が作成され、それぞれが別々に温められるため、ほぼすべてのセッションは冷えた状態から始まります。
境界の後に条件付きセクションを保持すると、接頭辞が再び 1 つになります。

**タスク タイプごとにサンプル セットを 1 つ選択し、そのままにしておきます。** プレフィックスに含まれるショットのサンプルはほとんどないため、上記のルールはそれらもカバーします。
各リクエストに最適な例を取得すると、呼び出しごとにプレフィックスが書き換えられ、キャッシュが放棄されます。
固定セットはリクエストへの適合性が少し劣りますが、セッション全体にわたってプレフィックスをウォームに保ちます。

**ステータス バーは、実行が現在どこにあるかをモデルに示します。** モデルは harness を認識できないため、一部のハーネスはコンテキストの最後にライブ状態を数行に書き込みます。

- 実行されたツール呼び出しの数
- 現在の TODO
- 経過時間
- 作業ディレクトリ

これらの行は最新の状態に保つ必要があり、これを行うには 2 つの方法があります。どちらも無料ではありません。
ターンごとにブロックを置き換えると、状態の真のコピーが 1 つ存在しますが、末尾は書き換えられ、キャッシュがなくなった後にキャッシュされます。
ターンごとに新しいブロックを追加するとキャッシュが保持されますが、古いブロックは履歴に残り、モデルはすでに変更された状態に基づいて動作できます。
セクション 9 の `<system-reminder>` メッセージを使用して、Claude Code を追加します。
いずれの場合も、実際の状態を読み取るコードを使用してブロックを作成します。 LLM サマライザーは通話を追加し、遅延を追加し、誤った結果を招く可能性があります。

**外部テキストはデータであり、決して注文ではありません。** 取得した Web ページ、ファイル、問題のコメント、および MCP サーバーの応答はすべてデータです。どれもユーザーが話しているものではありません。
そのテキストをマーカーなしで送信し、その中に命令のように見える文が system prompt と同等の条件で競合します。それが即時注射です。
セクション 3 では、脅威モデルと実行層の答えを説明します。権限と sandbox によって、ハイジャックされたエージェントが何を実行できるかを決定します。
プロンプト層は、命令とデータを分離しておくことにより、より早く動作することができます。

- 外部コンテンツを、ソース名を指定したタグ付きブロックでラップします。プロンプトで、タグ付けされたコンテンツは読み取るべきデータであり、従うべき指示ではないことを伝えます。
- 役割を厳密に保ちます。命令は system prompt に入力され、結果は `tool_result` ブロックに入力され、人間がユーザーの順番で話します。
- ロイヤルティ ルールを 1 回だけ述べます。エージェントはユーザーとオペレーターのために機能します。ツールを介して到着するテキストによってそれが変更されることはありません。この本ではこれを「忠誠心」と呼んでいます。

**プロンプト層は境界ではありません。** モデルは依然としてルールの外にある可能性があるため、とにかくセクション 3 のチェックが実行されます。
プロンプトレイヤーは確率を下げます。実行層はダメージを制限します。

## 障害モード

- **揮発性テキストはキャッシュを破壊します。** 変更されるコンテンツを遅れて配置するか、プロンプト接頭辞の外側に配置します。
- **古いセクション キャッシュ。** セッション状態が変化するとメモ化されたセクションをクリアします。
- **不足しているツールの名前をプロンプトに表示します。** ライブ対応ツール セットからツール テキストを生成します。
- **プロンプトにコンテキストを混合。** 頻繁に変更される場合は、プロジェクト ファイル、日付、および git ステータスをコンテキスト メッセージに含めます。
- **プロンプトは競合をオーバーライドします。** 1 つのリゾルバーを使用して優先順位を定義します。
- **キャッシュ キーが多すぎます。** 境界前の各 runtime 条件により、個別にウォーミングする必要があるプレフィックスが 2 倍になります。その後に条件セクションを残します。
- **古いステータス ブロック。** 追加された状態が蓄積され、モデルが古いコピーで動作する可能性があります。最新のブロックをマークするか、それを置き換えてキャッシュの再構築を受け入れます。
- **外部コンテンツは指示として読み取られます。** ツールの結果をソースごとにタグ付けし、タグ付けされたコンテンツがデータであることを示します。セクション 3 の権限チェックは実際の境界のままです。

## 実行可能

[`src/`](src/) 09 を前方に繰り上げて次を追加します。

- [`prompt.py`](src/prompt.py): `Section`、`static`、および `assemble`。
- [`registry.py`](src/registry.py): deepseek-harness の対照: オーダー番号、スコープ シャドウイング、および厳密な `{{variable}}` レンダリングで登録されたセクション。
- [`loop.py`](src/loop.py): 毎ターンプロンプトを再構築します。
- [`demo.py`](src/demo.py): トップレベルの `cache_control` を追加します。
- [`test.py`](src/test.py): 状態駆動型の包含をチェックします。レジストリ チェックでは、順序付け、シャドウイング、フェールラウド変数がカバーされます。

```bash
python sections/10-system-prompt/src/test.py         # offline checks, no key
uv run python sections/10-system-prompt/src/demo.py  # live demo, needs a key
```
