# 19 · MCP / plugins / channels

[English](README.md) · [繁體中文](README.zh-TW.md) · [简体中文](README.zh-CN.md) · **日本語** · [한국어](README.ko.md)

> 能力が足りないのでしょうか？さらに接続してください。 harness は、1 つの標準プロトコルを通じて世界に到達します。

harness は、そのツールで実行できることのみを実行でき、すべての組み込みツール (入力スキーマ、実行、エラー処理など) はすべて事前定義されています。

これでは、トラッカーの発行、システムの展開、知識ベースなど、ユーザーが望むサービスに合わせて拡張することはできません。使用する言語ごとに、それぞれのツールを手書きすることはできません。

MCP (モデル コンテキスト プロトコル) は、ギャップを埋めるオープン コントラクトです。外部サービスがそのツールを宣言すると、エージェントはそのツールをブラインドと呼び、誰がどのように作成したかがわかりません。
MCP 用語では、サービスはサーバーであり、接続して呼び出す harness はクライアントです。

したがって、エージェントは、誰も harness を編集することなく、Jira ツールまたはデプロイ ツールを取得します。 MCP を省略したままにすると、機能はバイナリで出荷されたもので凍結されます。

さらに 2 つの部分が MCP に基づいて構築されます。 plugin は、サーバーを hooks および skills とバンドルするため、1 つのユニットとしてインストールされます。
チャネルを使用すると、サーバーはメッセージをプッシュバックできます。両方とも同じプロトコルに乗ります。

## メカニズム

![機構図](assets/19-mcp-plugins-channels.png)

各サーバーに接続し、そのツール (`tools/list`) を検出し、それぞれを runtime `Tool` (セクション 2) としてラップし、ループがディスパッチする同じプールにそれらをマージします。

名前は `mcp__<server>__<tool>` という名前空間であるため、2 つのサーバーが衝突することはありません。ループとゲートは変更されません。MCP ツールは、トランスポート経由で `run()` を呼び出す `Tool` です。

- ディスカバリーはサーバーごとに 1 つの `tools/list` 呼び出しです。返される各仕様は、ラップされた `Tool` になります。
- 名前は名前空間化され正規化されているため、一意であり、API の名前パターンと一致します。
- 各ツールの MCP アノテーション (`readOnlyHint`、`destructiveHint`) は、ゲートが読み取る許可ヒントになります (セクション 3)。
- 1 つの `Registry` にマージされたモデルでは、MCP ツールとビルトインが同じリストに表示されます。

### その下のワイヤプロトコル

2026 年 7 月 28 日の仕様改訂により、ワイヤはステートレスになりました。すべてのリクエストが独立して実行されるようになり、どのサーバー レプリカでもそれに応答できるようになります。
上記の harness 側 (検出、ラップ、マージ) は変更されません。通信上で何が変わったのか:

- **ハンドシェイクは不要です。** 以前は、クライアントは `initialize` を呼び出し、何も実行する前に待機していました。
  これで、どのリクエストも最初に実行できるようになります。それぞれが独自のプロトコル バージョンと機能を `_meta` で保持します。
  バージョンを事前に確認したいクライアントは、`server/discover` を呼び出します。
- **セッションは不要です。** 以前は、サーバーはセッション ヘッダーの背後に接続ごとの状態を保持していました。
  呼び出し全体で状態を必要とするサーバーはハンドルを返し、クライアントはそれを通常のツール引数として返します。
- **1 つの通知ストリーム。** 以前は、クライアントは変更を聞くために長い GET 接続を開いたままにしていました。
  ここで、1 つの `subscriptions/listen` ストリームを開き、必要なイベント (変更されたツール リスト、変更されたリソース) に名前を付けます。
  リスト結果には、クライアントがキャッシュできる期間を示す `ttlMs` フィールドも含まれます。
- **サーバーは、コールバックではなく、応答することによって要求します。** 以前は、サーバーは独自のリクエストをクライアントに送信できました。
  ツール呼び出し中 (ユーザーに質問し、モデルにサンプルを依頼します)。マークされた中間結果を返すようになりました。
  `input_required`、クライアントは回答を添付して同じリクエストを再試行します。
- **機能が減少しました。** ルート、サンプリング、ロギング、および古い HTTP+SSE トランスポートは非推奨になりました。
  ローカル サーバー用の stdio、リモート サーバー用の Streamable HTTP の 2 つのトランスポートが引き続き公式です。

エージェントを使用しているユーザーの場合、画面上は何も変化しません。古いサーバーは動作し続け、v1 SDK は維持されたままになります。
リモート サーバーはロード バランサーの背後で拡張され、最初の呼び出しはラウンド トリップをスキップし、キャッシュされたツール リストはトークンを保存します。
非推奨の機能を使用しているサーバーの移行には 12 か月の猶予期間が与えられます。その作業はユーザーではなくサーバー作成者にあります。

### 新機能: 発見されたツールをラップする

`mcp.py` は、検出された各仕様を `Tool` に変換します。この名前はサーバーが衝突しないように名前空間が設定されており、API の文字セットに正規化されています。

```python
def tool_name(server, tool):                           # src/mcp.py
    return f"mcp__{normalize(server)}__{normalize(tool)}"   # buildMcpToolName

def wrap(server, spec, call):
    ann = spec.get("annotations", {})
    read_only = bool(ann.get("readOnlyHint"))
    bare = spec["name"]
    return Tool(
        name=tool_name(server, bare),
        run=lambda args, _t=bare: call(_t, args),      # dispatch calls out over the transport
        input_schema=spec.get("inputSchema") or dict(NO_INPUT),
        is_read_only=read_only,
        is_concurrency_safe=read_only,                 # reads are safe to batch
    )
```

- `tool_name` 名前空間すべてのツール。 `normalize` は、`[a-zA-Z0-9_-]` 以外の文字を `_` に置き換え、API 名前パターンを満たします。
- `run` は、ベア ツール名とサーバーの `call` をクローズするため、ラップされた `Tool` をディスパッチすると、トランスポートを介して戻ります。
- `readOnlyHint` アノテーションは `is_read_only` になります。これは、許可ゲート (セクション 3) が許可または要求を決定するために読み取るものです。

### 新機能: 検出とマージ

`connect` はディスカバリーを 1 回実行し、ラップされたツールを返します。呼び出し元はそれらをループの `Registry` にマージします。

```python
def connect(server, conn):                             # src/mcp.py
    return [wrap(server, spec, conn.call) for spec in conn.list_tools()]
```

- `conn` はライブトランスポートです: 実稼働環境では `stdio` または `http`、デモでは処理中です。 Discovery はどちらでも構いません。
- 返された `Tool` は組み込みとして同じプールに登録されるため、`registry.schemas()` はそれらを一緒にアドバタイズし、ループはそれらを同じ方法でディスパッチします。

### 新しい: チャネルと plugin 構成

2 つの小さな部分がセクションを締めくくります。

1 つ目はメッセージ フローを逆にします。通常、エージェントはサーバーを呼び出しますが、サーバーが独自にメッセージをプッシュすることもできます (Slack メッセージが到着します)。
harness は、そのテキストを `<channel>` タグでラップし、エージェントの次のターンの前に配置するため、モデルはそれを読み取ります。

```python
def wrap_channel(source, payload):                     # src/mcp.py
    return f'<{CHANNEL_TAG} source="{source}">{payload}</{CHANNEL_TAG}>'
```

2 つ目は構成の階層化です。同じサーバーを plugin、ユーザー、プロジェクト構成で一度に定義できます。 `merge_servers` は優先順位に従って勝者を選択します。

```python
def merge_servers(*layers):                            # src/mcp.py
    merged = {}
    for scope in PRECEDENCE:                            # plugin < user < project < local
        for layer in layers:
            merged.update(layer.get(scope, {}))
    return merged
```

- `wrap_channel` は、Slack、Discord、または SMS を同じプロトコル上の双方向サーフェスに変えます。タグ付けされたブロックは背景メモのようにキューに入れられます (セクション 13)。
- `merge_servers` は、複数のスコープで定義されたサーバーを解決します。 `local` は `project` をオーバーライドし、`user` は `plugin` をオーバーライドします。

誰でもチャンネルに送信できます。 Slack または SMS の受信メッセージは、必ずしもユーザーからのものであるとは限りません。スパムである場合や、エージェントを誘導するための指示である場合があります。
したがって、ターンになる前にゲートを通過します (Hermes は認証前に、受信メッセージごとに `pre_gateway_dispatch` を発行します)。

```python
def gate_inbound(source, payload, gates=()):           # src/mcp.py
    for gate in gates:
        out = gate(source, payload) or {}
        if out.get("drop"):
            return None                                # discarded: the model never reads it
        if out.get("rewrite") is not None:
            payload = out["rewrite"]                   # e.g. redact a secret
    return wrap_channel(source, payload)
```

- ループがテキストを確認する前に、ゲートがドロップ (スパム、不明な送信者) または書き換え (編集) される可能性があります。
- `None` を返すということは、ターンがまったく発生しないことを意味し、ジャンク入力としては最も安価な結果になります。

### 統合方法

デモではサーバーを検出し、エージェント ターンを 1 回実行します。モデルは MCP ツール ブラインドを呼び出します。

```python
reg = Registry()
for t in mcp.connect("kb", KBServer()):                # discover, wrap, merge
    reg.register(t)
run_turn([...goal...], model, reg, Session(mode=DEFAULT))   # the one agent call
```

- モデルは、組み込みの隣のツール リストで `mcp__kb__search` を確認し、それを呼び出します。誰がツールを作成したかは決して分かりません。
- このツールは読み取り専用であるため、ゲートはプロンプトなしで許可します。破壊的なツールは、修飾名をキーとするルールを要求するか、ルールによって事前承認されます。
- ループは変わりません。 MCP はツールをプールに追加します。下流のすべてはセクション 2 のディスパッチとセクション 3 のゲートです。

### さらに読む

これは `src/` にはありません。これは、ai-agent-book および MCP 仕様に基づいており、表内のシステムについては確認されていません。

**3 つのプリミティブ、1 つのプール。** サーバーは 3 種類のものを提供できます。ツールのみが上のプールに到達します。

- **ツール**はアクションです。モデルは 1 つを選択して呼び出します。 `tools/list` はこれらを返し、上記のコードはそれらをラップします。
- **リソース**は、クライアントが読み取ることができるデータであり、それぞれに URI (ファイル、テーブル、Wiki ページなど) が付いています。クライアントはそれを取得し、テキストをコンテキストに配置します。モデルがそれを呼び出すことはありません。
- **プロンプト**はサーバーから渡されるテンプレートです。これらは通常、モデルが選択したものとしてではなく、ユーザーが実行するコマンドとして表示されます。

**リソースはツール リストから除外されます。** Claude Code は、それらを 1 つずつアドバタイズしません。リソースを一覧表示するツールとリソースを読み取るツールの 2 つのツールが同梱されています。
したがって、1,000 個のドキュメントを保持するサーバーでも、ツール リストに 2 つのエントリが必要になります。

**接続と広告は 2 つの決定事項です。** サーバーに接続すると相互運用性が高まります。そのツールの宣伝にはコンテキストが費やされます。
2 番目の作業をすべて実行しなくても、1 番目の作業を実行できます。

**広告にかかる費用。** 宣伝される各ツールには、リクエストごとにトークンがかかります。名前、説明、完全な入力スキーマはすべてタスクの前に配置されます。
5 つのサーバーでは、タスク自体よりも多くのテキストを追加できます。また、リストが長いと、モデルが間違ったツールを選択する頻度が高くなります (セクション 2)。

**選択できる 3 つのレベル。** すべてのサーバーに対して一度ではなく、サーバーごとにアドバタイズする量を決定します。

- **すべて。** 最もシンプル。セッションがほぼ毎ターン使用するサーバーに最適です。
- **インデックス。** 名前と 1 行の概要を宣伝します。モデルがそのツールを要求したときに完全なスキーマをロードします (セクション 2 では検出側について説明します)。
- **1 つのドア。** サーバー名とツール名を取る 1 つのツールをアドバタイズします。残りはその後に残ります。エージェントは 50 のスキーマではなく 1 つのスキーマに対して支払います。

**これはプロトコルには含まれていません。** 仕様には、ツールをリストする方法とそれらを呼び出す方法が記載されています。そのうち何人がプロンプトに到達するかはクライアント次第です。
したがって、遅延読み込みは自分の harness で確認する設定です。サーバーは、サーバーがオンになっていると想定できません。

## 障害モード

- **名前の衝突。** 2 つのサーバーはどちらも `search` を公開します。 `mcp__server__tool` 名前空間は衝突を防ぎます。 `__` のサーバー名は依然として間違って解析されるため、名前は単純にしてください。
- **ツールリストの肥大化** 多くのサーバーは、トークンを消費し、選択を混乱させる大規模なツールリストを作成します (セクション 2)。
  軽減策: 説明を切り詰め、リクエストごとにすべてのスキーマを送信するのではなく、サーバーごとにアドバタイズする量を決定します。
- **接続後のプールが古い。** セッション中に追加されたサーバーはキャッシュされたツール リストにないため、モデルはそれを認識しません。
  軽減策: プールを再構築し、変更時にプロンプトを表示します (セクション 8)。 2026-07-28 の仕様では、これに対する `subscriptions/listen` および `ttlMs` ヒントに `toolsListChanged` が追加されています。
- **接続のチャーン。** 不安定なサーバーがタイムアウト、リセット、またはトークンの有効期限切れを起こします。軽減策: 繰り返し失敗した後に再接続し、`401` で再認証し、各呼び出しをタイムアウトします (セクション 11)。
  ステートレス リビジョンではストリームの再開可能性が低下するため、壊れた実行中のリクエストは再開されず、新しいものとして再発行されます。
- **過信された副作用** サーバーは、プロンプトをスキップするために、破壊的なツール `readOnlyHint: true` をマークします。軽減策: 修飾名に関するルールにより、とにかくそれが阻止されます (セクション 3)。
- **説明ポイズニング** ツールの説明はサーバーが作成したテキストであり、モデルはそれを指示として読み取ります。
  サーバーは、最初にユーザーのキー ファイルを読み取って送信するなど、そこに注文を隠すことができます。モデルならやってくれるかもしれない。
  軽減策: サーバーをインストールする前に説明をお読みください。変更した場合は、変更されたコードと同じようにレビューしてください。
- **ツール シャドウイング。** すべてのサーバーが 1 つのプロンプトを共有します。したがって、あるサーバーの説明で別のサーバーのツールについて語ることができます。
  支払いツールが壊れていると主張し、自分自身に呼び出しをプルします。
  軽減策: 名前空間により名前の衝突が防止されます。これでは止まらない。レビューされていないサーバーを実際の資格情報を保持するセッションから遠ざけます。
- **ハイジャックされた更新。** サーバーはレビューに合格し、次回の起動時に新しいコードと新しい説明を送信します。プロトコルはユーザーに再度質問することはありません。
  軽減策: バージョンを固定します。アップグレード後に説明をもう一度読んでください。各サーバーに独自の最小特権資格情報を与え、ある不良サーバーが別のサーバーのスコープに到達できないようにします。

## 実行可能

[`src/`](src/) は 18 を繰り上げて次を追加します。

- [`mcp.py`](src/mcp.py): 検出とラッピング、plugin 構成マージ、チャネル ラップ、および受信ゲート (`gate_inbound`)。
- [`test.py`](src/test.py): 検出と名前空間、ヒント マッピング、ゲートとのプールのマージ、構成の優先順位、チャネル タグ、および受信ドロップと書き換え。
- [`demo.py`](src/demo.py): エージェントの 1 ターンが、検出された `mcp__kb__search` を通じて、インプロセス MCP ツールをブラインドで呼び出します。

ループとディスパッチは変わりません。 MCP はセクション 2 プールにツールを追加します。セクション 3 ゲートは、自己宣言されたアノテーションを読み取ります。

```bash
python sections/19-mcp-plugins-channels/src/test.py         # offline checks, no key
uv run python sections/19-mcp-plugins-channels/src/demo.py  # live demo, needs a key
```
