# 2 · Tool runtime

[English](README.md) · [繁體中文](README.zh-TW.md) · [简体中文](README.zh-CN.md) · [日本語](README.ja.md) · **한국어**

> 기능을 추가한다는 것은 도구를 등록하는 것을 의미합니다. 루프는 동일하게 유지됩니다.

agent loop는 도구를 통해서만 작동할 수 있습니다. 모델은 `name`와 `input`가 포함된 구조화된 `tool_use` 블록을 출력합니다.

harness는 해당 이름을 코드에 매핑합니다. 입력을 검증하고, 핸들러를 실행하며, 결과를 반환합니다.

runtime은 다음을 수행해야 합니다:

1. 모델에게 어떤 도구가 존재하는지 알려줍니다.
2. 각 도구의 입력 스키마를 설명합니다.
3. 각 `tool_use`를 이름별로 라우팅합니다.
4. 가능한 경우 안전한 호출을 병렬로 실행합니다.
5. 대규모 도구 카탈로그가 탐색 가능하도록 유지합니다.

이 계층이 없으면, 모델은 행동을 요청할 수 있지만 아무 것도 실행할 수 없습니다.

하나의 `bash` 도구만으로 모든 기능이 문자열 처리 기능이 됩니다. 도구별 검증 또는 권한 로직이 없습니다.

두 가지 실패가 여기서 시작되며 모델이 책임을 집니다. 두 설명이 겹치기 때문에 잘못된 도구를 선택합니다. harness가 입력을 다시 작성했기 때문에 편집이 실패합니다.

## 메커니즘

![메커니즘 다이어그램](assets/02-tool-runtime.png)

도구는 이름, 핸들러, 스키마 및 몇 가지 술어를 가진 작은 객체입니다. 레지스트리는 도구를 이름별로 저장합니다. 디스패치는 조회입니다.

### 새 기능: tool runtime

```python
@dataclass
class Tool:                                  # src/tools.py
    name: str
    run: Callable[[dict], Any]
    description: str = ""                      # advertised to the model
    input_schema: dict = ...                   # the Anthropic schema it accepts
    is_read_only: bool = False
    is_concurrency_safe: bool = False         # may batch in parallel
    is_edit: bool = False                     # read by the gate (section 3)

class Registry:                              # src/tools.py
    def register(self, tool): self._tools[tool.name] = tool   # add a handler
    def get(self, name):      return self._tools.get(name)    # dispatch = lookup
    def schemas(self):        ...             # the tools list handed to the model
```

- 도구는 데이터 클래스입니다.
- 레지스트리는 `name -> tool`입니다.
- 기능을 추가한다는 것은 핸들러 하나를 등록하는 것을 의미합니다.
- `schemas()`는 모델에 광고된 도구 목록을 반환합니다.
- `run_concurrently` 배치는 `is_concurrency_safe`로 표시된 도구입니다.
- 안전하지 않은 호출은 순서를 유지하므로, 쓰기 작업이 경쟁 상태가 되지 않습니다.

### 통합 방식

섹션 1은 인라인 `HANDLERS` 사전을 사용했습니다. 섹션 2는 `registry`를 루프에 전달하고 `tool_use` 각각을 `_dispatch`를 통해 라우팅합니다:

```python
def run_turn(messages, model, registry, max_steps=10): # src/loop.py (now takes a registry)
    ...
    results = [_dispatch(b, registry)                   # was: run_tool(call)
               for b in response.content if b.type == "tool_use"]
    messages.append({"role": "user", "content": results})

def _dispatch(block, registry):              # resolve, run, wrap as a tool_result
    tool = registry.get(block.name)           # name -> tool
    content = run_tool(tool, block.input)
    return {"type": "tool_result", "tool_use_id": block.id, "content": content}
```

루프 본문은 그 외에는 변경되지 않았습니다. 이제 디스패치 단계에서만 레지스트리를 사용합니다.

`_dispatch`는 다음 확장 지점입니다. 섹션 3에서는 그곳에 권한 게이트를 추가합니다. 섹션 4에서는 hooks를 추가합니다.

데모는 명확성을 위해 순차적으로 디스패치합니다. 실제 런타임은 안전한 호출을 일괄 처리하고 필요에 따라 큰 도구 스키마를 로드합니다.

### 추가 읽기

이 내용 중 어느 것도 `src/`에 포함되어 있지 않습니다. 이는 ai-agent-book과 tool use에 발표된 자료에서 온 것이며, 표에 있는 시스템에서는 확인되지 않았습니다.
Claude Code가 언급될 때, 대비는 자체 소스에서 나옵니다.

**그룹화.** 도구는 호출이 어디로 가고 무엇에 영향을 미치는지에 따라 다섯 그룹으로 나뉩니다.

- **인식(Perception)** 은 외부 세계를 읽습니다.
- **실행(Execution)** 은 외부 세계를 바꿉니다.
- **협업(Collaboration)** 은 다른 에이전트에 도달합니다.
- **이벤트 트리거(Event trigger)** 는 외부 세계가 에이전트를 깨우도록 합니다.
- **사용자 통신(User communication)** 은 사람에게 도달합니다.

다섯 그룹 중 네 그룹은 나중에 별도의 섹션에서 다룹니다. 섹션 6, 12, 16은 협업을 다루고, 섹션 13과 14는 이벤트 트리거를 다룹니다.
섹션 19는 사용자 채널을 구축합니다. 이 섹션은 다섯 개 계층이 모두 위치하는 레이어를 구축합니다.
그룹화가 가치가 있는 이유는 계약이 다르기 때문입니다: 퍼셉션 호출은 안전하게 반복 및 배치할 수 있지만, 실행 호출은 그렇지 않습니다.

**세분화.** 예를 들어, 에이전트가 PDF, Word 파일, 스프레드시트를 읽어야 한다고 합시다. 하나의 도구를 사용할까요, 아니면 세 개를 사용할까요?

같은 종류의 입력에 대해 같은 작업을 수행한다면 도구를 합치세요. 타입 매개변수가 있는 하나의 `read_document`가 거의 동일한 세 개의 리더보다 선택하기 쉽습니다.
매개변수가 겹치지 않으면 도구를 나누세요. 관련 없는 필드를 결합하는 스키마는 어떤 필드가 적용되는지 알 수 없으므로 모델이 잘못된 필드를 채웁니다.

**설명 작성.** `description`는 모델이 도구를 선택하기 전에 읽는 유일한 텍스트입니다. 이는 사람을 위한 문서가 아닙니다.

유용한 것은 다섯 가지를 다룹니다:

- 도구를 언제 사용할지.
- 사용하지 말아야 할 때.
- 각 매개변수의 실제 값.
- 반환되는 값의 형식.
- 호출 비용.

몇 가지 실행 예시는 또 다른 산문 단락보다 더 도움이 됩니다. 책에서는 이를 추가함으로써 큰 이익을 얻었다고 보고합니다.
해당 수치는 출처가 없으므로, 크기보다는 방향을 참고하십시오.

**매개변수 충실도.** 모델은 중괄호 따옴표가 포함된 검색 텍스트를 가진 수정을 전송합니다. 처리기로 가는 동안 harness가 이를 곧게 펴줍니다.

이제 수정이 실패하고, 모델은 문자열이 일치하지 않았다는 사실만 봅니다. 올바른 입력을 보냈기 때문에, 전사본에는 그 간격에 대한 설명이 없습니다.
규칙은 다음과 같습니다: 입력을 변경하지 않고 핸들러에 전달합니다. 잘못된 입력은 거부하고 그 이유를 설명합니다. 절대로 다시 작성하지 않으며, 모델이 작성하지 않은 인수를 추가하지 않습니다.

**체크리스트 매개변수.** 환불 도구는 핸들러가 사용하지 않는 `expected_price`를 받습니다.

이를 기록하는 것이 핵심입니다. 모델은 호출이 실행되기 전에 자신이 생각하는 가격을 명시해야 합니다.
핸들러는 저장된 가격을 읽고 이를 결정하며, 두 값이 다를 경우 기록합니다.
따라서 마지막 검사는 모델이 조작할 수 없는 데이터를 기준으로 합니다. τ-bench 점수는 동일한 방식으로 실행됩니다: 에이전트가 했다고 말한 것이 아니라 최종 데이터베이스 상태를 읽습니다.

**지각 인터페이스.** 대규모 저장소를 검색하면 4,000줄이 일치하지만, 문맥에 들어가는 것은 처음 50줄뿐입니다.

세 가지 규칙은 결과를 정직하게 유지합니다:

- 검색은 후보 페이지 하나와 커서를 반환합니다.
- 읽기는 오프셋과 한계를 사용하므로 모델이 긴 파일을 탐색할 수 있습니다.
- 잘림은 결과에 표시됩니다.

조용한 잘림은 오류보다 더 나쁩니다. 모델은 파일 일부를 전체인 것처럼 읽고, 이후 모든 단계가 그 간격을 물려받습니다.

코드 검색은 선택을 보여줍니다. 네 가지 접근법이 있고, 어떤 시스템도 하나만 사용하지 않습니다:

| 접근법 | 찾는 것 | 비용 |
| --- | --- | --- |
| **Glob** | 경로 패턴에 따른 파일. | 내용에 대한 정보 없음. |
| **Grep** | 줄 번호와 함께 정확한 문자열과 정규식. | 쿼리를 좁히기 위해 여러 번 호출. 동의어를 놓침. |
| **임베딩 인덱스** | 의미별 코드화로 일반 언어 질의가 연결됩니다. | 구축하고 동기화 상태를 유지할 인덱스. 불투명한 순위. |
| **LSP 기호** | 정의, 참조 및 유형, 정확하게. | 언어별 언어 서버. |

Claude Code와 커서는 그 테이블의 반대편에 앉아 있다. Claude Code는 인덱스를 전혀 사용하지 않고 단계별로 검색한다: glob, 그 다음 grep, 그 다음 읽기,
호출 사이에 모델이 쿼리를 좁히는 것과 함께. 이 책에서는 대신 인덱스를 구축하기 위해 Cursor가 비용을 지불하는 것을 설명하며, 따라서 일반 언어 쿼리
식별자를 지정하지 않는 코드를 찾을 수 있습니다.

편집도 같은 방식으로 나눕니다. 변경된 내용을 말하는 다섯 가지 방법:

| 스킴 | 모델이 출력하는 것 | 절충 |
| --- | --- | --- |
| **Diff plus 적용 모델** | 대략적인 스켈레톤 diff를 두 번째 훈련된 모델이 다시 작성한 것. | 빠르고 관용적임. 두 번째 모델이 필요함. |
| **이전 문자열과 새 문자열** | 찾을 정확한 텍스트와 그 자리에 넣을 텍스트. | 명확하며, 문제가 있으면 즉시 실패함. 먼저 새로 읽어야 함. |
| **줄 번호** | 범위와 그 교체. | 간결함. 이전 편집으로 파일이 이동되면 구식이 됨. |
| **편집기 명령** | 작은 명령어 언어, vim 스타일. | 간결함. 하나의 구문을 더 잘못 쓰기 쉬움. |
| **앵커** | 시작 마커와 종료 마커. | 이동에도 살아남음. 마커가 반복되면 애매함. |

동일한 두 시스템이 편집에서 다시 나뉨. Claude Code는 정확한 이전 문자열을 교체하고 모델이 파일을 먼저 읽게 함,
그래서 오래된 문자열은 잘못된 줄을 편집하는 대신 명확하게 실패합니다. 책에서는 Cursor가 대신 거친 스켈레톤을 보내고,
두 번째 훈련된 모델이 그것을 바탕으로 파일을 다시 작성하며, 그 경로가 더 빠른 것으로 보고한다고 설명합니다.

**조기 시작 및 연쇄 중단.** 호출은 나머지 배치가 끝날 때까지 기다릴 필요가 없습니다. 자신의 인수가 파싱을 끝내는 순간 바로 시작할 수 있습니다.

모델은 여전히 이후 호출들을 작성하고 있으므로, 조기 호출의 지연 시간은 생성 과정 안에 숨겨집니다. 이것이 속도를 높여주며 실패에 대한 하나의 규칙이 필요합니다.
오류는 그것에 의존하는 호출들을 중단시킵니다. 같은 배치 내 독립적인 호출들은 계속 실행되며, 부모 턴도 마찬가지입니다.

**셸 상태.** 한 번의 호출이 `cd build`을 실행한 다음, 가상 환경을 활성화합니다. 다음 호출에서 둘 중 어느 것도 여전히 보이나요? 두 가지 설계가 있으며, 둘 다 옹호 가능합니다.

- **호출마다 초기화.** Claude Code의 bash 도구는 호출 간에 활성 셸을 유지하지 않습니다. 한 호출에서 설정된 변수와 셸 함수는 다음 호출에서는 사라지며,
  도구 설명에는 모델이 절대 경로를 사용하도록 지시합니다. 각 호출은 독립적으로 재현되며, 병렬 호출이 서로 침투할 수 없습니다.
- **하나의 지속 세션.** 본문은 공유 터미널을 기본값으로 설정하므로 `cd`, 내보낸 변수, 활성 가상 환경이 모두 유지됩니다.
  병렬 작업을 위해 별도의 셸도 여전히 사용 가능합니다. 모델은 설정 명령을 덜 반복하며, harness는 세션 상태를 추적하고 초기화할 수 있습니다.

**대규모 발견.** 20개의 연결된 서버가 수백 개의 도구를 제공하지만, 전체 스키마는 프롬프트에 맞지 않습니다.

그래서 레지스트리는 먼저 이름을 보내고, 어떤 항목이 요청될 때만 전체 스키마를 로드합니다. 요청은 모델로부터 평이한 언어로 들어올 수 있습니다.
MCP-Zero는 에이전트가 어떤 기능이 부족한지 말하게 하고, 이를 서버와 해당 서버의 도구와 매칭한 다음 일치하는 스키마만 주입합니다.
모델은 도구가 존재하는지 알 필요가 없으며, 이는 키워드 검색으로는 불가능한 일입니다.

**캐시 안전 로딩.** 로드된 스키마가 컨텍스트의 어디에 위치하는지가 비용을 결정합니다.

끝에 한 번만 추가하고 그대로 둡니다. 프롬프트 앞부분의 도구 블록을 편집하면 캐시된 접두사와 그 이후의 모든 토큰이 무효화됩니다(10장).
덧붙이면 접두사는 그대로 두고, 다음 차례에 스키마는 일반 기록으로 변합니다.

## 시스템별

각 에이전트가 도구를 정의하는 방법, 호출 경로, 병렬 처리 방식, 대규모 카탈로그를 노출하는 방법.

| | Claude Code | mini-swe-agent | deepseek-harness |
| --- | --- | --- | --- |
| **장점** | 도구별 검증, 권한, 병렬 처리, 지연 탐색. | 하나의 `bash` 도구, 작은 runtime, 카탈로그 없음. | 에이전트별 도구 세트; 호출당 하나의 감사된 파이프라인. |
| **단점** | 모든 도구가 계약을 가져야 함. | 도구별 검증이나 권한 없음. 게이트는 하나의 명령 문자열만 확인. | 간단한 도구조차 출력 계약을 선언해야 함. |
| **왜** | 기능별로 새로운 도구 하나; 루프는 그대로 유지. | 모든 동작이 셸 명령이므로 도구 하나면 충분. | 범위별 해결사가 하나씩 조회, 전송, 표시를 처리. |
| **방법: 도구 정의** | 스키마, 핸들러, 그리고 술어. | 하나의 `bash` 스키마, 하나의 명령 필드; 다른 이름은 오류 발생. | 스키마, 타입 지정 출력 계약, 본문, 순수 프리젠터. |
| **방법: 전송** | MCP로 권한 필터링된 풀에서 별칭 조회. | 레지스트리 없음. 모든 호출은 셸 명령. | 범위별 조회 후, 5단계 보호 파이프라인. |
| **방법: 병렬 호출** | 안전한 호출은 배치; 안전하지 않은 것은 단독 실행; 플래그 기본 꺼짐. | 아니요. 텍스트 모드는 응답당 하나의 동작만 수행. | 호출별 분류, 독점적으로 실패 시 닫힘. |
| **방법: 탐색** | 이름 먼저; 이름이나 키워드로 요청 시 전체 스키마 로드. | 한 도구만 있을 때는 필요 없음. | 지연 로딩 없음. 제한과 사전 설정이 각 범위를 형성함. |

## 실패 모드

- **알 수 없는 도구 이름.** 모델이 누락되었거나 비활성화된 도구를 지정합니다. 루프가 중단되지 않도록 `tool_result` 오류를 반환하세요.
- **스키마 드리프트.** 스키마는 한 가지를 말하는데, 핸들러는 다른 것을 기대합니다. 디스패치하기 전에 검증하세요.
- **안전하지 않은 병렬 처리.** 두 번의 쓰기가 동일한 파일을 손상시킬 수 있습니다. 도구가 안전한 것으로 알려져 있지 않은 한 기본적으로 순차 실행으로 설정하십시오.
- **카탈로그 오버플로우.** 도구 스키마가 너무 많으면 프롬프트가 혼잡해질 수 있습니다. 전체 스키마는 필요할 때까지 미루고, 캐시된 접두사가 유지되도록 로드된 스키마를 마지막에 추가하세요.
- **과도한 결과.** 큰 출력은 context window를 가득 채울 수 있습니다. 결과를 제한하고 전체 출력을 저장한 후 미리보기와 경로를 반환하세요.
  컷을 라벨링하세요. 침묵하는 컷은 모델이 전체인 것처럼 부분 파일을 읽도록 합니다.
- **잘못된 도구 선택.** 두 설명이 겹치거나, 하나의 도구가 두 가지 작업을 합니다. 중복된 항목을 합치고, 과부하된 스키마를 나누며, 각 도구가 무엇을 위한 것이 아닌지 명시하세요.
- **조용한 입력 드리프트.** harness는 핸들러로 가는 도중에 인수를 정규화하거나 추가합니다. 호출이 실패하고 모델은 그 이유를 알 수 없습니다. 나쁜 입력은 이유와 함께 거부하세요.
- **배치 실패가 확산됩니다.** 병렬 배치에서 하나의 호출이 실패하면 전체 실행이 중단됩니다. 그것에 의존한 호출만 중단하세요.
